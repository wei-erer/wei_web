# PART 9 · 渗透流程与解题方法论

*第 18–20 周 · 11 节*

> Web 安全不只有漏洞：真实的渗透是一条从授权、信息收集、验证、利用到报告的完整流程，CTF 解题只是其中一个片段。这一 PART 先把流程走通，再给做题的方法论。

---

## 渗透测试全流程：一次授权的测试长什么样

*约 30 分钟*

> 🎯 **本节目标**：能说出渗透测试的六个阶段，以及每个阶段「做什么、产出什么、边界在哪」。

CTF 题目只是「给你一个入口，把 flag 找出来」。真实工作里，一次测试是从**授权**开始的，中间有大量不是打漏洞的工作：范围确认、资产梳理、验证记录、风险沟通、修复复测。这一节先把整条链走一遍。

**六个阶段（PTES 简化版）**

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| ① 前期沟通 | 确认授权书、范围（域名/IP/时间窗）、禁止项（社工、破坏性操作） | 授权书、测试范围表 |
| ② 信息收集 | 子域、端口、指纹、目录、历史泄露（GitHub/备份）、员工信息 | 资产清单与攻击面地图 |
| ③ 威胁建模 | 按资产价值与暴露面排序，挑最可能成功的路径 | 优先级列表 |
| ④ 漏洞验证 | 每个疑似点做最小验证，记录请求/响应证据 | 漏洞清单（含复现步骤） |
| ⑤ 利用与后渗透 | 拿到权限后评估影响范围（绝不越权、绝不破坏） | 影响描述与证据 |
| ⑥ 报告与复测 | 风险评级、修复建议、复测确认 | 报告 + 复测记录 |

CTF 里你只做 ④（验证）和 ⑤（拿到 flag）；但找工作、打真实项目、做 SRC 时，②③⑥ 才是拉开差距的地方。

1. 把六个阶段抄进笔记，每个阶段后面写一句「这一步的产出是什么」。
2. 找一份公开的授权测试模板（SOW）读一遍，体会「范围」写得多细。
3. 想一想：如果没有授权就动手，你会踩到哪些法律红线（回到 p0l2）。

> 💡 「Web 不只是漏洞」——攻击链的每一环都要有依据。真实测试里，能说清「我怎么发现的、影响是什么、怎么修」比多打一个 shell 更有价值。

## 信息收集与资产测绘：先画地图再动手

*约 40 分钟*

> 🎯 **本节目标**：能对一个授权目标做一轮基础信息收集，产出一张「资产 + 端口 + 指纹」清单。

信息收集决定后面所有工作的上限。它的目标不是「扫得越多越好」，而是**用最少的请求画出最准的地图**：有哪些域名、哪些端口、什么技术栈、有没有泄露。

**四类收集**

| 类型 | 手段 | 常见工具 |
| --- | --- | --- |
| 域名与子域 | 证书透明度日志、字典爆破、搜索引擎 | crt.sh、subfinder、amass |
| 端口与服务 | 常见端口扫描、服务识别 | nmap、masscan（授权目标） |
| Web 指纹与路径 | 响应头、报错页、目录探测 | whatweb、dirsearch、Burp |
| 公开信息 | GitHub 泄露、网盘、招聘信息、历史备份 | GitHub 搜索、Google dork |

**一次最小化的收集流程**

```bash
# 1. 子域（从证书透明日志拿公开记录）
curl -s "https://crt.sh/?q=%25.target.com&output=json" | jq -r '.[].name_value' | sort -u

# 2. 端口与服务
nmap -sV -p 80,443,8080,3306,6379 target.com

# 3. Web 指纹
curl -I https://target.com/
whatweb https://target.com/

# 4. 目录与泄露（小字典先跑）
dirsearch -u https://target.com/ -e php,bak,zip,txt
```

**产出应该长什么样**

| 资产 | 端口/服务 | 指纹 | 备注 |
| --- | --- | --- | --- |
| www.target.com | 443 nginx | ThinkPHP 5.0 | 疑似旧版本，优先验证 |
| admin.target.com | 443 | Spring Boot + Actuator | actuator 未关闭 |
| target.com | 8080 Tomcat | Java 8 | 管理后台弱口令待验证 |

> 💡 所有收集动作都必须落在授权范围内；测完删掉本地数据。信息收集的最大风险不是「扫不到」，而是「扫了不该扫的」。

- [crt.sh（证书透明度查询）](https://crt.sh/)

## 漏洞验证与利用：把「可能」变成「已证明」

*约 35 分钟*

> 🎯 **本节目标**：学会用最小验证证明一个漏洞，并记录可复现的证据。

新人最容易犯的错是「看到一个参数就写报告说这里有注入」。验证的标准只有一条：**能稳定复现，且能说明影响**。

**验证的三条纪律**

| 纪律 | 做法 | 为什么 |
| --- | --- | --- |
| 最小化 | 只证明存在，不多取数据、不拖库 | 降低风险，也符合授权范围 |
| 可复现 | 保存原始请求/响应、时间、账号 | 别人能照着重放 |
| 有影响 | 说明能读到什么、改到什么 | 决定风险等级 |
| 留证据 | 截图 + 文本，别只留截图 | 报告需要原始数据 |

**一条合格的验证记录**

```
漏洞：订单详情水平越权
位置：GET /api/order?id=1001（当前账号 A）
验证：把 id 改为 1002，返回 B 用户的收货地址与手机号
证据：原始请求 / 响应（附）、两个账号信息、时间戳
影响：任意用户可读取他人订单与隐私信息
建议：服务端按 session 的 user_id 过滤，并返回 403
复测：修复后同一请求返回 403，已验证
```

> 💡 CTF 里「拿到 flag 就算赢」，真实测试里「能证明影响、能帮助修复」才算完成。这也是为什么同一道题，有人写报告像流水账，有人能卖出价钱。

## 后渗透与内网：拿到 webshell 之后

*约 35 分钟*

> 🎯 **本节目标**：了解拿到权限后的常见动作与边界，知道哪些能做、哪些绝对不做。

这一步在 CTF 里常常是「读个 flag 就结束」，在真实授权测试里则要回答一个问题：**这个入口能造成多大影响？**但所有动作都要在授权范围内，且以「不破坏、不外传数据」为前提。

**常见动作（按风险从低到高）**

| 动作 | 目的 | 边界 |
| --- | --- | --- |
| 确认权限与身份 | 知道自己是 www-data 还是 root | 只执行 id / whoami |
| 读配置与凭据 | 评估泄露影响 | 只读授权范围内的文件 |
| 内网探测 | 评估横向风险 | 严格按范围，禁止扫办公网 |
| 提权验证 | 证明影响 | 只做无害 PoC，不装后门 |
| 权限维持 | 一般不在授权测试中做 | 需单独书面授权 |
| 数据外带 | 绝对不做 | 用脱敏样本证明即可 |

**拿到 shell 后的前 5 条命令**

```bash
id                          # 我是谁
hostname && ip addr        # 我在哪
cat /etc/passwd | head      # 有什么用户
ls -la /var/www             # 站点目录
env | grep -i secret        # 有没有环境变量泄露

# 注意：这些命令只用于「评估影响」，不用于扩大战果
```

> 💡 红线：不装后门、不横向到范围外、不下载真实用户数据、不修改业务数据。CTF 里可以随便打，真实环境里每一条都要先问「授权了吗」。

## 报告与合规：风险评级、复现步骤与修复建议

*约 30 分钟*

> 🎯 **本节目标**：能写出一份让开发看得懂、改得动的漏洞报告。

报告是渗透测试的最终交付物。开发不关心你用了什么工具，只关心三件事：**在哪、怎么复现、怎么修**。

**一份报告的骨架**

| 部分 | 写什么 | 常见问题 |
| --- | --- | --- |
| 标题 | 漏洞类型 + 位置（如「订单接口水平越权」） | 写成「发现漏洞」 |
| 风险等级 | CVSS 或高/中/低，给出理由 | 只给等级不给理由 |
| 复现步骤 | 编号步骤 + 原始请求 | 步骤缺登录态/参数 |
| 影响 | 能读到什么、影响多少用户 | 写「危害巨大」没有细节 |
| 修复建议 | 具体到代码/配置层 | 只写「加强校验」 |
| 复测 | 修复后同样请求的结果 | 没有复测 |

**风险评级的一个简单口径**

```
高危：无需登录即可利用；或可读取大量敏感数据；或可直接执行命令
中危：需要普通账号；影响单个用户数据；或需要特定条件
低危：信息泄露（版本、路径）；需要极高交互成本
提示：仅内部信息、配置建议

（正式项目用 CVSS v3.1 计算，并附向量字符串）
```

> 💡 写报告时想象读者是赶工期的开发：**他能不能照着你写的步骤，在 10 分钟内复现并改掉**。这才是报告的合格线。

## 拿到一道题的第一分钟：做这七件事

*约 30 分钟*

> 🎯 **本节目标**：形成一套固定起手式：七件事做完，题目至少会给你三个可尝试的方向。

新手最常见的状态是：打开题目，看一圈，不知道从哪开始。老手的区别不是更聪明，而是**有一套固定动作**。这套动作不保证解出题，但保证你不会停在「一片空白」。

**七件事（按成本从低到高）**

| # | 动作 | 看什么 | 常见结论 |
| --- | --- | --- | --- |
| ① | 读题面 | 题名、描述、附件、提示 | 题名往往就是方向（备份文件 / 源码泄露 / 弱口令） |
| ② | 看 URL 结构 | 有没有 ?id= ?file= ?url= ?page= ?cmd= | 参数名直接指向漏洞类型 |
| ③ | 看页面源码 | HTML 注释、隐藏 input、内联 JS | 隐藏字段、flag、接口名 |
| ④ | 看 Network | 页面加载了哪些接口、传了什么 | 可复现的请求、可疑 API |
| ⑤ | 看响应头 | Server / X-Powered-By / Set-Cookie | 技术栈与框架 |
| ⑥ | 试探性输入 | 单引号、{{7*7}}、&lt;script&gt;、../、127.0.0.1 | 报错 / 回显 / 延时 = 信号 |
| ⑦ | 记录异常 | 报错、变长、跳转、变慢 | 异常就是入口 |

### 七件事的手动流程

1. 用 Burp 或 DevTools 打开题目，先**不要**着急改包，把页面完整走一遍。
2. 把每个功能点列出来：登录、注册、搜索、上传、下载、评论、导出、设置。
3. 对每个功能点问一句：**它背后可能用到哪种漏洞**？（见下面的功能地图）
4. 把「URL 参数 / 表单字段 / Cookie / Header」四处的输入位置各试一次。
5. 在笔记里写三行：这是什么类型的站、有哪些入口、我打算先试哪两个。

**功能 → 漏洞地图**

| 功能 | 优先想 |
| --- | --- |
| 搜索框 / 回显输入 | XSS、SSTI、SQLi |
| 登录 / 注册 | 弱口令、SQLi 绕过、JWT/Session 伪造、越权 |
| 上传头像 / 文件 | 文件上传绕过、图片马 + 文件包含 |
| 下载 / 导出 | 路径穿越、任意文件读取、SSRF |
| URL 预览 / 远程抓取 | SSRF |
| 评论 / 留言 / 昵称 | 存储型 XSS、SQLi |
| 个人资料 / 订单 | 水平越权（改 id） |
| 后台按钮 / 管理接口 | 垂直越权、逻辑漏洞 |

> 💡 七件事做完还没思路，就去看题目的「功能」本身：这个站是做什么的？每个功能背后都有一个潜在的漏洞类型。**先列功能，再选漏洞，比随机试 payload 快得多。**

## 题型识别决策树

*约 35 分钟*

> 🎯 **本节目标**：用一个决策树，把「一片空白」变成「三个候选方向」，并知道每个方向花多久。

把下面的树背下来（或者打印出来贴在显示器旁）。做题时顺着走，不要凭感觉乱试。

**主决策树**

```
题目给了源码吗？
├─ 给了 → 直接读源码，按「入口→变量→落点→判断」四步找漏洞
│         （PART 4 / p3l8）
└─ 没给
   ├─ URL 里有参数吗？
   │   ├─ ?id= / ?uid= / ?cat=      → 先试 SQL 注入（p5l3 / p5l4）
   │   ├─ ?file= / ?page= / ?path=   → 先试文件包含 / 路径穿越（p5l7）
   │   ├─ ?url= / ?image= / ?link=   → 先试 SSRF（p5l9）
   │   ├─ ?cmd= / ?exec=             → 命令执行（p5l8）
   │   └─ ?q= / ?search= / ?name=    → XSS / SSTI（p5l5 / p5l11）
   ├─ 有登录/注册吗？
   │   ├─ 有 → 弱口令、SQLi 登录绕过、JWT 伪造、越权（p5l15 / p5l16）
   │   └─ 无 → 继续往下
   ├─ 有上传功能吗？        → 文件上传（p5l6）
   ├─ 有 XML 输入吗？       → XXE（p5l12）
   ├─ 前端有加密/校验逻辑？ → 读 JS，控制台直接调用绕过（p1l6 / p3l2）
   └─ 什么都没有？
        └─ 信息收集：目录扫描、备份文件、.git、robots.txt（p6l3）
```

**参数名 → 首选漏洞（速查）**

| 参数名 | 首选 | 次选 |
| --- | --- | --- |
| ?id= / ?uid= | SQLi | 越权（改成别人的 id） |
| ?file= / ?page= | 文件包含 / 路径穿越 | 任意文件读取 |
| ?url= / ?image= / ?link= | SSRF | 命令执行（若被拼进命令） |
| ?cmd= / ?exec= / ?ping= | 命令执行 | 代码执行 |
| ?q= / ?search= | XSS（反射） | SQLi（拼进 like）、SSTI |
| ?name= / ?msg= | XSS（存储） | SSTI |
| ?lang= / ?tpl= | SSTI | 文件包含 |
| Cookie / Authorization | JWT 伪造 / 反序列化 | 越权 |

**拿到 flag 位置后的第二棵树**

```
需要读文件？
├─ 有文件包含 → php://filter / 日志包含
├─ 有 SSRF   → file:// / gopher://
└─ 有命令执行 → cat /flag

需要伪造身份？
├─ Cookie 里是明文 → 直接改
├─ 是 JWT          → alg=none / 弱密钥 / 算法混淆
└─ 是序列化数据    → 反序列化（p5l13 / p5l14）

需要出网但没有回显？
├─ 写文件到 web 目录
└─ DNSLog / HTTP 外带
```

> 💡 决策树的价值不是「一定对」，而是**把茫然变成有序的尝试列表**。每个分支给 2 分钟，不行就换下一个——这一步的纪律比聪明重要。

## Web 题切入点清单（打印版）

*约 30 分钟*

> 🎯 **本节目标**：把这两张清单存进笔记，做题时逐条对照，避免漏掉入口。

**按「输入位置」列清单**

| 输入位置 | 可能注入的漏洞 | 怎么试 |
| --- | --- | --- |
| URL 参数 | SQLi / SSTI / 文件包含 / SSRF / 命令执行 | 改一个字符看报错/回显/长度 |
| POST 表单 | SQLi / XSS / 上传 / 反序列化 | Burp 里改字段重放 |
| Cookie / Header | 反序列化 / 伪造身份 / XFF 伪造 / SQLi | 逐个头改一遍 |
| User-Agent | SQLi（有些题存 UA 进库）/ 命令执行 | 换 UA 看行为变化 |
| 文件名 | 上传绕过 / 路径穿越 | 改扩展名、改目录部分 |
| JSON 字段 | 原型链污染 / 反序列化 / 逻辑越权 | 加 __proto__ / 改 id |
| XML 输入 | XXE | 加 DOCTYPE 实体 |
| Referer | CSRF 校验旁路 / 逻辑校验 | 换成内网/管理员域名 |

**按「页面现象」列清单**

| 你看到的 | 意味着 |
| --- | --- |
| 报错里出现 SQL 关键字 | SQLi（报错注入优先） |
| 页面回显我输入的内容 | XSS（反射）/ SSTI |
| 能下载文件、路径可猜 | 路径穿越 / 任意文件读取 |
| 有「加载远程图片/URL 预览」 | SSRF |
| 有「记住我」「token」 | JWT / 反序列化 |
| 有「验证码」 | 复用 / 爆破 / 前端绕过 |
| 价格、数量、积分能改 | 逻辑漏洞 |
| URL 里有 id 且能看别人数据 | 水平越权 |
| 响应里出现 base64 大串 | JWT / 序列化数据 / 编码套娃 |
| 页面里引用了 /static/ 或 .map 文件 | 前端源码泄露（source map） |

> 💡 这两张表最好手抄一遍。手抄的过程中你会自然记住「哪里该试什么」，比读十遍有用。

## 卡住了怎么办：五种破局

*约 30 分钟*

> 🎯 **本节目标**：建立「卡住不等于不会」的处理流程，并学会用时间盒管理自己。

**五种破局手段**

| 症状 | 动作 | 为什么有效 |
| --- | --- | --- |
| 完全没思路 | 回头补信息 | 大概率是信息没收集全：再扫目录、再读 JS、再读题面 |
| 参数试不通 | 换输入位置 | 很多题的过滤只做了 GET，换成 POST / Cookie / Header 就过了 |
| 不知道怎么拿 flag | 反向思考 | 想要 flag 需要什么能力？倒推哪个漏洞能提供这个能力 |
| 利用链差一步 | 降维验证 | 先确认「这里有没有问题」（如猜对一位长度），再想自动化 |
| 实在卡死 | 按纪律看 WriteUp | 只看「第一步从哪入手」，然后关掉自己继续做 |

**时间盒规则（很重要）**

```
单个方向：最多 15 分钟
单道题：  最多 60 分钟（入门阶段）
超时 → 记下当前思路，换题或看提示

卡住 30 分钟以上的最大原因不是难，
而是「在错误的方向上反复试同一件事」。
```

### 卡住时的三分钟自检

1. 我试过的方向，是不是都属于同一类漏洞？（如果是，换一个大类）
2. 我是不是在同一个参数上反复改，而没有换输入位置？
3. 我能不能用自己的话说出「这题到底要什么」？（说不出来就回去读题面）
4. 我把当前进度记下来了吗？（记下来，才敢放下）

> 💡 「换个方向」不等于放弃。你的目标是学会这一类题，不是死磕这一道。做完复盘，这道题的收益才算拿到。

## WriteUp 六问复盘法

*约 30 分钟*

> 🎯 **本节目标**：每道题都能转化成可复用的知识，而不是「做过了」。

做完题（或看完 WriteUp）后，强迫自己回答六个问题，写进本页底部的「我的笔记」——那里就是你的复盘本。

**六问：问什么、为什么问**

| # | 问题 | 为什么必须回答 |
| --- | --- | --- |
| 1 | 漏洞为什么会出现？（哪一行、哪个错误假设） | 决定你能不能在新题里认出同一个错误 |
| 2 | 用户输入经过了哪些处理？ | 过滤漏在哪，就是你下次的绕过点 |
| 3 | payload 每一部分有什么作用？ | 拆不开 payload = 换个环境就不会 |
| 4 | 为什么其他尝试没成功？ | 决定你下一次该先试什么，避免重复劳动 |
| 5 | 开发者应该怎么修？ | 修复思路比利用更能说明你理解了原理 |
| 6 | 换个环境还成立吗？ | 区分「这道题特有」与「通用原理」 |

**复盘模板（直接抄进笔记）**

```
## 题目：____（平台 / 题目名 / 类型）

1. 漏洞原理：
   ____（一句话：输入从哪来，被当成了什么）

2. 输入处理：
   ____（有无过滤；过滤做了什么；哪一步漏了）

3. payload 拆解：
   ____（逐段说明作用）

4. 失败尝试：
   ____（试了什么；为什么不行）

5. 修复方式：
   ____（代码层怎么改）

6. 可迁移性：
   ____（下次遇到什么特征就该想到它）
```

> 💡 只收藏 WriteUp 会产生「我好像会了」的错觉。用自己的语言复述原理，才是真正理解的开始。**建议本课程中心的「我的笔记」就是你的复盘本。**


### 自测 · 答不上就回去重读

2. 为什么「修复思路」也要写？

4. 你打算把复盘写在哪？

## 比赛策略与赛前清单

*约 25 分钟*

> 🎯 **本节目标**：知道比赛里怎么分配时间、怎么避免低级失误，并有一张赛前一晚能照着过的清单。

**时间分配（以 4 小时赛为例）**

| 阶段 | 时长 | 做什么 |
| --- | --- | --- |
| 开局 | 0–10 分钟 | 把所有题扫一遍，按「看上去会」排序 |
| 热身 | 10–40 分钟 | 先拿 1–2 道低分题，建立手感 |
| 主攻 | 40–150 分钟 | 攻中档题；单题超过 40 分钟没进展就换 |
| 查漏 | 150–180 分钟 | 回头处理卡住的题，或补环境问题 |
| 收尾 | 最后 30 分钟 | 确认 flag 已提交、WriteUp 素材已保存 |

**赛前检查清单**

```
环境
[ ] Burp / Yakit 能正常抓 HTTPS
[ ] 浏览器代理插件配置好
[ ] Python + requests 可用
[ ] 常用字典、脚本目录就绪
[ ] 网络稳定（VPN/代理确认）

知识
[ ] SQLi / XSS / 文件类 / SSRF 的基本 payload 能默写
[ ] 知道怎么快速判断技术栈
[ ] 记得决策树（p7l2）

心态
[ ] 允许自己卡住
[ ] 卡住就换题，不较劲
```

> 💡 多人队伍里最重要的一条：**随时同步「我在试什么、结果如何」**。三个人各打各的，等于一个人打三遍。
