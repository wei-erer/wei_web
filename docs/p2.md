## HTTP 请求与响应结构

*约 30 分钟*

> 🎯 **本节目标**：能逐行拆解一个原始 HTTP 请求和响应。

HTTP 是「一问一答」的文本协议。读懂它，是后面所有漏洞的前提。

**请求的四部分**

```http
POST /login HTTP/1.1          ← 请求行：方法 + 路径 + 版本
Host: example.com             ← 请求头开始
User-Agent: Mozilla/5.0
Content-Type: application/json
Cookie: session=abc123
Content-Length: 27
                              ← 空行（必须）
{"user":"admin","pw":"123"}   ← 请求体
```

**响应的四部分**

```http
HTTP/1.1 200 OK               ← 状态行
Content-Type: text/html; charset=utf-8
Set-Cookie: session=abc123; HttpOnly
Content-Length: 26
                              ← 空行
<h1>Hello, Web!</h1>          ← 响应体
```

- **请求行**：方法、路径（含查询串 ?a=1&b=2）、协议版本。
- **请求头**：Host、Cookie、User-Agent、Referer、Content-Type 等。
- **请求体**：GET 一般没有；POST/PUT 携带数据。
- **响应头**：Content-Type、Set-Cookie、Location（重定向）、Server。

> 💡 CTF 里「改请求」改的通常是这几处：路径参数、请求头（Cookie/Referer/X-Forwarded-For/User-Agent）、请求体。90% 的 Web 题都是在这三个位置做文章。

## 请求方法与状态码

*约 25 分钟*

> 🎯 **本节目标**：能根据方法和状态码判断发生了什么，并知道哪些状态码在 CTF 里是「有戏」的信号。

- **GET** 取数据，参数在 URL；**POST** 提交数据，参数在请求体；**PUT** 更新；**DELETE** 删除；**HEAD** 只要响应头；**OPTIONS** 查支持的方法（CORS 预检会用到）。

- **200** 成功｜**301/302** 重定向｜**304** 缓存未改
- **400** 请求格式错误｜**401** 未认证｜**403** 拒绝访问｜**404** 不存在｜**405** 方法不允许
- **500** 服务器内部错误｜**502/503/504** 网关/服务不可用

CTF 里的状态码信号：

- 本该 403 的页面返回 200 → 可能绕过了权限校验。
- 同样的请求，改一个参数后响应长度变了 → 存在注入或条件判断（盲注的核心）。
- 500 且报错里带 SQL 语法 → 注入点暴露。
- 302 跳到 /admin → 可能已经拿到管理员会话。

> 💡 别只看状态码。**响应长度、响应时间、响应内容差异**，往往比状态码更能说明问题。

## Cookie、Session、Token

*约 35 分钟*

> 🎯 **本节目标**：讲清「登录状态」的三代实现方式，以及各自的攻击面。

HTTP 是无状态的：服务器默认不记得你上次来过。为了让「登录一次，之后都认识你」，诞生了三种方案。

**① Cookie + Session（服务端存状态）**

```http
响应：Set-Cookie: session=8f3a...; HttpOnly; Path=/
请求：Cookie: session=8f3a...

服务端：session 表里 8f3a -> {uid: 1, role: "user"}
特点：浏览器只拿到一个随机 ID，真实数据在服务器
```

**② JWT（信息存在 token 里）**

```js
// JWT 由三段组成：header.payload.signature
// payload 是 base64url，任何人都能解开看
{
  "alg": "HS256",
  "typ": "JWT"
}
.
{ "uid": 1, "role": "user" }
.
<用密钥算出的签名>
```

JWT 的关键认知：**payload 是明文可读的（只是 base64），安全性完全依赖签名。**所以攻击面很明确——篡改 payload 后能否让签名校验通过。

- **Cookie 相关攻击面**：session id 可预测、未设 HttpOnly 被 XSS 偷走、SameSite 缺失导致 CSRF。
- **JWT 相关攻击面**：alg 改成 none、弱密钥可爆破、公钥当私钥用（算法混淆）、kid 注入。
- **前端存储 token 的风险**：放 localStorage 会被 XSS 读走。

实操：F12 → Application → Cookies / LocalStorage，看这个站存了什么。

## 用 curl 手动发请求

*约 30 分钟*

> 🎯 **本节目标**：脱离浏览器，用命令行精确控制每一个请求头。

浏览器会「帮你补全」很多头，这反而让你看不清到底发了什么。curl 让你完全掌控。

**常用姿势**

```bash
# 最基础
curl https://example.com/

# 只看响应头
curl -I https://example.com/

# 跟随重定向，并显示过程
curl -L -v https://example.com/

# 发 POST 表单
curl -X POST -d "username=admin&password=123" https://example.com/login

# 发 JSON
curl -X POST -H "Content-Type: application/json" \
     -d '{"user":"admin"}' https://example.com/api

# 带上 Cookie
curl -b "session=abc123" https://example.com/profile

# 自定义任意头（伪造 Referer / XFF）
curl -H "Referer: https://admin.example.com" \
     -H "X-Forwarded-For: 127.0.0.1" https://example.com/
```

> 💡 浏览器 Network 面板里右键请求 → **Copy as cURL**，可以直接得到等价命令。这是从「浏览器操作」过渡到「脚本操作」最省力的桥。
